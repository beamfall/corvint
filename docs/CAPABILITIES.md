# Corvint capability catalog

This is the one page for an agent that knows nothing about Corvint. It lists every `corvint`
command, every binary built from `cmd/`, and every MCP tool. For each one it says what question
it answers, when to use it, the smallest call, what comes back, how mature it is, and when it
refuses or abstains. Each claim is taken from the code and `--help` text on the revision that
holds this file. The [capability catalog spec](specs/capability-catalog-v0.md) (CAP-V0) owns the
page, and `tools/capabilities-check` fails `go test ./...` when a command, binary or MCP tool
has no row, when a row names something that no longer exists, when a code-declared subcommand is
missing from its command's row, when a command's maturity disagrees with its root help group, or
when a listed refusal code no longer appears in the source.

The binary carries two more views of the same surface. `corvint help --json` prints a
machine-readable command catalog (`corvint-capability-catalog/0`) derived from the command
registry: fields the registry cannot answer are `null` and named under `unknowns`; `corvint help
--json COMMAND` prints one command's entry, under 5 KB (`corvint-capability-command/0`,
CAP-V0-950). `corvint help guide` prints a task-indexed guide with runnable examples and the
non-capabilities each tracked by an issue (CAP-V0-015 to CAP-V0-021).

For a dated, counted snapshot of this page by maturity, with the first promotion batch and its
unmet gates, see the [Core promotion inventory](build-log/2026-10-29-core-promotion-inventory.md)
(V1-3180). It is a snapshot, not a second catalog: when the two differ, this page is right.

## Command trees

Every public command at every depth, including single-mode companion roots,
ships a `corvint-command-tree/0` catalog with usage, flags, required inputs and an example
(CAP-V0-7700). Use the printing command in each tree's `helpJson` field;
`corvint help --json` links every tree. Snapshots live under `internal/capcatalog/trees/`.
`corvint-cli --binary BINARY [COMMAND...] --help` (also `-h`) supplies each node's offline
usage, flags, required inputs and example (CAP-V0-9300). The adapter's own help is
`corvint-cli --help`. A literal `help` node has its own page with `help --help`.
Native analyzer protocol frames and folded compatibility help retain their original behavior;
uniform discovery does not imply that every native invocation exits 0 for a help flag.
The complete node table below is generated by `make capability-catalog` and checked by
`tools/capabilities-check`; missing dispatch words, flags, binaries, MCP tools or node rows fail
the existing required Go test shards. The legacy CLI ratchet is empty. `llms.txt` links every
printing command and snapshot.

The native compatibility paths are all sixteen `corvint-analyzer-*` binaries listed below and
`corvint-test-runner`. `corvint-js-test-provider` also retains its authored provider help. Use the explicit discovery profile for a uniform page.

Use `corvint help --json` → `mcpTools` for offline MCP tool names, summaries,
server/profile selection and role conditions. MCP tools do not accept CLI help flags.
The configured server's live `tools/list` supplies input schemas and configured availability;
the offline catalog does not assert that a tool is enabled there. The [MCP tool tables](#mcp-tools)
below give minimal calls, and [MCP setup](MCP-SERVER.md) explains profile selection.

CLI failures use `binary`, `code`, explanatory `error`, `help`, and `ok:false` on stderr
(ACX-V0-7707). Native evidence and diagnostic fields are retained, with the original document
in `details`. Exit 2 means invalid CLI input; exit 1 means operational refusal; exit 0 means
success. A documented domain result such as an open frontier keeps its own advisory exit.
Protocol-only analyzer/MCP traffic keeps its own wire contract. Companions use Core's release
line and development suffix.
`make install-local LOCAL_BIN_DIR=DIR` installs all native binaries, with one rollback executable
per destination; put DIR on PATH. Existing foreign `.bak-*` files are not updater-owned and remain
untouched.

How to read maturity:

- **core**: the verbs `corvint help` lists as Core (decision 0332). Only the modes and profiles
  the [Core compatibility freeze](specs/core-compatibility-freeze-v1.md) lists are frozen. Other
  modes of the same verb can be experimental; the row says so.
- **experimental**: no stability promise. The owning spec governs the behaviour.
- **implemented**: the owning spec records delivery. This is still not a 1.0 stability promise.
- **internal**: CI, release or qualification tooling, not for everyday agent use.

Every Corvint read reports what it could not see. An `UNKNOWN`, `NOT_RUN`, `NOT_OBSERVED`,
`NOT_PRODUCED` or `unsupported-*` result is the answer, not a crash. Keep it and do not replace it
with a guess. Commands are local-only, with no network or telemetry. `init`, `adopt`,
`feature` and `impact` are qualified on Darwin and Linux only.

## Start here

| Task | Command sequence |
|---|---|
| Orient on an unfamiliar repository | `corvint init`, then `corvint overview` for the inferred shape and suggested next commands |
| Find the files to read for one task | `corvint context --task "TEXT" --subject PATH` |
| Check what a change reaches | `corvint impact PATH...` for paths, or `corvint impact --base FULL_SHA` for the committed range to `HEAD` |
| Choose the tests for a change | `corvint affected --base FULL_SHA` for the plan; `corvint test --base FULL_SHA --dry-run` to see the experimental Go run without running it |
| Get advice on a branch | `corvint review --base FULL_SHA`: compact affected advice and overlap with local branches (experimental) |
| Look up documentation | `corvint docs corpus build --manifest M > corpus.json`, then `corvint docs corpus search --artifact corpus.json --query TERM`, or serve it with `corvint-mcp --tool-profile corpus` ([guide](DOCUMENTATION-CORPUS.md)) |
| Map an application for E2E selection | `corvint flows appmap ...` ([application map](APPLICATION-MAP.md)) |
| Inspect application flows | `corvint flows --manifest FILE`, then `flows coverage`, `flows gaps` (`--provider FILE` adds the E2E tests no variation links) and `flows status` (each flow, variation, attached tests and last result) ([flow coverage](FLOW-COVERAGE.md)) |
| Give an agent host Corvint tools | `corvint mcp --root /abs/repo` over stdio; add `--tool-profile flows` or the groups `test-validity`, `test-evidence`, `docs`, `corpus` and `affected` (`corvint.affected`, `corvint mcp` only) ([MCP](MCP-SERVER.md)) |
| Read retained live-test evidence | `corvint test-validity --discover`, or the `corvint.test_validity` tool of `corvint-test-validity-mcp` |

## Commands

One row per top-level command in `corvint help`. Run `corvint COMMAND --help` for the complete
contract; the subcommands named here are the ones the help lists.

Columns: Q = the question it answers; Use / not = when to use it and when not; Min = the smallest call; Out = what it prints.

## MCP tools

`corvint help --json` includes an offline `mcpTools` entry for every tool below:
`name`, `availability` (server/profile conditions) and `summary`. The source inventory
check rejects missing entries; configured `tools/list` supplies the argument schemas
and actual availability. The [root snapshot](../internal/capcatalog/catalog.json)
ships these entries even without a running server.

Each server speaks MCP over stdio, is bound to one repository root, and is read-only. Tool names
are the `corvint.*` names in `tools/list`. The [MCP guide](MCP-SERVER.md) covers setup and the
protocol version: both servers speak MCP `2026-07-28` (no `initialize`; every request carries
metadata) unless started with `--protocol-version 2025-11-25` for an `initialize`-first client.

`corvint-mcp` profiles: the default lists `corvint.help`, `corvint.impact` and `corvint.status`.
`--tool-profile flows` adds the five `corvint.flows.*` tools. The comma list may also name the
groups `test-validity` (`corvint.test_validity`), `test-evidence` (`corvint.test_evidence`),
`docs` (`corvint.docs_draft`, `corvint.docs_consume`), `corpus` and `affected` (`corvint.affected`,
served only by `corvint mcp`, which holds the planner; `corvint-mcp` refuses the group by name).
`corvint-docs-mcp` and `corvint-test-validity-mcp` also list `corvint.help`.
The corpus group (`--tool-profile corpus --corpus-artifact ALIAS=PATH`) lists only the
`corvint.docs_*` tools that the artifact's capabilities support.

uncertainty instead of a guess.
