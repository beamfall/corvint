## Job and verified current state

CI publishes a review request for documentation approved separately from a product merge, with a complete inventory of what the agent corpus gained, changed and retired. Public main f51f3c9e6fbfc5a6b219692e8bf46e4e43297a36 (historical reviewed base; non-test implementation/owning-contract guard unchanged at current public 1fda1b94984245d0cd0ac0a6d17cc72572ce6619) has no republish command/package/spec in bounded cmd/internal/spec searches. Existing compilation is deterministic with a supplied timestamp and builder tuple. Existing adoption sharding enforces closure within one manifest, but cannot detect a shard deliberately removed from both the next manifest and inputs. Existing import parity is input-to-output parity, not previous-to-next parity. Existing connector keys include merge identity; successive documentation merges create separate drafts. Private proof confirms these distinctions, not new implementation acceptance.

## Requirements

- `RCP-V0-001`: The operator supplies separate closed request and trusted approval-policy files. Policy pins repository, approved full documentation commit, canonical manifest SHA256, publication target and prior result/artifact SHA256. Only the approved state authorizes building. Missing/revoked/pending approval, revision mismatch, manifest mismatch, unavailable commit or mismatched repository fails before build/cache/request/output effects. Source revision is a separate immutable field; a product merge alone never admits a build.
- `RCP-V0-002`: Approval pins bind the exact documentation bytes: every provider/document input declared for the republish must be reachable at the documentation commit with matching path/blob/content digest; source inputs bind the separate source commit. An immutable full commit is required; refs and wall-clock discovery are excluded. A policy copied by an author is not authenticated approval. Host-owned policy and its provenance remain outside author writes; the local process attests pin matching, not forge authentication.
- `RCP-V0-003`: Closed versioned input/output profiles reject unknown/duplicate members, invalid identity/path/enum and oversized input. Fixed explicit timestamps and sorted stable identities make identical request, policy, builder/toolchain and pinned input bytes produce identical artifact, provenance, parity and connector request bytes. Ambient paths, duration, cache hits and execution timestamps stay outside those canonical bytes.
- `RCP-V0-004`: Provenance names documentation/source commits, repository identity, compiler and companion revisions, schema versions, Go/tool versions, canonical manifest digest, all provider versions and every input path/revision/blob/content digest. Corpus and indexed byte digests bind produced bytes. Dirty/unrecorded builders remain explicit limitations; they do not qualify immutable release provenance.
- `RCP-V0-005`: Previous-artifact parity enumerates added, retired and changed stable IDs for subjects, claims, relations, journeys and observations, including typed details and relevant capability/coverage/behavior/stability changes. The entire inventory is compared, independent of paging. Missing previous bytes/digest is unknown and fails a replacement run; first publication requires an explicit trusted baseline-none policy. No percentages imply behavioral adequacy.
- `RCP-V0-006`: Parity additionally compares provider/shard input inventories, even for empty or restricted-only shards. A previously present shard omitted from the proposed manifest is a blocked dropped-shard finding unless the trusted policy explicitly declares its retirement (provider ID + canonical path). Report missing shards and their record retirements separately. A retention exception does not hide raw counts. Unknown/missing/duplicate shard identity blocks.
- `RCP-V0-007`: Where a manifest explicitly admits dependency-closed reuse, rebuild only changed shard contributions; unchanged contributions may be reused solely from an operator-digest-pinned previous producer result with matching compiler, schema, profile and complete dependency fingerprints. Across the complete command, including previous-artifact validation and indexed production, only changed eligible shard contributions may be built. Reused complete records must equal their source-pinned originals after the existing evidence normalization and pass the same provider predicates. Always revalidate original immutable bytes, all restricted tokens, aggregate limits, duplicate IDs, cross-shard joins and final global semantics. Never infer independence from an unchanged path or a caller boolean. Unsupported/native/behavior/observation shard profiles use the ordinary full-build fallback with a named reason. Reuse and cold build must produce exactly the same final bytes; cache choice is operational evidence only.
- `RCP-V0-008`: The actual consumer is the existing indexed artifact reader: build corpusindex from the source-validated corpus, Open with the externally pinned digest, and retain real query/trust-envelope evidence. Serving or uploading is outside the republish command. Reader source-validation/freshness/authenticity limits remain unchanged.
- `RCP-V0-009`: Emit a typed republish plan through the existing connector package. Its fixed generated body contains only validated identifiers, digests and counts plus allowed evidence URL. The pending key hashes an unambiguous repository + publication target + corpus-kind tuple, independent of documentation/source revisions and individual change IDs. The request remains draft=true. Exact retry is a no-op; a later approved revision replaces that same pending draft. A rejected/stale/unapproved request does not overwrite the prior request. Approval policy binds the current generation/prior digest so an older revision cannot replace a newer pending revision.
- `RCP-V0-010`: The optional pending-state writer is host-owned, trusted-local and single-writer. Validate the entire plan and prior state before a private exclusive-temp/atomic-replace write; use connector destination protection, reject symlinks/aliases/nonregular paths and protect both product and documentation roots plus their Git administrative/common paths. Invalid input, interrupted preparation and stale generation preserve the previous complete state. No concurrent-writer, hostile-directory-swap, remote transaction or power-loss guarantee is claimed.
- `RCP-V0-011`: The builder, author and deterministic connector writer receive separate host environments. The command reads no outward-write credential and performs no network/publication operation. Policies, previous artifacts, mutable outputs and caches remain outside author worktrees. Tests and local pin matches cannot promote approval authenticity, independent adoption, external switch-over, or host credential isolation.

## Minimal approval admission and pending replacement algorithm

This is an explicit trusted-local profile. The independently configured host step, running outside the author environment, selects an approval-policy file and its SHA256. The command accepts `--trusted-local --policy FILE --expected-policy-sha256 SHA`; these options belong to the host/operator invocation, not to the request file or an agent tool. A digest supplied by an author is not authenticated authority. The host's operating-system/configuration isolation is a stated prerequisite, not something this CLI can infer from matching bytes. The local fixture qualifies deterministic admission under that prerequisite; no forge approval connector is invented or fetched.

The request has no approval boolean/state/issuer slot. Closed policy fields are profile, repository, target, decision (`APPROVED`, `PENDING`, `REVOKED`), full documentation/source revisions, canonical manifest digest, fixed build timestamp, expected previous pending generation/digest, previous result/artifact digests or explicit first-build NONE, `reuse_eligibility` (a sorted unique array of exact provider-ID/shard-path pairs), `previous_sidecar_profile` and `previous_sidecar_sha256` (or both explicit NONE), allowed shard retirements, and an opaque decision-record identity for attribution. Policy bytes and configured SHA must match before `APPROVED` is consulted. The decision-record identity alone authenticates nothing. Producer records the policy/decision attribution and the trusted-local qualification limit in provenance. Author-authored policies, request-level approval fields and policy-hash mismatch refuse.

1. Read and strictly decode request and policy under their bounds; verify policy bytes against the host-configured SHA and require `APPROVED`. Require the request tuple (repository, publication target, docs/source commits, manifest digest, timestamp and canonical `reuse_eligibility` array) to equal the policy tuple. The request cannot add or remove an eligible shard: compare the full array, not only its count. Hash that array deterministically as `reuse_eligibility_sha256`. If reuse is selected, require the prior Result and policy to agree on `previous_sidecar_profile`/`previous_sidecar_sha256`, and require its sidecar eligibility digest to equal the current one; changed eligibility or mismatched profile/digest refuses cache admission. A deliberate cold build consumes no prior cache and uses an explicitly policy-matched empty eligibility array; do not silently label a rejected cache reused. Verify full commits and every manifest input from immutable Git: provider/document bytes equal the bytes at the approved documentation commit; source/evidence bytes bind their declared source revision. Reject stale/missing/mismatched inputs before cache/build/output effects. This admits the documentation event independently of the product merge.
2. For replacements, require the digest-pinned previous result and artifact named by policy; for a first build, require the policy's explicit NONE values and expected generation zero/state NONE. Recompute previous-result/artifact bytes, canonical schema/digests and source bindings, plus the exact sidecar bytes/profile/digest referenced by both policy and previous Result when reuse is selected; unknown or missing prior inventory refuses. Build the next corpus/index and complete parity, apply explicit shard-retirement exceptions without hiding findings, and verify an actual indexed consumer query. Unsupported incremental profiles take the named cold-build path.
3. Canonical Result (`corvint-corpus-republish-result/0`) contains immutable provenance, artifact/index byte digests, complete parity, `reuse_eligibility_sha256`, and `incremental_sidecar` with exact `profile` (`corvint-corpus-incremental-cache/0`) and canonical-byte `sha256`, or explicit NONE when no sidecar is emitted. The Result has no pending request or self digest. Policy pins the prior Result digest, which transitively pins its sidecar profile/digest; compare those members against the policy's explicit previous-sidecar pins before reuse. `resultSHA256 = SHA256(canonical Result)`; the generated connector body can then include that digest without a hash cycle. Derive the pending key as `pm-` + SHA256(canonical array `[repository, target, "corpus-republish"]`). Build the fixed request with that key and deterministic branch, draft=true, validated digests/revisions/counts and allowlisted evidence URL. No arbitrary body/template slot. The queue must rederive Result/request from pinned inputs before any state write.
4. Use one canonical Pending file per repository/target, not an append-only request ledger. Fields are profile, repository, target, unsigned generation, policy digest, docs/source revisions, result digest and the single connector Request. Strictly decode and verify existing state, including key/branch/draft invariants, and compare its complete original bytes/digest. If existing state already contains the identical result, policy digest, revisions and request, return NOOP with the existing generation and bytes. Approval is still checked on that invocation. This permits an exact retry of the same approved grant after its first successful replacement.
5. Otherwise require the existing generation and original-byte SHA256 to equal the policy's expected previous generation/digest (or both explicit NONE/zero with absent state). Replayed older grants fail this comparison and preserve state. The host-approved grant orders replacements; timestamps, commit lexical order, product merges and caller booleans grant nothing. A newly approved explicit policy may select its exact documentation revision; ancestry or a local timestamp cannot substitute for policy authority. Increment generation exactly once with overflow refusal and produce the new single Request under the same pending key.
6. The host provides a private single-writer destination directory separate from policy, request, previous artifacts/cache, source/documentation roots and both roots' Git common/administrative directories. Use the connector's bounded no-follow/destination-protection primitives. Create an exclusive mode0600 temporary file there, write and close the complete canonical new Pending, check context, then reread and compare prior state to the expected original bytes immediately before atomic rename. NOOP writes nothing. Failed validation, write/close, changed-prior detection or cancellation before rename removes only the owned temporary file and preserves prior bytes. A successful rename is the local commit point; cancellation after that cannot be called rollback. This is atomic file visibility under the single-writer prerequisite, not a concurrent CAS or power-loss guarantee.

The existing `postmergeconnector.Request` and deterministic `Writer.Upsert` remain the consumer contract. Implement separately typed `BuildRepublishPlan`/`ValidateRepublishPlan`/`ApplyRepublishLocal`/`SaveRepublishPending` in `internal/postmergeconnector/republish.go`; do not mutate the existing Input/Build validator or inject edited bodies into ordinary plans. `ApplyRepublishLocal` must prove the same key replaces one Forge map entry across two documentation revisions. `SaveRepublishPending` applies the algorithm above and readback proves one pending file/request; ordinary connector historical recording is observational history, never the pending queue. Remote provider exactly-once and replacement semantics remain separately unqualified; this command performs no cloud post.

Discriminating controls: missing/revoked/pending policy, author request approval field, policy-hash mismatch, wrong doc/source/manifest pin; whole-shard omitted from both manifest and inputs; unchanged request retry; newer grant replacing the same key; stale previous generation/digest retaining byte-identical prior state; corrupt prior state, unsafe destination and pre-rename cancellation retaining prior bytes. Actual host credential isolation and approval authenticity remain NOT_OBSERVED unless independently retained evidence supplies them.

## Incremental design and limits

Keep DCP /1 and /2 unchanged. Add an opt-in incremental build API with a versioned sidecar (not evidence authority) and explicit reuse-eligible provider/shard groups supplied by the republish request, admitted by trusted policy. Narrow initial eligibility to ordinary adoption-provider record shards without native/behavior/observation contributions. The closed `corvint-corpus-incremental-cache/0` sidecar records each exact provider-ID/shard-path pair and complete dependency fingerprint. Its eligibility digest is part of that fingerprint and must match request/policy/prior Result. Record the complete import contribution before global joins; reuse requires the trusted previous-result digest, exact prior artifact/sidecar digests, same shared compiler tuple and all source/provider/profile/anchor dependencies, not only the provider shard digest. Changed source identities conservatively invalidate all dependent shards. Preload every provider to screen restricted tokens even when contribution is reused, then run the existing global validations/finalization; omission must not bypass restricted screening. Unsupported profiles rebuild normally with a named reason. A cache entry restores all compiler state that the original import contributed: subjects, claims, relations, journeys and observation contributions if a future admitted profile supports them; capability declarations; adoption-provider membership (even when a shard contributes zero public records); every typed detail; unaggregated import-parity rows including zero/count/reason semantics; and all other recorded inputs to aggregate counts, capabilities, adoption joins and final restricted-output checks. For this initial ordinary-adoption profile, observation/behavior contributions are ineligible and cold-built. Recompute provider preload/restricted-token registration from original inputs rather than trust cache tokens. Restore contributions through bounded duplicate/membership/count checks into fresh compiler state, never by replacing its global state or copying a prior final artifact. Missing membership/details/parity or an unknown contribution field refuses; global validations cannot infer absent contribution state as success.

Required negative witnesses alter only the eligibility array while preserving shard bytes, replace sidecar profile/digest/bytes, and independently remove cached adoption-provider membership, one typed detail and one import-parity contribution. Each must refuse or, only for a declared unsupported profile, take the named cold path; no altered cache may be reported reused. The cold oracle must compare complete final artifact bytes including typed details, import parity, restricted summaries, capabilities and gaps, with cross-shard joins still evaluated.

`doccorpus.BuildIncremental` performs the same final artifact construction and checks as Build; avoid a second compiler or parallel index/server. Refactor only the required contribution/finalization seam. In the discriminating two-shard test, counters must show zero compilation of the unchanged shard and one changed-shard compilation while global validation still runs; a full independent Build is the byte oracle. Prior verification reconstructs the complete canonical corpus with source-validated eligible reuse and exact original-byte equality. Indexed production consumes an opaque immutable compiler result, without repeating shard materialization. Ordinary cold APIs remain independent test oracles; every immutable input is still loaded and validated. No speedup, bounded-memory improvement or reduced total validation cost is claimed without measurement.

Resources retain existing DCP bounds (128 provider shards; /2 input/artifact bounds and record/journey caps). Republish request/policy/provenance/parity are each bounded 4 MiB; deterministic pending state has one request per declared target; reject parity over bound rather than truncating required inventory. A build/result may be up to the existing corpusindex bound, no new global capacity promise. Contexts bound Git/process operations; no permanent daemon, worker queue, Tasks store or network service is created.

## Failure modes, rollout and rollback

Approval/ref/manifest/source mismatch, missing prior result, dropped shard, cache incompatibility, unsafe output, stale pending generation and incomplete parity fail closed. Unsupported reuse falls back to full build with an explicit reason; it cannot convert failed verification into reuse. Emit diagnostics separately from canonical artifacts. Write only to explicit private fresh output locations or the admitted pending-state destination. Reuse connector file protections rather than generalizing a new filesystem layer.

Rollout is a separately built experimental `cmd/corvint-corpus-republish` companion with plan/build and explicit trusted-local queue subcommands; no Core registration, release archive/install change or CI auto-trigger. Rollback stops invocation and reverts task-owned code while preserving generated outputs and previous state. No store migration, state erase, release or external publish is needed.

## Experimental implementation readback (code phase)

The narrow code-phase implementation exists in `internal/corpusrepublish`, `cmd/corvint-corpus-republish`, `internal/doccorpus/incremental.go`, and `internal/postmergeconnector/republish.go`; proposed intent and delivery qualification are unchanged. Request and policy use nested `binding` objects for the matching approval tuple; the request embeds the canonical manifest. Source markdown may also be source evidence, but its exact blob must be reachable at the separately approved documentation commit. Every provider input binds that documentation commit; source/evidence inputs bind the separate source commit. A host policy and prior artifacts located inside either author checkout or Git metadata are refused by the command's existing connector destination protection. This verifies layout only, not host or forge authentication.

Canonical Result stores `consumer` as a typed operation/receipt-byte-digest/trust-envelope witness; the actual indexed receipt's original bytes are retained in `consumer.json`. Generic result values are not decoded and re-encoded inside the Result, avoiding a false noncanonical refusal after a typed receipt becomes generic maps. The Result still pins every actual consumer byte and retains the reader's existing source-validation/authentication limits. Provenance explicitly retains unrecorded/dirty builder and host-isolation limits.

The private `postmerge-republish-pending/0` representation is `{profile, generation, plan}`. Its closed typed plan retains rendering input (repository, target, documentation/source revisions, policy/Result/corpus/index digests, counts and allowed evidence URL/origins) plus exactly one existing connector Request. It therefore retains the logical fields above and lets validation rederive every fixed body byte on disk readback. There is no author template or edited-body slot. NOOP compares the entire canonical plan; otherwise the original previous bytes and generation must match policy before the exclusive temporary write/re-read/atomic rename. Build artifacts use fresh exclusive files, may retain already completed fresh files after a later output failure, and never overwrite prior bundles. Queue replacement remains atomic under its trusted single-writer prerequisite.

## Last repair2 source-validation amendment (proposed)

The original issue requires only changed eligible shards to be built across the whole command. The prior implementation reimported both shards during prior Open, prior index production and final index production; an actual isolated compiled CLI coverage witness measured first build4, unchanged replacement6 and one-changed replacement7 imports. Inner Stats therefore did not qualify the complete capability. This proposed amendment requires a non-wire, package-minted immutable VerifiedCorpus from the complete compiler boundary; a zero, forged or caller-mutated Artifact cannot qualify. Prior incremental Open retains exact source rederivation and canonical original-byte equality, using fully source-bound cached-record validation. Index production accepts only that token or the unchanged ordinary cold source-validation API. All original provider/schema/purpose/bounds/capability/details/evidence/journey/anchor predicates and restriction/global validation remain mandatory. Cache pins grant byte identity, never authority to invent record fields. Cold byte/refusal comparison remains a separate test oracle, not a production reimport. The actual complete-command RED/GREEN counter proof includes prior validation, both index productions and the indexed consumer; target counts for two eligible shards are first2, unchanged0 and one-changed1. No accepted intent or external qualification is inferred.
