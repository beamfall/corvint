## Human intent and scope

`docs/specs/REQUIREMENTS.tsv` is generated by `script/gen-spec-requirements.sh`, which scans every
spec body for lines shaped like a requirement definition and, for each id, keeps the best match it
finds. A requirement-coverage table that merely lists an id in a row is itself a valid match for
that scan, at lower rank than a real definition line but still a match. That means a generated index
can go on citing an id, and every previously-generated-and-committed copy of the index can still
compare equal to a fresh regeneration, after the paragraph that actually defined the requirement has
been deleted — because the coverage-table row that survives is exactly the same kind of "definition"
the generator would have used if the clause body had never existed.

This is not hypothetical: commit `dfd02ea` deleted eighteen GPK clause bodies from
`go-production-kernel-migration-v0.md` while their coverage-table rows and their
`REQUIREMENTS.tsv` entries stayed put. `spec-requirements-check` (which only diffs a fresh
regeneration against the committed index) passed, because nothing about the row-only ids had
changed. A worker later reading the spec to write a performance manifest found the clauses missing;
the loss surfaced by inspection, not by gate. Commit `0913cd2` restored the clauses. This gate is
the mechanical check that a coverage-table row is not evidence that the clause it names still
exists.

Affected user: an agent or engineer editing or reviewing a spec body, and any downstream reader of
`REQUIREMENTS.tsv` who treats a listed id as proof that requirement text exists. Measurable job: for
the committed working tree, refuse to let a requirement id survive an edit as a table row with no
clause body anywhere, and refuse to let two clause bodies both claim to define the same id.

The owner instruction of 2026-09-07 places repository gate tooling in scope for AGENTS.md invariant
8. This spec discharges that for `script/check-requirement-definitions.sh` only. Three of the four
sibling gate scripts named in `../agent-memory/fixes.md` remain unspecified.

## Requirements

- `RDG-V0-001`: The gate MUST read every non-blank row of `docs/specs/REQUIREMENTS.tsv`, take the
  first tab-separated field as a candidate id, and check it further only when that field matches the
  shape "one or more letters/digits/hyphens starting with a letter, ending in a literal hyphen and
  exactly three digits". A row whose first field does not match this shape MUST be left unchecked
  rather than reported.
- `RDG-V0-002`: The gate MUST exempt every id starting with `CEM-CB-` from RDG-V0-003, because
  `cem-0.2-canonical-binding.md` documents that family only as table rows by design and never had a
  clause body.
- `RDG-V0-003`: The gate MUST fail when a checked id (per RDG-V0-001, after the RDG-V0-002 exemption)
  has no recorded definition location anywhere in the files scanned under RDG-V0-004, and MUST list
  every such id in its failure output.
- `RDG-V0-004`: The gate MUST scan every file matching `docs/specs/*.md` except
  `docs/specs/README.md`, and MUST record a definition location for an id on any line where, after
  only leading whitespace, an optional `-`/`*` bullet, and optional surrounding `**` and backtick
  markers are stripped, the id is immediately followed by `:` or `.`. An id appearing later in a line
  (for example, named in running prose) MUST NOT be recorded as a definition.
- `RDG-V0-005`: The gate MUST fail when the same id is matched as a definition (per RDG-V0-004) at
  more than one location, whether or not that id is checked under RDG-V0-001, and MUST report the id
  together with every location beyond the first.
- `RDG-V0-006`: When a successful Git index query establishes that
  `docs/specs/REQUIREMENTS.tsv` is not tracked, the gate MUST exit success without scanning any spec
  file or reporting any failure. If that Git query fails operationally, the gate MUST instead
  diagnose the Git failure and exit non-zero.
- `RDG-V0-007`: The gate MUST NOT write to any file. After RDG-V0-006 has established that the TSV
  is tracked and the scan completes, the gate MUST exit non-zero exactly when RDG-V0-003 or
  RDG-V0-005 found at least one failure, exiting zero otherwise. Operational failures remain
  non-zero.

## Non-goals and simpler baseline

The simpler baseline is `spec-requirements-check` alone, which regenerates `REQUIREMENTS.tsv` and
diffs it against the committed copy; that check is unaffected by this gate and stays in place. This
gate does not judge requirement text for correctness, completeness, or adherence to the canonical
`- \`PREFIX-NNN\`: text` shape in `../SPEC-DRIVEN-DEVELOPMENT.md` — RDG-V0-004's match is broader
than that shape (it also accepts an unbulleted line and a period-terminated form), so a line can
satisfy this gate while still being invisible to a stricter reader such as the OCM intent reader
named there. It does not check that a definition's row in `REQUIREMENTS.tsv` cites the same file and
line the gate found, does not check ids that never appear in `REQUIREMENTS.tsv` at all (except when
they collide with a duplicate, per RDG-V0-005), and does not run when the TSV file is absent rather
than empty.

## Trust boundary, limits, and failure modes

Spec files and `REQUIREMENTS.tsv` are untrusted input read from the working tree; the gate performs
no writes and takes no revision argument, so it always checks the tree as currently checked out. It
shells out to `perl` to do the scan; a missing or broken `perl` is an environment failure, not a
finding, and is out of scope for this spec. Both failure classes are collected across the whole
corpus before the gate exits, so one run reports every row-only id and every duplicate rather than
stopping at the first.

| Failure | Behavior |
|---|---|
| Id is a row in `REQUIREMENTS.tsv` with no clause-body definition anywhere in scope | fail, listing the id |
| Id is `CEM-CB-*` with no clause-body definition | pass, by RDG-V0-002 |
| Same id defined at two or more locations | fail, naming the id and every location beyond the first |
| `docs/specs/REQUIREMENTS.tsv` absent | pass trivially, by RDG-V0-006 |
| Git cannot determine whether `docs/specs/REQUIREMENTS.tsv` is tracked | fail with a Git diagnostic, by RDG-V0-006 |
| TSV row's first field does not match the id shape | unchecked, neither pass nor fail is reported for it |
| Id named only in running prose (not at line start) | not recorded as a definition; can make an otherwise-defined id read as row-only |

## Rollout, rollback, and drift

The gate is already load-bearing in `make gate` and has no feature flag; rollback is removing the
`requirement-definitions-check` prerequisite from the `gate` target and reverting
`script/check-requirement-definitions.sh`, which returns the repository to the state that let
`dfd02ea` pass silently. Drift rule: `script/gen-spec-requirements.sh`'s definition-matching regex
and this gate's must be read together whenever either changes, because a row the generator would
promote to "defined" but this gate would not recognize (or vice versa) reopens the gap this spec
closes — the two scripts are not required to share code today, only to agree on what counts as a
definition line.

## Unresolved

The two scripts' definition-matching regexes are maintained independently and were not diffed
against each other while writing this spec; whether they can silently diverge is not established
here. Three sibling gate scripts (`check-decision-numbers.sh`, `check-traceability-tests.sh`,
`check-sql-native-ratchets.sh`) remain unspecified.
