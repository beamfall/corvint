## V1-1380: allocation no longer depends on the json/v2 encoder pool (DCP-V1-085)

### Decision

`json.Marshal` draws its output buffer from a `sync.Pool`. A cold encoder grows the buffer
geometrically (about 190 MB for one 29.8 MB corpus, V1-0587), a warm one does not, and a GC cycle,
a P migration or race instrumentation empties the pool. The canonical-form checks of
`doccorpus.ParseArtifact` and `corpusindex.Open` and the digest `hashValue` computes now stream the
deterministic encoding (`json.MarshalWrite`, whose streaming encoder never buffers the whole
output: its working buffer starts at 4 KiB and grows only to the largest single token, and the
pool retains it up to 64 KiB) into a comparer or a sha256 hash, and the two re-encodes `Open` keeps (the corpus it reparses
and the derived index) go into a buffer pre-sized from the input. The writer is wrapped so jsontext
does not take its `*bytes.Buffer` path, which regrows whenever less than a quarter of the length is
free and would defeat the pre-sizing. `Encode` and its ~40 small callers are unchanged.

Contract: encoded bytes, digests, output bounds and refusal messages are unchanged; a value whose
encoding exceeds its bound is still refused with `output bound exceeded`. The DCP-V1-040 1 GiB
ceiling and its race guard are unchanged. New requirement `DCP-V1-085`, accepted under the owner's
standing auto-accept (2026-10-11); no accepted requirement is amended.

## V1-0328: re-index writes a full 153.7 MB snapshot per tree (measured; no change)

Measured on this repository at base (8,978 tracked files, 113,663,473 tracked bytes, 8,488 admitted
sources, 53,460 symbols) with the base binary, in a separate clone. Cold: the snapshot store was
removed, then `corvint index`. One-file change: a one-line append to
`internal/contextindex/snapshot.go`, committed, then `corvint index`.

| Run | Snapshot bytes | Wall s | User+sys CPU s | Max RSS | Load (1-min) |
|---|---|---|---|---|---|
| cold 1 / 2 / 3 | 153,683,500 each | 5.44 / 10.47 / 16.01 | 8.42 / 8.75 / 9.44 | 1.21-1.25 GB | 44.0 / 42.7 / 40.2 |
| one-file 1 / 2 / 3 | 153,683,541 each | 6.03 / 9.50 / 15.82 | 8.26 / 8.04 / 9.37 | 1.15-1.40 GB | 42.9 / 40.6 / 49.2 |

Cold median 10.47 s wall (range 5.44-16.01), 8.75 CPU s; one-file median 9.50 s wall (6.03-15.82),
8.26 CPU s. The finding holds and is larger than filed: every tree change rewrites the whole
153.7 MB file (not 63 MB), and the shared store gains a second 150 MB file per tree until eviction
(8 files, 1 GiB). A one-file change costs the same as a cold build.

Where the time goes (scratch test calling `BuildForSnapshot` and `encodeSnapshot`, three runs,
loads 48.6-44.8): build 6.15-11.09 s, gob encode 0.40-0.72 s, sync and close 5-10 ms. Source
bodies are 99,458,253 of the 153,683,491 snapshot bytes (65%). The encode allocates 814-874 MB,
because a gob encoder buffers each top-level value whole before writing it; that is most of the
1.2-1.4 GB peak RSS.

Recommendation: no change in this lane. Every way to write fewer bytes per tree (reusing unchanged
blob facts, not storing bodies, or a lazily loaded pack) changes the snapshot format, which needs
the `deployment-neutral-index-platform-v0.md` format gate and an owner decision under invariant 7.
The design for it is `2026-10-06-v1-0328-large-repo-index-design.md`; its earlier per-blob shard
variant was falsified on latency (decision 0073). The encode and write are 5-10% of each run's
build-plus-write time, so a write-only change would not repay a format change; the cost that matters is the
repeated build (6-11 s) and the 150 MB of disk and 0.8 GB of transient allocation per tree. Owner
decision needed: whether to schedule the 2026-10-06 design (format change) or close V1-0328 with
this measurement.

  `doccorpus`, `appflows`, `flowcoverage` and `appmap` hit the 30-minute per-package timeout under
  that load; `doccorpus` then passed its new tests and the capacity test separately (above).
  `lspstdio` (`TestNativeContextWorker`, semantic backend tests) and `postmergeworkflow` (replay
  tests) failed on process deadlines and `Backend unavailable`; the same tests fail the same way
  in a worktree at base under the same load (61-67; lspstdio 5 of 6 and postmergeworkflow all 8

  binary-exec units were not run; the repository gate is run by the orchestrator.
- Review, one Codex round: one P2, that the comment and spec claimed the streaming encoder stays
  within a 4 KiB buffer when it grows to the largest single token. The wording in `encoding.go`,
  DCP-V1-085 and this entry was qualified. No byte, digest, bound or refusal regression was found.
