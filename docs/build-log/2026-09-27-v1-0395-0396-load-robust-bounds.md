## 2026-09-27 V1-0395 V1-0396 LCP-V0-008: a Git probe expiry is a time bound, and the ledger concurrency test waits out load

Both were found on a loaded host (load about 200 to 430 on 12 CPUs) while running focused tests for
other rc.1 fixes.

V1-0396. The Git repository probe has its own fixed 10-second bound
(`internal/gokernel/repository.go`, `repository-probe-timeout`). Under load it expired inside a
dogfood event whose deadline was longer, and the event reported the generic
`dogfood-event-unavailable`. LCP-V0-008 already requires an expiry to report
`dogfood-event-deadline`, never the generic code, even when it first surfaces as a failed repository
read. Decision: `runLocalCompletionEvent` treats a `repository-probe-timeout` error from the read as
that time bound and reports `dogfood-event-deadline` (or `dogfood-event-index-snapshot-stale` after
a snapshot-miss build, as for any expiry). The probe's own bound is unchanged. LCP-V0-008 now names
the probe expiry, the reason table says so, and the self-observation ledger sentence no longer
claims that the code is returned only after the event deadline.

V1-0395. `TestAppendSerializesConcurrentProcesses` started 24 helper processes under one 10-second
context, and each helper waited at most 5 seconds for the start barrier. Under load `command.Start`
failed with `context deadline exceeded` after 12 seconds. Both bounds are hang detectors, not latency
budgets (decision 0082); they are now 5 minutes and 2 minutes.

Evidence: the `LCP-V0-008 Git probe expiry` subtest of `TestDogfoodEventStrictInputAndDeadline`
returns a `repository-probe-timeout` error from the read under a one-minute deadline and expects
exit 2 with `dogfood-event-deadline`.

Rollback: revert the change; a probe expiry again reports `dogfood-event-unavailable`, and the
concurrency test again fails under load.
