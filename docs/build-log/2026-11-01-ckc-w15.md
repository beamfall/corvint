# 2026-11-01 ckc-w15 content-keyed citation claims (V1-3980)

Lane ckc-w15 built CEM 2.0 Phase 1a at origin/main `b7ffc233396da54e2ac5a094ec314dc3b067f6fb`:
reviewed citation-plan rows are recorded as claims keyed by path, edit content and BASE anchors,
and compiled back to current hunk IDs at refresh time. The spec is
`docs/specs/cem-content-keyed-claims-v0.md` (`CKC-V0-001`..`013`), intent `proposed`, delivery
`experimental`. The cem/1.0 wire, `cem`, the seal and every verifier are unchanged.

## Decisions

- Decision: claims are a private lane input file (`corvint-dogfood-claims/v0`). They are not a
  CEM field and are never read by `cem`. The compiled output is an ordinary citation plan keyed by
  full hunk ID, so binding it is the existing bind path, and the map bytes are those of the
  equivalent hand-keyed plan (`TestClaimsCompileByteIdenticalCEM`).
- Decision: an exact match is path + `contentSha256` + BASE range, relocated by the anchor only
  when BASE moved. The claim is never matched by hunk ID, ordinal or range alone. This is the key
  difference from `--refresh PLAN`, whose second matcher (path + BASE range) carries rows across
  content changes.
- Decision: every ambiguous case refuses for reassessment, and the hunk is drafted afresh. The
  refusal classes are `duplicate`, `unlocated`, `split`, `merged`, `changed` and
  `cite-unlocated`. A claim that overlaps no hunk is `gone`. Refusing costs one manual edit, but
  it never yields a wrong carry.
- Decision: duplicate content is refused even when BASE is unchanged, because no anchor can tell
  the copies apart without guessing. This is a known limit: a lane that pastes the same block
  twice reviews both copies again.
- Decision: tombstones are keyed by path, relation and the SHA-256 of the cited BASE text, not by
  line numbers, so a deleted cite stays deleted after BASE renumbers it. A suppressed hunk gets
  the draft's unknown fallback row, whose note names the removed row, so the precheck
  (DCW-V0-019) still passes. Unknown rows are never tombstoned.
- Decision: `record-claims` is a separate command, not a side effect of the refresh. This keeps
  `propose-citations` read-only (DCW-V0-150).
- Decision (AC3 follow-up): `record-claims` reads its BASE blobs through one `ls-tree` and one
  `cat-file --batch` (CKC-V0-012), and so does a claims compile after BASE moved. The shared
  drafting path (`--refresh PLAN`, plain drafts and governing-spec reads) still reads blobs one
  file at a time. Batching it would speed both flows by the same amount, so it cannot close a
  claims-versus-current gap; it is left for a separate optimization.
- Decision: recording is not folded into the refresh. A step's record needs the plan the author
  reviewed from that refresh's output, which exists only after the refresh returns. The next
  refresh runs after a fix commit has re-keyed the hunks, so it would have to re-read the
  previous HEAD's patch, which is the same cost the record pays now. Recording inside the bind
  loop would reuse the bind's patch, but that loop is `script/dogfood-*.sh`, owned by lane
  icl-m15. It would also move the cost to closeout rather than remove it.
- Decision: carried cite spans join the draft's `used` set, the same as `--refresh PLAN` carries.
  A hunk drafted afresh therefore never repeats a span that a carried row already cites.

## Replay methodology

`TestClaimsReplay` is env-gated. It replays real fix sequences of this repository, and the
sequences file is built by scratch scripts that are not committed.

- **Sequence form.** Each sequence is `NAME MAPCOMMIT BASE0 COMMIT:BASE ...`.
- **Choosing sequences.**
  - Each sequence starts at a sealed cem/1.0 map committed under `.corvint/changes/`.
  - The fix commits are the next first-parent commits on the same lane or batch branch, up to 8
    of them.
  - A step's BASE is BASE0, unless the merge base with main moved.
  - 48 candidates were found. The first 20 that replay cleanly are counted. One candidate was
    excluded because its plan exceeded the claim bound.
- **Step 0.** The sealed map's rows are the reviewed plan. Both flows start from that plan. The
  claims flow records it, with the plain draft as `--draft`.
- **Each later step.** The harness checks out COMMIT and runs, in process:
  - the plain draft;
  - `--refresh PLAN` (the current flow);
  - `--refresh CLAIMS` (the claims flow).

  The author then fixes the output to the target. The claims flow records the fixed plan, with
  its own output as `--draft`.
- **Oracle target.** The oracle is independent of both flows.
  - A hunk keeps the predecessor's reviewed rows when its path and raw body equal exactly one
    earlier hunk's, unique in both directions. When BASE moved, each cite is moved to the single
    line-aligned occurrence of its cited bytes.
  - Any other hunk takes the plain draft's rows. Unknown rows match by reason. A cite the author
    deleted from the step-0 draft for that file becomes an unknown row.
- **Manual edits.** For each hunk, an edit count is `max(extra rows, missing rows)` against the
  target, so a replaced row counts once.
- **Incorrect carry.**
  - For the claims flow, it is any output row outside the target on a hunk that the claims
    compile carried. The harness runs the same `claimsCompiler` on the same claims file and patch
    to learn which hunks were carried.
  - For the current flow, it is any output row outside the target that equals an earlier
    reviewed row. That count is an upper bound, because it also catches drafted rows that happen
    to coincide with earlier ones.
- **Time.** Time is wall-clock per step for the in-process `ProposeCitations` call. The claims
  flow also adds its `RecordClaims` call.

### Oracle refinement (disclosed)

The first full run used the current flow's rule for both flows: an output row outside the target
that equals an earlier reviewed row. That rule flagged 2 claims-flow rows. Debug output showed
that neither was a carry:

1. **batch-1031c, step `9214d096d37b`, `script/check-line-citations.sh` BASE 575,6.** No claim
   matched this hunk, so the claims flow drafted it afresh. The plain draft cites
   `daily-change-evidence-workflow-v0.md` 1586. In both refresh flows a carried row already used
   that span, so the draft fell to 2657. 2657 is an earlier reviewed row of another hunk. The
   current flow printed the same row.
2. **batch-1031b, step `cc37f145efa5`, `internal/tasks/cli/delivery_screen.go` BASE 402,7.**
   stderr shows `REASSESS changed ... nothing carried, the hunk is drafted afresh`. The fresh draft
   cited 191 because a carried row held 166. 191 is an earlier reviewed row of the next hunk.

Both rows are fresh drafts. Both are already counted as manual edits. The rule was changed to use
the compile's carried set for the claims flow, as defined above. That rule is stricter on carried
hunks, because every outside-target row there counts, whether or not it equals an earlier row.
The re-run on these 2 sequences gave `claims-incorrect=0`. Edit counts are unchanged by the rule.

## Acceptance

- **AC1: MET.**
  - `TestClaimsCompileByteIdenticalCEM` binds the compiled plan and the hand-keyed plan to
    byte-identical cem/1.0 maps.
  - Claims carried incrementally through fix steps compile to the same plan and map as claims
    recorded once at the final step.
  - The replayed real corpus checks plan rows against the oracle, not map bytes. Byte-identity on
    real history is NOT_RUN.
- **AC2: MET.** There were 0 incorrect carries over 20 real sequences under the refined rule
  disclosed above, and 0 in the injected fixtures. The first rule flagged 2 rows; both were fresh
  drafts, as shown above.
- **AC3: NOT_MET (failed evaluation).**
  - The edits bar was met: 18 vs 112 manual row edits, 83.9% fewer.
  - The time bar was missed. Before the follow-up, the claims flow's p95 plan-step time was
    higher than the current flow in every run: +33%, +21% and +34%.
  - After batching the record's reads, the gap narrowed to −2.4%, +1.6% and +5.6% (runs B1-B3).
    The bar, no slower than the current flow, was met in 1 run of 3 and missed in 2.
  - The claims refresh alone stays at parity with the current refresh: −16%, −4% and −1% at p95.
    The record is still about 110-150 ms of added work per step under this host's load.
  - Closeout time is NOT_OBSERVED, so the ≥30% p95 closeout bar is unproven. The measured
    plan-step proxy misses it.
- **AC4: MET.**
  - `TestClaimsTombstones` shows a refresh never redrafts a deleted cite, including after a content
    change reassesses the edit. The suppressed hunk keeps the unknown fallback, which passes the
    precheck (`preflightRun`). The tombstone survives a re-record.
  - Tombstone suppression after BASE renumbers the cited text is covered by keying alone, not by
    a dedicated test: NOT_RUN.
  - The replay suppressed 20 drafts and made no incorrect carries.

### Failed evaluation: AC3 time bar

The claims refresh does the same drafting work as `--refresh PLAN`, and drafting dominates its
time. The record step reruns the canonical patch, resolves each plan row and hashes the BASE
blobs.

Attempt (CKC-V0-012):

- Profiling showed that the record cost 25-35% of a refresh, mostly per-file blob reads: two Git
  processes for each hunk path and cited path.
- Batching them cut the record to 9 Git processes, and its in-process time from about 142 ms to
  about 70 ms on this lane's diff.

Result: the p95 gap went from +21-34% to −2.4%, +1.6% and +5.6%. The bar was missed in 2 of 3
runs. The bar was not changed.

Why parity is not reachable by cutting the record alone:

- The claims refresh already costs the same as the current refresh. Any record cost above zero
  is a net loss at p95, unless noise hides it.
- What remains is the canonical patch read (about 28 ms), the batched blob read (about 30 ms) and
  the root, ancestry and revision checks (6 `rev-parse` processes).
- A cheaper record would drop one or two of these processes, by joining the revision lookups or
  using a single `cat-file` with `%(objectmode)` on Git versions that support it. That saves about
  10-20 ms, below the noise of these runs. It was not attempted.

Remaining options, none attempted here:

- Record in the bind loop, which reuses the bind's patch. This moves the cost to closeout; the
  loop is owned by lane icl-m15.
- Make the shared draft cheaper only where claims make work provably unneeded, for example
  skipping the anchor `git grep` and governing-spec reads when every owed hunk carries. When some
  hunk is drafted, dropping carried hunks' patterns is not output-neutral: `git grep -o` overlap
  and the governing-spec majority both depend on the full set.
- Measure the real closeout time, where 94 fewer manual row edits should dominate.

The time bar stays failed as measured. Closeout time is still NOT_OBSERVED.

## Proposed `docs/DOGFOOD.md` text (for lane icl-m15, not applied)

> **Content-keyed claims (experimental, CKC-V0).** After the reviewed plan binds, record it:
> `corvint dogfood record-claims BASE --plan PLAN --claims "$GITDIR/claims.json" --draft DRAFT`.
> After a fix commit or a `origin/main` merge, draft with
> `corvint dogfood propose-citations BASE --refresh "$GITDIR/claims.json"` instead of
> `--refresh PLAN`. Rows whose edit is provably unchanged are carried. Each `REASSESS` hunk is
> drafted afresh and must be reviewed. A cite you deleted is never drafted again. Record the
> fixed plan again before the next step.

## Friction

1. **The corvint MCP server failed to connect** (`plugin:corvint:corvint` CONNECTION_CLOSED) for
   the whole session.
   - Expected: `corvint` MCP tools for context and affected.
   - Actual: they were unavailable, so the lane used the CLI over ssh instead.
2. **Mac shell aliases break plain `ls`** in agent shells.
   - Expected: `ls DIR` lists the directory.
   - Actual: the interactive alias errors, and `/bin/ls` is needed.
3. **The spec Agent digest claim length limit is enforced only at generation**
   (`make spec-requirements`).
   - Expected: the limit is stated in the spec template, or checked earlier.
   - Actual: the lane found it on the first generate and rewrote the claim.
4. **zsh leaves an unquoted `--include=*.go` glob for rsync/grep unmatched** on the Mac and
   aborts the command.
   - Expected: the pattern passes through.
   - Actual: `no matches found`, and the pattern must be quoted.
5. **`heavy.sh` refuses a whole-package `go test`** unless `HEAVY_WHOLE_REASON` is set, even
   when `corvint affected` returns scope UNKNOWN (LANGUAGE_FRONTIER) for the lane's own package.
   - Expected: an owned package with UNKNOWN selection is accepted, or the refusal names that
     case.
   - Actual: a manual reason string was needed.
6. **`capabilities-check` requires every new subcommand to be documented in
   `docs/CAPABILITIES.md`**, and only the test (`subcommand-undocumented "dogfood
   record-claims"`) tells you.
   - Expected: the requirement is named in the spec-driven or capability docs that a new-command
     author reads.
   - Actual: it was found by a failing check.
7. **`spec-requirements-check` fails while the regenerated `INDEX.json` and `REQUIREMENTS.tsv`
   are unstaged**, even though they are correct in the worktree.
   - Expected: the check names "stage the generated files".
   - Actual: it reported a mismatch.
8. **The replay oracle's first incorrect-carry rule counted fresh drafts as carries.**
   - Cause: both refresh flows exclude already-carried spans from drafting, so a fresh draft can
     differ from the plain draft and equal an earlier row.
   - Expected: stderr marks which hunks were carried and which were drafted.
   - Actual: the `hunk ... edits` note is printed for every row, carried or drafted. The harness
     had to recompute the carried set. A `carried` marker per hunk in the PROPOSED notes would
     make this observable to authors too.
   - Fixed in this lane (CKC-V0-013): in a refresh, each note now ends with `; carried` or
     `; drafted`. The replay harness still computes its own carried set as the oracle.
9. **One replay candidate (lane-affected-w3-1031) was refused by the 256-claim bound**
   (250 claims, 265 rows).
   - Expected: a large lane can use claims.
   - Actual: the bound refuses the whole record, so large batch lanes that exceed it cannot use
     claims.
10. **`dogfood-inputs-check` refuses an unquoted `-run ^(A|B.*)$` verify line**
    (`unsupported-verify-syntax`).
    - Expected: the regex is accepted.
    - Actual: only a quoted alternation of exact names is admitted, which the refusal explains.
11. **The shared draft path starts two Git processes per blob it reads**, and one `git grep`
    over BASE dominates every refresh (480-700 ms of a 1000-1300 ms refresh in the profile).
    - Expected: blob reads are batched, as `record-claims` now does (CKC-V0-012).
    - Actual: `--refresh PLAN`, the claims refresh and plain drafts read governing specs and
      line text one file at a time. This is an optimization for both flows, not an AC3 fix.
12. **The replay times the flows back to back in a fixed order, on a host shared with other
    lanes** (1-minute load 26-107 during runs B1-B3).
    - Expected: the plan-step comparison is stable enough to judge a 5% bar.
    - Actual: the current flow's own p95 moved from 1772 to 3120 ms between runs, more than the
      gap being measured. Alternating the order per step, or a quiet host, would make it
      fairer.
