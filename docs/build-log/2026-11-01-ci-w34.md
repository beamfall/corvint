- `GET /repos/beamfall/corvint/actions/workflows/401278239/runs?per_page=100&page=1..3` (CI control

- `GET /repos/beamfall/corvint/actions/runs/<id>/jobs?filter=latest&per_page=100` for the 40 most

- Each control-plane run is joined to the CI run whose `updated_at` precedes its `created_at` by at
  most 20 s. Wall time is `updated_at - run_started_at` (it includes queue wait).
- Job logs need authentication, so no log was read; the reuse decisions are inferred from job and
  step timings and skipped steps.

## V1-1778: control plane runs only when it can change an outcome (AFP-V0-855)

Prior work (4c927e284, AFP-V0-079) gave the status jobs a per-head concurrency group, so AC1 was
already met. It kept a job for every cancelled run, though, so that a run cancelled after
`go-product` passed still gets its status.

Before, over 201 control-plane runs:

| Triggering CI run | Runs | Started a job | Mean wall (s) | Total wall (s) |
|---|---|---|---|---|
| pull_request / success | 59 | 59 | 41 | 2429 |
| pull_request / failure | 18 | 18 | 20 | 360 |
| pull_request / cancelled | 31 | 31 | 26 | 836 |
| merge_group / success | 45 | 45 | 26 | 1178 |
| merge_group / failure | 3 | 3 | 129 | 388 |
| merge_group / cancelled | 1 | 1 | 8 | 8 |
| push (all) | 43 | 0 (all jobs skipped) | 3 | 147 |

Of the 31 cancelled pull-request runs, 30 had a newer head on the same branch. The 31st, branch
`alert-autofix-6`, had no newer head and no rerun. A superseded head can post nothing, because no
open pull request has it at its head.

Change: the `control-plane` job starts for a cancelled run only when
`toJSON(github.event.workflow_run.pull_requests) == '[]'` or
`contains(github.event.workflow_run.pull_requests.*.head.sha, github.event.workflow_run.head_sha)`.
A non-empty list that lacks the run's head (GitHub listed the pull request by branch, at its newer
head) skips the job. The AFP-V0-079 case (cancelled, head still current) still runs.

Review fix (Codex P2, orchestrator round 1): GitHub sends an empty list for a fork pull request
(actions/runner#3444). The first version skipped every cancelled run with an empty list, so a
current fork head lost its required status. That failed closed, but it reopened the AFP-V0-079
liveness gap. An empty list now starts the job, and the step's open pull-request lookup by head
SHA decides whether to post. The tests now evaluate the condition against GitHub-shaped
`workflow_run` payloads instead of a supplied boolean. Without the empty-list clause the fork case
fails.

Expected effect on this window: at most 30 of 31 cancelled pull-request runs start no job (about
13 runner-minutes of wall time and 30 queue slots). The saving applies only to runs whose payload
listed the pull request by branch. The payloads were not retained, so that count is
`NOT_OBSERVED`. If GitHub lists only pull requests at the run's head, superseded runs carry empty
lists and the saving is zero. AC3, the measured after window, is
`NOT_OBSERVED`: `workflow_run` runs from the default branch, so the change takes effect only after
merge. Disposition: delivered in code. The after-window measurement remains a closeout step.

## V1-2113: merge-queue artifact-integrity reuse, before/after (AC3)

AC1 and AC2 were implemented by 491857d59 and 3c5ef790a (AFP-V0-163, merged 2026-10-21). This
lane retains AC3 and checks whether the skip fires.

Before (ticket body, old repository, run ids no longer reachable): merge_group run 39458994189
took 11.4 min, with artifact-integrity running in full for 11.3 min. PR run 39472511845 took
12.6 min.

After (40 recent merge_group runs). One run is excluded because its artifact-integrity record
reports a completion time before its start (41290713999):

| Queue runs | n | artifact-integrity median (min) | run wall median (min) | run wall range (min) |
|---|---|---|---|---|
| reuse fired (HIT) | 13 | 0.2 | 6.7 | 4.4 to 7.5 |
| gate ran in full (MISS) | 26 | 15.6 | 29.6 | 26.8 to 38.0 |

Does the skip fire when it should? For each queue entry, the queue base (from
`gh-readonly-queue/main/pr-N-<base>`) was compared with the `main` tip when its pull-request run
started (the latest `push` CI run before it).

- In every HIT, those two were equal.
- In 22 MISSes, `main` had moved, so the trees differ. Running in full is the correct
  AFP-V0-163 fail-closed behavior (AC2).
- 4 MISSes were queue commits that never reached `main` (entries dropped from the queue).
- 1 MISS had an equal base: 41243422967, whose queue run started 29 s after the pull-request run
  41243402148. The record job could not yet exist (a race, see Friction).

So the skip does fire in practice, and no fix is needed.

In MISS runs, the critical path is not artifact-integrity. The longest job was a go-product shard
in all 26: shard (7) in 14 runs, (4) in 7, (5) in 3, and (1) and (3) once each. Those shards miss
REUSE for the same moved-base reason. Disposition: AC3 retained. Ticket ready to close on review.

## V1-0470: bounded README presentation path (DCI-V0-855 to DCI-V0-857)

Why DOCS had not fired since 2026-09-29:

1. The approved qualification bound a SHA-256 of the whole tracked tree, so every merge to `main`
   invalidated it (`qualification-source-drift`, recurrence 2026-10-02).
2. The root README later gained the capability table, delimited by
   `<!-- capability-gate:readme -->` comments. The admitted HTML subset refused any comment
   (`unsupported-html`), so even a fresh qualification chose FULL. The table's reader,
   `tools/capabilities-check`, was missing from the consumer inventory.

Changes:

- DCI-V0-855: qualification profile `/1` binds `classifierSha256` (rows under
  `tools/docs-ci-plan/`) and `policySha256` (the row of `documentation-ci-v0.md`), not the whole
  tree. The check list gains `merge-queue-full-race`.
- DCI-V0-856: a DOCS pull-request run produces no `ci-tested-tree-record` or
  `ci-narrowed-tree-record`, so its queue entry runs its own root race invocation. This backstop
  stands in for the whole-tree binding: a README reader added after review fails in the queue and
  never reaches `main`. The ci.yml conditions already held; a workflow test now pins them.
- DCI-V0-857: the two capability-gate markers are the only admitted HTML comments. A DOCS run also
  runs `go test -race ./tools/capabilities-check`, and the check list gains
  `capabilities-check-tests`.
- `.github/qualifications/docs-only.json` is replaced by the `--qualification-proposal` output for
  6908ef4a6^ with `approved:false`. DCI-V0-005 leaves the approval to an independent review of this
  exact source.

Replay evidence, in a disposable clone at 6908ef4a6^ with a locally approved copy of the proposal
(not committed): a one-word prose change to the root README produced `mode DOCS`,
`reason qualified-presentation-change`, `verified:true`, `changed [README.md]` (exit 0). Before the
DCI-V0-857 commit, the same replay produced `FULL unsupported-html`.

Fork recorded: the lane does not set `approved:true`. Setting it, which DCI-V0-005 requires an
independent review to do, is the orchestrator's step after its Codex review of this source. After
that, the remaining closeout steps are hosted DOCS observation (DCI-V0-008) and native completion.
Until the artifact is approved, README PRs keep running FULL, which is safe. Disposition: delivered
in code, with the approval and the hosted observation outstanding.

## Friction (full list)

1. `gh` is not on this host's PATH. The Windows `gh.exe` fails under WSL interop ("Invalid
   argument"), sandboxed or not. The lane brief said `gh` was authenticated here. I fell back to the
   unauthenticated REST API: 60 requests per hour and no job logs. 48 calls covered 40 queue runs,
   but the reuse decision logs could not be read.
2. `make dogfood-change` refuses (`FAIL not-complete`) once the worktree has an uncommitted edit.
   Running it after the first spec edit lost the pure pre-change receipt. The lane ordering was my
   error; the refusal named its fix.
3. `make spec-requirements` refused my additions to the frozen `Intent status` and digest `Status`
   headers (SRG-V0-980), so the acceptance notes moved onto each requirement line. The refusal was
   clear. The AFP header is still a roughly 10 KB line that newcomers will try to extend.
4. `corvint affected` selected `tools/corvint-pr-tests` as a `PATH_LITERAL_READER` of
   `tools/docs-ci-plan/main.go`, but no file there names that path (a false positive). heavy.sh
   then refused the whole package without `HEAVY_WHOLE_REASON` (101 s run).
5. Any edit to `.github/qualifications/docs-only.json` selects about 90 packages through
   `UNBOUNDED_READER`, which makes the affected plan for a qualification-only change useless.
6. The installed `corvint` reports `DEGRADED self-binary-stale` (built from 35475f86) as soon as
   a lane edits Go source.
7. After `dogfood-change`, the untracked `.corvint/change.cem.json` sidecar makes every later
   `affected` call warn `MIXED worktree`.
8. `actionlint` is not installed on this host, so workflow lint can only run in hosted CI.
9. The DOCS route had been dead for a month with nothing to flag it. A stale qualification
   silently selects FULL, and a new README consumer (the capability table) was added with no
   inventory update.
10. Race in AFP-V0-163: a queue run can start before its pull-request run's
    `artifact-integrity-record` exists (41243422967, 29 s gap), and then reruns the gate in full.
11. Queue run 41290713999's artifact-integrity record has `completed_at` before `started_at`
    (-44 min). This is either a timing anomaly in the jobs API or a rerun artifact.

## Hot spots

- Merge-queue wall time is dominated by entries built on a moved `main`. 26 of 39 queue runs
  (67%) ran full at a median of 29.6 min, against 6.7 min for a reuse hit. Their critical path is
  go-product shard (7), then shard (4), not artifact-integrity. Every queue entry after the first
  in a burst misses all tree-equality reuse.
- Superseded pull-request pushes: 30 cancelled CI runs in 2.7 days on the same branches. The
  batching and lane flow push several heads per PR.
