## V1-0887: measurement

Base: `59d492017e421a43eaa21d717236cc54d80de160`. The branch was then re-based on `origin/main`
`55b0c0f0901ca516705b1d6d6b43651c071e6ccd` before any commit. That range changes nothing under
`internal/tasks`.

Method:

- Stores: three synthetic stores with 880 tickets and 3,000, 6,000 and 13,000 receipts, built by
  the opt-in `TestRC3_SyntheticStore` generator, each at its final path in a scratch directory and
  never in a live `.git/taskman`. Each store got a policy with four attempts and one claim.
- Binary: `corvint-tasks` built from the base.
- Calls: one process per call, with `--timing`. Six interleaved rounds; round 0 was a warm-up.
- Load: recorded before and after every call.

Medians of 5 (host load 35 to 39 on 12 CPUs; every outcome OK):

| receipts | verb | wall ms | CPU ms | snapshot read ms | validation ms | journal write ms |
|---:|---|---:|---:|---:|---:|---:|
| 3,000 | heartbeat | 488 | 460 | 79 | 212 | 116 |
| 6,000 | heartbeat | 561 | 470 | | | |
| 13,000 | heartbeat | 552 | 490 | 121 | 205 | 116 |
| 3,000 | renew | 630 | 470 | | | |
| 6,000 | renew | 569 | 470 | | | |
| 13,000 | renew | 619 | 500 | | | |

Both verbs are sub-second but not milliseconds. CPU grows about 6% from 3,000 to 13,000 receipts.

Profile (in-process, 20 heartbeats at 13,000 receipts, load about 60): about 525 ms of CPU per
heartbeat.

- Transaction model: about 165 ms. Canonical wire encoding is about 62 ms and ticket decoding about
  57 ms. Both are proportional to tickets.
- Writer-audit observe: about 97 ms.
- Authority session: about 70 ms.
- Observation bind: about 37 ms.

A differential profile (13,000 against 3,000 receipts) adds about 48 ms per heartbeat. About 31 ms
of that is the two `receipts/` listings in the writer audit's captures.

Microbenchmark of one listing (load about 75):

| receipts | list names | whole name scan | hash |
|---:|---:|---:|---:|
| 3,000 | 10.9 ms | 16.5 ms | 1.7 ms |
| 13,000 | 28.6 ms | 36.4 ms | 3.8 ms |

That is about 1.8 µs per name under load, mostly the directory read. Sorting is negligible. Name
validation plus the inventory hash is about a third of the per-name cost.

The attempt record keeps a constant size (about 1.8 KB). Nothing accumulates per heartbeat.

## V1-0887: decision

Under CAL-V0-116 and CAL-V0-224, the two exact listings are the only history-proportional step.

Removing them needs one of four routes:

1. A next-name probe.
2. Stat-stamp listing reuse.
3. A sharded or segmented `receipts/` layout.
4. Liveness records outside the journal.

The first two are CAL-V0-224 non-goals. The third changes the journal format. The fourth is
excluded unless the owner decides it. Each changes an accepted contract, so this lane implements
none of them. It reports the choice as an owner decision.

Cutting the per-name constant (validation and hash, about a third of the per-name cost) would
lower the slope but not flatten it. At 13,000 receipts it would save at most about 10 ms of a
roughly 550 ms call. It is not done here: that saving does not justify touching the audit's
error ordering.

A heartbeat with no listings would still carry about 450 ms of ticket-proportional work (model,
session and commit). So reaching "milliseconds" also depends on V1-0915-style model cost work.

Delivered: CAL-V0-232 and `TestCALV0232_LivenessWritesNeverReadHistory`. At 70 and 280 receipts,
heartbeat and renew run through `store.Lease`, each with an empty lease cache as a CLI process has.
Both must commit on the writer-checkpoint route, keeping the attempt and generation, while every
receipt before the writer checkpoint has mode 0. The test passes with no code change: base and
change behave the same, since no production code changed.

Mutation: the lease writer route was made to read `receipts/000000000001.json` before taking the
lock. The test failed at both sizes ("HEARTBEAT 0 with 69 sealed history receipts ... permission
denied"; 279 at the larger size). With the original restored, it passes (70: 22.0 s; 280: 30.8 s;
load about 45 to 50).

The test skips on Windows, where mode 0 does not deny reads. It also skips when a sealed receipt
still reads, as for a privileged process.

AC1 is not met; it is retained as the residual in the spec. AC2 (lease, fencing and refusal
semantics unchanged): no production code changed, and the existing CAL-V0-009, 048, 189, 190, 230
and 231 suites cover them. AC3 does not apply: no liveness record moved.

## V1-1403: status lines

The leases spec header `Delivery status:` now equals the digest's delivery clause. That clause adds
the CAL-V0-225..231 segment and CAL-V0-232. The digest `- Status:` line is the intent status, `; `,
the delivery status, then one historical sentence. The INDEX and README projections follow the
header through `make spec-requirements`.

Survey of `docs/specs/INDEX.json`:

- 195 of 202 specs have a digest status line.
- In 110, the digest status is the intent and delivery header values with at most a short addition.
- In 85, the digest elaborates beyond the header. Usually the header is one word such as
  `experimental` and the digest is a sentence or more.

The specindex rule (`internal/specindex/index_test.go`, `checkDigest`) requires only that the
normalized digest contains both header values. Decision: keep that containment rule. It is the
intended contract. The header is a short, machine-projected status (INDEX.json and README columns),
and the digest is a human summary allowed to elaborate. An equality or no-elaboration check would
refuse 85 specs, so this lane adds no repo-wide gate.

The narrower defect seen here is different. This header was a long clause that had become a stale
prefix of the digest's delivery clause. Detecting that mechanically needs a delimiter convention
the specs do not share, so it is left as a residual and not turned into a check.
