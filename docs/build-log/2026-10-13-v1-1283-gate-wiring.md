## Intent

A ticket can require, as a native Tasks gate, that its change's committed cem/1.0 map verifies and
that every hunk under the ticket's claim-era touch paths is at least anchored. The gate records PASS
or FAIL with the pinned `verdictSha256` and the per-path minimum tier. It refuses a producer-written
tier, and it fails when the native verifier and the independent `interop/cem01-go` consumer disagree.

## Decision: the runner substitutes closed attempt placeholders (A)

Chosen. A COMMAND gate's argv may contain three whole-entry placeholders, which the native runner
replaces from the claim and the attempt before it executes the gate (`TCB-V0-015`,
`internal/tasks/store/lease_gate.go`):

- `{attempt.baseCommit}` becomes the attempt's base commit.
- `{attempt.candidateCommit}` becomes the attempt worktree's HEAD.
- `{claim.touchPaths}` becomes the claim-era `effects.touchPaths`, as canonical JSON.

Only an argv entry that equals a placeholder is replaced; substrings stay literal. The substituted
argv joins the gate's inputs digest, so a reused or re-verified result binds the attempt facts. A
ticket edited after its claim refuses `STALE_TICKET`, and a multi-repository candidate refuses
`UNSUPPORTED`. Preflight and batch runs have no attempt and keep the placeholders literal, which the
command refuses as an unreadable argv.

Rejected: (B) the gate command reads the attempt facts itself through a pinned Tasks read. A static
argv carries no attempt identity, so the command would have to find "its" attempt by guessing. A
pinned `corvint-tasks` executable digest churns with every Tasks build. The gate's evidence would
come from the store whose completion it is meant to constrain, a circular trust path. And it is a
larger change across both binaries.

## Decision: one closed Core command

`corvint cem gate-verdict --base OID --candidate OID --predicate touched-anchored|all-anchored
--touch-paths JSON --portable-consumer PATH` (`TCB-V0-016`, `cmd/corvint/cem_gate_verdict.go`)
runs the library at `--root` and prints its canonical document. It exits 0 on a grant, 1 on a
refusal and 2 on an unreadable argv (stderr code `cem-gate-verdict-invalid-arguments`). Every flag
is required exactly once, and both OIDs are full commit IDs. `cmd/corvint` imports no Tasks package
and the Tasks store imports no Core package; the store sees only argv, exit code and output.

The dispatch and the help text live in the new file. `main.go` changes one line to call a wrapper
that runs the stable verifier invocation and then this command, and `help.go` appends
`cemGateVerdictHelp` to `cemHelp` on its closing line. Neither file moves a line, so the line
citations other specs hold into both files stay valid; inserting the lines in place had broken them.

## Decision: the portable consumer must recompute the same verdict

After the native `verify.Stable` run, the library runs the given absolute portable consumer as
`verify-stable-canonical --repository R --map M --expected-base B --target T --artifacts A`
(`TCB-V0-017`) in the environment `PATH=/usr/bin:/bin`, `LC_ALL=C`, `LANG=C`. Unlike the native git
reads, it stays in the gate's process group, so the Tasks runner's group kill on timeout or
cancellation stops it and its descendants too. Its leader is killed at a 30-minute budget and the
pipe drain is bounded at one minute. The document pins the portable route, outcome, `verdictSha256`
and citation digest. The cross-check runs before the ACCEPT check, so two consumers that both reject
still have to agree.

- A different `verdictSha256` claim, a different recomputed digest, a different outcome or a
  different citation block is a FAIL `CEM_VERDICT_VERIFIER_DISAGREEMENT` (`verifier-disagreement`).
  The document pins both verdicts and evaluates no predicate.
- A consumer that cannot run, whose output is not one `cem-stable-verification/1` result with a
  verdict digest, that ends on a signal, or whose exit status its outcome does not explain (0
  exactly on ACCEPT, 1 or 2 otherwise) is `CEM_VERDICT_UNVERIFIABLE` (`portable-consumer-failed`). An
  agreeing ACCEPT document followed by a failing exit is therefore never a grant.
- A portable result never raises or replaces a native tier, and the gate never takes the
  consumer's path from the map or the store.

`interop/cem01-go` needed no change: its `verify-stable-canonical` route already recomputes the
verdict and citation block.

## Decision: per-path minimum tiers

The document's `paths` array (`TCB-V0-018`) lists each governed path once with the lowest recomputed
tier among its hunks and whether that tier satisfies the predicate. The tiers come only from the
consumer's citation block. A map whose producer wrote a `tier` member is not ACCEPTed by the stable
verifier, so it refuses `stable-not-accepted` before any predicate row exists.

## Decision: the policy entry is opt-in

The canonical entry (`TCB-V0-019`) is recorded in the spec's "Tasks gate wiring" paragraph with
`/usr/local` executable paths. It declares `required: false`, so it runs only for a ticket that
names `cem-verdict` in `requiredGates`. A default-required entry would refuse every ticket whose
change has no sealed cem/1.0 map, including every documentation-only ticket. `env: ["PATH"]` needs
`PATH` in the policy's `environment.allowedEnvKeys`. A host-specific copy of the entry, with this
machine's executable paths, was delivered to the orchestrator outside the repository; registering it
in the live store is an operator step this lane does not take.

## Decision: test confinement

`internal/taskman` tests must not read the interop module. The portable tests use the test binary
itself as a stand-in consumer: `TestMain` answers `verify-stable-canonical` with an in-process
`verify.Stable` result. Disagreements are produced by wrapping that consumer in a one-line `sed`
patch. The `cmd/corvint` `TCB-V0-016` test builds and runs the real `interop/cem01-go`.

## Failure modes

New closed codes and reasons, in addition to lane 1's:

- `CEM_VERDICT_VERIFIER_DISAGREEMENT` (`verifier-disagreement`).
- `CEM_VERDICT_UNVERIFIABLE` (`portable-consumer-failed`), including a signal or an exit status
  that disagrees with the consumer's own outcome.
- `CEM_VERDICT_INPUT_INVALID` (`invalid-input`) now also covers a portable consumer path that is
  not absolute and clean.
- The command's argv refusal `cem-gate-verdict-invalid-arguments`, exit 2.
- The runner's `STALE_TICKET` and `UNSUPPORTED` refusals for a substituted gate.

## Findings

- A migrated map cannot pass the gate. The gate reads the sealed map at the seal commit, which
  still holds the cem/0.2 bytes; the cem/1.0 bytes exist only in the V1-1277 bulk rewrite. A gate
  run for completion needs a natively sealed cem/1.0 map. Admitting migrated maps would need a
  provenance-aware mode with its own contract.
- Real dogfood maps are mostly `cited`, so `touched-anchored` refuses for an ordinary claim scope:
  36 of 38 hunks in the V1-1340 map, and 8 of 11 in lane 1's own seal. The predicate is working as
  specified; citation plans rarely reach `anchored`.
- A touch key without a trailing `/` is an exact path. V1-1283's own claim keys
  (`docs/specs`, `internal/taskman` and two others) govern no hunk, so this gate would refuse
  `no-governed-hunk` for it.

## Retained limits and NOT_PRODUCED

- Preflight and batch runs keep placeholders literal and refuse, so `cem-verdict` can only run in
  an attempt's gate run.
- A ticket edited after its claim needs a re-claim before the gate can run.
- The multi-repository `UNSUPPORTED` refusal is not exercised by a test.
- `CAL-V0-016` (`docs/specs/corvint-tasks-agent-leases-v0.md`) still says a gate runs with its
  declared argv. It is not amended; `TCB-V0-015` is the only statement of the substitution.
- The `internal/taskman` portable tests use the stand-in consumer; only the `cmd/corvint` test runs
  the real one, and only on darwin: `interop/cem01-go` qualifies process containment there alone
  (`stable_process_other.go` answers `unsupported-process-containment`), so on the linux CI shard
  the real consumer reported `UNSUPPORTED`, the gate refused `verifier-disagreement` as specified,
  and the test now skips `NOT_RUN` off darwin (PR #863 CI run 38463640466).
- Lane 1's git reads (`runRead`, also used by `capture.go`) still run in their own process groups
  under a 30-second bound, so a Tasks group kill does not reach a read in flight; they are left as
  lane 1 specified them. On `corvint`'s own cancellation only the consumer leader is killed; its
  descendants are swept by the Tasks runner's group reap, not by `corvint`.
- The gate must run with the seal commit as the candidate. A later commit refuses
  `sealed-tree-mismatch`, as lane 1 recorded.
- The portable consumer is the slower of the two runs: about 28 seconds native and 92 seconds
  portable in an earlier measurement on this repository. The V1-1340 rehearsal took
  7 seconds in all.
- Live registration is NOT_PRODUCED: the installed `corvint` predates this branch, `cem01-go` is not
  installed, and the live policy has no `cem-verdict` entry. One real ticket completion through the
  gate (criterion 4) is the orchestrator's step after merge.

## Independent review

One read-only Codex round over `523fa4ce6..39c8bdc09` returned CONCERNS with three findings:

1. High, fixed: an interrupted gate could leave the portable verifier running, because the consumer
   ran in its own process group and the Tasks runner's group kill missed it. It now stays in the
   gate's group, and `TestTCBV0017PortableConsumerSharesTheGateProcessGroup` asserts its group.
2. Medium, fixed: a failed portable process could contribute to a GRANT, because an agreeing ACCEPT
   document followed by exit 2 or a signal was read as a result. The exit status must now agree
   with the outcome; three new cases refuse `portable-consumer-failed`.
3. Medium, retained: the native integration is unproved. `TCB-V0-019` runs stand-in commands, not
   the installed binaries under the live policy, so live registration and one real completion stay
   NOT_PRODUCED and are the orchestrator's criterion 4 step.

Reverting either fix makes its test fail (checked by reapplying the old behaviour locally). Per the
one-round cap, the fixes were not re-reviewed.
