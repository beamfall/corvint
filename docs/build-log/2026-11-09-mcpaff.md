# Lane mcpaff: the affected MCP tool (V1-5254)

Lane `claude/mcp-affected`, based on the unmerged big-cut branch (decision 0594) at
`fea1de8587085a4538484b97d216c32511ff3928`. One ticket, serving the testing product: an agent host
can ask the MCP server which tests a change requires and get the CLI's own answer.

## V1-5254: MCP: add `corvint.affected`

**What was wrong.** No MCP tool named `affected` or `test` existed under `internal/mcp` or
`internal/capcatalog`; the server answered impact, status, help and the opt-in groups, but not the
question `corvint affected` answers. The planner lives in `cmd/corvint` (`package main`), which no
`internal/mcp` package can import, so the server had no path to it.

**The fix.** A new opt-in tool group `affected` (`--tool-profile affected`) adds
`corvint.affected`, served per declared root under `corvint-affected-mcp-tool-error/0`
(`MMR-V0-1118`, extending `MMR-V0-012`):

- `internal/mcp/toolgroup/affected.go`: the group. Its closed input is one optional `base`
  string (1 to 4096 characters, never option-like); everything else is `-32602` before the planner
  runs. A call runs an `AffectedRunner` for the root and answers the planner's stdout bytes as the
  framed text block and the identical parsed `structuredContent`; a planner refusal becomes the
  group's tool error carrying the planner's `code` and `error`; a hook-less group is `not-served`,
  a moved root `invalid-root`. The group never re-derives or narrows the selection.
- `internal/mcp/cli`: `Hooks{Affected}` and `ServeWithHooks`. The `affected` token joins
  `toolGroups`; `openGroups` and `startUnavailable` build the group; `runVersioned` refuses the
  group by name (`corvint-mcp: invalid arguments: the affected group is served only by corvint
  mcp: ...`) when no hook is supplied, so the standalone `corvint-mcp` binary never advertises a
  tool it cannot answer.
- `cmd/corvint/mcp.go`: `corvint mcp` supplies `mcpAffectedRunner`, which runs this binary's own
  `--root ROOT affected --summary [--base BASE]` through `runContext`. The tool's bytes are
  therefore the CLI's bytes: same parser, planner, self-binary freshness check and canonical
  writer. The verb's help names the group.
- Catalog and docs: `capcatalog.MCPTools` entry, regenerated `catalog.json` and trees
  (`make capability-catalog`), `docs/CAPABILITIES.md` (group lists and the MCP tools row),
  `docs/MCP-SERVER.md` (group table), `docs/GLOSSARY.md` repin.

**Design call.** Executing a sibling `corvint` binary from `corvint-mcp` was rejected: it would be
a forwarding path (product invariant 7) with a brittle binary lookup. Moving the planner out of
`cmd/corvint` was out of scope for the lane. The hook keeps one implementation and one wire; the
cost is that only `corvint mcp` serves the group, which the refusal, the help, the catalog
availability column and the spec all state.

**Not delivered.** The acceptance criterion "the answer includes the flow and variation selections
once the one-plan ticket lands" depends on V1-5251, which is not on this branch. The verdict
carries what `affected --summary` carries today; `MMR-V0-1118` records that the selections join
the answer when V1-5251 lands.

## Review repair (lane mcpafffix, 2026-11-09)

An independent review of `corvint.affected` reported six items. Each was checked against the code
before anything changed; the spec delta to `MMR-V0-1118` (concurrency, failure, stale-binary,
framing and size bounds, each with a falsifier) was committed first, then the code. The checks
below ran with `GOTOOLCHAIN=local` (go1.27.3) and `TMPDIR=/home/russell/.cache/corvint-tmp`.

| # | Finding | Disposition | Evidence |
|---|---|---|---|
| 1 | Up to 64 concurrent planner runs per root, no serialization | FIXED | `internal/mcp/server/server.go` admits 64 requests (`connection.limit`) and runs each `handleRequest` in its own goroutine; a group call outside `--follow-ref` went straight to the planner. `toolgroup.NewAffected` now holds a one-slot gate per root; a waiting call answers `-32603` when its context ends without starting the planner. The planner is safe to run concurrently (no process-wide mutable state; cache entries are `O_EXCL` plus rename in `internal/liveverify/affected/graphcache.go`), so the gate bounds CPU and memory, not correctness. Under `--follow-ref`, `followRef.bound` already serialized every call to the root. Test `TestMMRV01118AffectedSerializesPlannerPerRoot`: fails before (peak 2 runs for one root), passes after. |
| 2 | Whole stderr parsed as one JSON object; message unbounded | FIXED | `runAffected` prints `corvint: DEGRADED ...` to stderr (`degradeStaleAffected`, `cmd/corvint/affected.go`) before `compactAffectedReceipt` or `writeAffectedVerdict` can still refuse, so a stale binary's refusal collapsed to `affected-failed` with raw text, and the parsed `error` was never cut. `affectedFailure` now reads the last non-empty line and bounds both messages to 4096 bytes on a rune boundary. Test `TestMMRV01118AffectedFailureReadsLastLineBounded`: fails before, passes after. |
| 3 | `self-binary-stale` refusal reaches the tool error with a useless fix text | NOT_REAL as stated; hint FIXED | In `affected --summary` the stale check is a degradation inside the successful verdict (`degradations`, `degradationDetails`, exit 0; `degradeStaleAffected`), never a refusal; only `corvint test` (`cmd/corvint/test.go:378`) refuses on it. The answer bytes must stay the CLI's, so the recovery (rebuild and restart `corvint mcp`, because the server keeps the binary it started with) went into the tool description and `corvint mcp --help`. Test `TestV15254MCPAffectedStaleBinaryDegrades` injects a stale build stamp through the served `corvint mcp` child and requires the CLI's degraded bytes, no tool error, and the recovery in both texts: fails before (description lacked it), passes after. |
| 4 | Only the text block is framed | BY_CONTRACT | `AHI-004` binds "the `corvint-mcp` tool-result text block (`MCPV0-008`)"; `MCPV0-008` states that `structuredContent` "carries the identical parsed object unwrapped, for programmatic callers that do not read it as model input". The tool-error object is the closed unframed object every group answers; its message is the planner's own and now bounded (item 2). The spec bullet and the code comment in `affected.go` cite the clause. |
| 5 | Oversized verdict falls to the server's `output-bound-exceeded` | FIXED | The result carries the verdict twice (framed text plus structured), so about 450 KiB of verdict hit the 1 MiB bound in `writeResultContext`. The group now encodes its result as the server does and answers `verdict-oversized` in its own profile, naming the size and `corvint affected --summary`, when the result exceeds `MaxMessageBytes` less 4096 bytes of frame headroom. Test `TestMMRV01118AffectedOversizedVerdictIsNamed` (600 KiB verdict refused by name, 400 KiB answered whole): fails before, passes after. |
| 6 | `--follow-ref` with the group; planner processes | CHECKED, recorded | `toolHandler.dispatch` routes every non-help call of a followed root through `followRef.bound`, which syncs the detached worktree to the ref under the lock before the group answers, so the planner plans the followed commit. Test `TestMMRV01118AffectedGroupUnderFollowRef` (moved ref: the planner sees the new HEAD, the result carries one REFRESHED follow-ref block beside the framed bytes). Processes: the planner starts only `git` (`exec.LookPath("git")`, `gitstatus.Executable()`); the `go` toolchain is run only by `typedreach.ProbeConfig` from `corvint test`, and no planner package imports `net/http` or dials. Recorded in the spec bullet. |
