# V1-0785 and V1-1596: pool waitlist, hand-off grace and dispatch launch room

Date: 2026-10-18
Tickets: V1-0785 (GitHub issues beamfall/corvint#583 and #1067), V1-1596 (GitHub issue
beamfall/corvint#1039). V1-1585 (GitHub issue #1028, typed member lifecycle) is NOT STARTED.
Requirements: PSR-V0-130..136 and PSR-V0-140..143 (`docs/specs/corvint-tasks-pool-safe-reuse-v0.md`,
sections "V1-0785 bounded pool waitlist and hand-off grace" and "V1-1596 dispatch launch room for
pool-requiring tickets"). They are accepted under the owner's standing auto-accept of lane
requirements (2026-10-11). Nothing was added to the agent leases spec (CAL-V0), which is at its
obligation bound; the dispatcher's `pool-wait` event kind is defined by PSR-V0-143.

## Owner decisions applied (D3)

- A separate `pool wait` command, not a flag on `claim` or `pool acquire`.
- Waiters block only lower-priority claims, or same-priority claims that arrive later.
- A wait lasts at most 600 s (`maxWaitSeconds` 1..600 per pool; no pool keeps a waitlist unless it
  declares one).
- Hand-off grace is opt-in, `handoffGraceSeconds` default 0.

## Deviations from the ticket's proposed wording

1. **Two registration forms.** The ticket proposed `--ticket/--holder`; issue 1067 needs a live
   attempt to hold its place by attempt and generation. Both forms are supported (PSR-V0-130), and
   the attempt form dies with the attempt's generation.
2. **Grace reserves capacity, not a member.** A `GRACE` entry reserves one unit of free capacity for
   the ticket's next generation (PSR-V0-136); it does not pin the specific member. Pinning would
   need a new allocation state, and any free member serves the successor equally.
3. **Pruning on every pools.json write.** Dead entries never block (PSR-V0-133). They are dropped by
   any lease write that settles the waitlist (including `reap`), by `pool wait` and by `pool sweep`,
   not by `reap` and `pool sweep` alone.
4. **Refresh semantics.** A refresh keeps the place (sequence, `since`) and the priority snapshot;
   refreshing a `GRACE` entry keeps `GRACE` and the later expiry, so a successor that registers
   inside its grace window does not lose its rank.
5. **Dispatch room ignores the waitlist.** PSR-V0-140 does not subtract waitlist entries from room:
   a waiting attempt's session is already counted as a pending worker, so subtracting would count
   it twice.
6. **Status through events.** Each waiting ticket's reason and the computed room are reported by
   `pool-wait` events in the dispatcher's event list (PSR-V0-143), not by a new ledger field; the
   ledger profile `taskman-dispatch-state/6` is unchanged.

## Review round (PR #1087)

Five review findings were confirmed. Each new test below failed on head `2d0c548e8` before the fix
and passes after it. The PSR text was amended with the same IDs under the owner's standing
auto-accept (2026-10-11).

1. **P1: waitlist against priority admission (PSR-V0-132).** On a pool with `priorityAdmission`,
   a waiter that the waitlist admitted was refused by priority admission in favour of the
   equal-priority ticket that the waitlist had refused. The two rules deadlocked the member.
   Priority admission now drops any competitor that the waitlist makes yield to the claimant
   (`waitlistYielders`), in both the claim path and the plan. The test is
   `TestPSRV0132_WaitlistOutranksPriorityAdmission`, run with priority admission on and off and
   with a GRACE successor against a P0 claimant.
2. **P2: claim-next picked a blocked ticket (PSR-V0-132).** The plan ignored the waitlist, so
   `claim --next --pool` chose the plan's first ticket and was then refused on it. A `--pool` plan
   now defers that ticket, naming the head waiter, at the transaction's recorded time.
   - The plan preview applies this at its observation time.
   - `NextClaimTicket` and `CLAIM_NEXT` now share one plan input (`claimNextInput`), so the
     store derives scope for the ticket the claim takes.
   - Tests: `TestPSRV0132_ClaimNextSelectsTheWaiter` and `TestPSRV0132_ClaimNextPoolClaimsTheWaiterCLI`.
3. **P2: some pools.json writes kept dead waiters (PSR-V0-133).** `pool release`, `pool
   confirm-safe`, pool membership writes and slot writes re-encoded the state with expired entries.
   `planLease` now prunes any posted `pools.json` centrally, judging liveness against the attempts
   the same write posts. A waitlist that is all live or empty stays byte-identical. The test is
   `TestPSRV0133_EveryPoolsWriteDropsDeadWaiters`.
4. **P2: a full waitlist dropped the GRACE entry (PSR-V0-136).** At 512 entries, a HANDOFF release
   now refuses `LIMIT_EXCEEDED` naming the GRACE entry, with nothing written. A release with any
   other reason is unaffected. The test is `TestPSRV0136_FullWaitlistRefusesHandoffGrace`.
5. **P3: the rendered entry omitted `since` (PSR-V0-135).** `PoolWaiterValue` now carries `since`,
   which the spec already required. The test is `TestPSRV0135_WaiterValueCarriesEveryField`.

The store-path half of finding 2 cannot be observed through the CLI without a scope deriver: the
fixture claims derive no scope, so the CLI test passes even when `NextClaimTicket` lacks `Now`.
The shared `claimNextInput` makes the two selections agree by construction.

`TestPSRV0111_CeilingRelaunchesOnSameRequestID` (`internal/tasks/cli`) failed twice under host load
during this round. It then passed 3 of 3 runs, and once at the unchanged head, so it is treated as
the known timing flake, which is tracked separately.
