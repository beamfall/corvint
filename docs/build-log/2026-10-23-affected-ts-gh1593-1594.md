# TypeScript scanner and Playwright env identity for GitHub #1593, #1594

Date: 2026-10-23. Lane: opencode/affected-ts-gh1593-1594 (base 698ce6c75). Tickets: V1-2467,
V1-2468. Requirements `TJAA-V0-038..044` in
`docs/specs/typescript-javascript-affected-adapter-v0.md` are accepted under the owner's standing
auto-accept (2026-10-11). They amend `TJAA-V0-034` (the `!` predecessor and the reason an
ambiguous slash raises) and `TJAA-V0-035` (global names and `process.env` writes).

## Decisions

- #1593 cause: `ambiguousSlash` scanned every `/` of the raw text. The closing slash of
  `/[^x]+/` follows `+`, an ambiguous predecessor. Reading that closing slash as an opening slash
  gave `/, '').replace('/`, which holds a quote, so the module was marked computed loading. A
  probe of the origin/main package reproduced the issue table exactly: rows 1 to 3 raise
  `typescript:dynamic-import` and row 4 does not.
- `TJAA-V0-038`: the check now walks the import-scan lexer over the comment-stripped text.
  Strings, template text, comments and admitted regular-expression literals are skipped. The
  first ambiguous slash is the first point where the two readings can diverge. The literal
  reading of that slash is still taken over the raw text. `!` takes the verdict of its own
  position, either prefix negation or non-null assertion. A `!` that starts a line is always the
  prefix negation. `}` and `)` stay ambiguous: block versus object literal needs
  grammar state, and treating `}` as an opener could hide `import(` after `{} / 2`.
- `TJAA-V0-039`: that ambiguity is now its own reason, `typescript:scan-unresolved`.
  `typescript:dynamic-import` only means that a computed `require`/`import(` call was read.
  Advisory narrowing treats the new reason like any non-dynamic frontier (`NOT_NARROWED`).
- `TJAA-V0-040`: the observer records a site for every reason: `path:line`, or `path` when only
  the file is known. Unterminated literals carry their offset through a `sourceSyntaxError` that
  still unwraps to `strconv.ErrSyntax`. The Playwright plan detail names at most 8 sites. The
  general `affected-plan/0` frontier keeps bare reason codes. Its consumers (`internal/appflows`
  and the narrowing switch) match exact codes, and the Ruby-style located entries
  (`RUBY-AFFECTED-V0-046`) are a separate wire change.
- #1594 (`TJAA-V0-041..044`):
  - Global object names refuse the env and numeric roots only in code, or as a whole computed
    string key (`x['globalThis']`). Because string text could still become code, a code
    `Function` token and any `constructor` token now refuse those roots too.
  - A top-level `process.env.NAME =`/`??=`/`||=`/`&&=` statement no longer refuses the process
    root, because Node stores a string. A computed `executablePath` that reads a written name
    still fails the identity, because `launchOptions` is an identity key.
  - The identity detail names the first blocking `use` property's token and line. It also names
    the scope token that refused a needed root. The pure parser reports the start of its last
    primary expression as the refusing token.
  - The issue's config shape resolves both projects. It has top-level dotenv, `??=` writes, a
    `global-setup` project, every listed default form and a computed `executablePath`.

## Independent review

A read-only reviewer subagent found two problems, both fixed with regression tests:

- (HIGH) `foo⏎!/'/…` read the `!` as a non-null assertion. That hid a later `require`, where the
  old raw scan had widened.
- (MED) string-only global names could reach the global object through
  `Function("return globalThis")`.

The reviewer also flagged that the token walk depends on regexStart verdicts. A slash after a
comment was the remaining divergence, so the walk now reads the stripped text.

## PR #1596 review repair

An independent reviewer reported four findings. Each one has a regression test, and each test
failed on head 3ccbea4 before its fix.

1. (P1) `debugger⏎/'+/…` read the slash as division and swallowed a real `require` without
   a frontier.
   - Fix (`TJAA-V0-045`): every predecessor the ASCII classifier cannot settle is ambiguous.
     That covers non-operand keywords, non-ASCII bytes, `\` and escaped identifier parts.
   - A `//` or `/*` that the division reading would form also counts as a moved boundary.
   - Test: `TestUnsupportedSlashPredecessorPreservesUncertainty_PR1596`.
2. (P2) An escaped `'construc\u0074or'` key reached `Function`. A `'Num' + 'ber'` key then
   replaced `Number`, so `Number('1')` was admitted and changed a devices descriptor.
   - Fix (`TJAA-V0-041` amended): the env and numeric roots are refused under any reflective or
     code-from-text channel. Those are `Function`, `constructor` or `vm` anywhere, a string
     escape, a dynamic `import(`, a non-literal `require(` argument, or a non-literal computed
     member key.
   - Test: `TestPlaywrightReflectiveAccessRefusesEnvAndNumericRoots_PR1596`.
3. (P2) Site naming searched the whole body and counted lines once per unresolved import. That
   is quadratic: 100,000 imports did not finish within 60 s.
   - Fix: the scan keeps each specifier's offset, and each file indexes its line starts once.
     The same input now takes 0.46 s.
   - Test: `TestFrontierSitesAreLinear_PR1596`.
4. (P3) A commented `'./missing'` on line 1 was reported instead of the import on line 2.
   - Fix: sites use the parsed offset (`TJAA-V0-040` amended).
   - Test: `TestFrontierSiteIsTheParsedSpecifier_PR1596`.

## Residuals

- `}` and `)` before a regular expression still widen, now as a named `scan-unresolved` site.
- A `use` text that occurs several times in the config names every occurrence's line, at most 4.
- dotenv or another imported module that replaces `process.env` remains outside the static model.
- Configs that use computed member keys such as `devices[name]`, or string escapes, lose the
  env and numeric admissions and stay unresolved.
- Recall on the reporter's repository is `NOT_OBSERVED`.
