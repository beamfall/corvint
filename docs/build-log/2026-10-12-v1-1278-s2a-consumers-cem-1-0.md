## Intent

S1 left the `cem/0.x` wire in place because the consumers it listed under "Blocked in S1" still
read or wrote it. S2a moves every one of them to `cem/1.0`, so that no code outside
`internal/cem` calls `wire.Spec01..03`, `wire.ParseMap`, `wire.Canonical`, `verify.Exact` or
`verify.Canonical`. S2b can then delete those, `patch`, the 0.x workflow producers and the 0.x
`cem` CLI routes. The `internal/cem` 0.x code is untouched in this stage.

## Decisions

- One admission rule for every consumer (`CEM-V1-210`): a `cem/0.1..0.3` map refuses with
  `unsupported-spec` plus the `CEM-V1-200` recovery line (`wire.RetiredSpecFix`) where the error
  shape carries text. A refusal is never an internal error, a fallback or a pass.
- Frozen 0.x-only profiles admit no map: `lrf/0` (the LRF adapter refuses every map before any
  other input: a 0.x map with the retired-spec refusal, a `cem/1.0` map with "lrf/0 evaluates no
  cem/1.0 map"), `frontier/0` (a `cem/1.0` map keeps its `frontier-stable-view/0` route,
  `NOT_PRODUCED`, exit 1), `tcq/0`, `external-frontier-obligations/0`, the attest v0/v1
  predicates, and `prove` outside `--attest-cem-v2`. Their 0.x code stays until S2b deletes it.
- Signed attestations (decision 0525 §2): a `cem/0` or `cem/v1` statement still verifies as a
  claim without map bytes (`NOT_RUN`), and every supplied map refuses with `unsupported-spec`
  (`checkRetiredClaimMap`); no 0.x map can be `VERIFIED`. `prove --attest-cem-v2` keeps
  `attest-cem-v2-requires-stable-map` (`CEM-V1-065`), `docs corpus cem-stable` keeps

## Failure modes

- A consumer that still decodes a 0.x map shows up in acceptance search 1.
- A frozen profile that cannot be produced from a `cem/1.0` map refuses; it never emits a partial
  document.
- A frontier-v0 case that needs a 0.x map is skipped only through the declared capability, and the
  skip set is closed by `TestEveryCapabilityNamesWhyItIsOutOfReach`.
- A cli-parity retirement that is not pinned to its decision fails
  `TestDecision0308DeclarationsAreClosed`.
