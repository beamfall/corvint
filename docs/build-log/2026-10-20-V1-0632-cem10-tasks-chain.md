# 2026-10-20 V1-0632: runner receipt admission and the Tasks-to-verify chain

The 2026-10-17 delivered-open audit (`docs/build-log/2026-10-17-delivered-open-audit.md`) left
V1-0632 open on three gaps. This lane takes gaps 2 and 3. Gap 1, the positive capsule and dashboard
`cem/1.0` cases, belongs to a later lane.

- **Gap 2:** the portable envelope qualification was never cited as complete against criterion 2.
- **Gap 3:** no test ran the chain from Tasks through the runner and the producer to both verifiers,
  with controls.

The new requirements are `CEM-V1-280..287` in `docs/specs/cem-stable-v1.md`. They are accepted under
the owner's standing auto-accept (2026-10-11).

## Problem

### Opaque runner files

The plain producer (`CEM-V1-240`) checks its runner plan and receipt only by SHA-256. It would
therefore bind any of these as readily as a passing receipt:

- a receipt of failed tests;
- a receipt of only skipped tests;
- a receipt over earlier source bytes;
- a receipt of another plan.

A native or portable verifier cannot tell these apart either: both check the runner files only as
artifacts by digest.

### No end-to-end test

Each link of the chain had its own tests:

- Tasks attempts and gates (`internal/tasks/store`);
- the runner (`cmd/corvint-test-runner`);
- the producer (`internal/cemcandidate`);
- the verdict gate (`internal/taskman`, `cmd/corvint` `TestTCBV0016*`).

No single test joined them, so the controls the ticket asks for had never been run through the whole
chain.

## Decisions

- **Admission is opt-in.** It is a request member, `runnerAdmission: "corvint-test-runner/0"`. It is
  not a default, because the public `neutral-criterion` case carries opaque runner artifacts that
  are not `corvint-test-runner` documents. `CEM-V1-240` must keep reproducing that case byte for
  byte.
- **Admission is a producer check, not wire or verifier authority.** The map bytes are unchanged and
  record nothing about admission. `executionAuthority` stays `CALLER_OBSERVED`. A caller can still
  forge a self-consistent passing receipt; receipt authentication is V1-1264 / `FPK-V0-036`.
- **Order and codes.** The checks run in this order:
  1. `runner-document-invalid`
  2. `runner-receipt-tampered`
  3. `runner-receipt-stale`
  4. `runner-receipt-failed`
  5. `runner-receipt-skipped`

  Admission runs before the bundle is created, so a refusal leaves no directory at all.
- **Stale means "not the target's bytes".** Every plan input file must be a blob of the request
  `target` with the pinned SHA-256. The files are read by one bounded `git cat-file --batch`
  (at most 4096 inputs and 64 MiB).
- **The chain test lives in its own package, `internal/cemchain`.** The test builds `corvint`,
  `corvint-test-runner` and the portable `cem01-go` from repository sources. The Tasks and producer
  packages are read-confined in CI (`.corvint/test-read-scopes.json`) and cannot read those sources.
  An undeclared test-only package can. The package has no runtime code.
  Because a nested build cannot be declared narrowly, `internal/cemchain` is added to
  `.corvint/unbounded-readers.json` with that reason, as `tools/cem-trial` is. It is therefore
  selected on every change, at a cost of about 31 s.
- **Real binaries, private store.** The chain uses:
  - a private disposable native Tasks store from `internal/tasks/fixture`;
  - the production `cem-verdict` gate argv shape, pointing at the built CLI and consumer;
  - real `go test` runs through `corvint-test-runner plan` and `run --trusted-local`, pinned to the
    host `go` executable by SHA-256.

## Evidence (gap 3)

`TestCEMV1286TasksRunnerProducerVerifyChain` (`internal/cemchain`) passed on darwin/arm64 with
go1.27.2 in 30.9 s, including the binary builds. In order, it does the following.

1. **Tasks claim.** It creates a native ticket with `touchPaths ["src/"]` and claims it on the base
   commit, with scope `.corvint/changes/`, `artifacts/` and `src/`.
2. **Runner receipts.** The runner executes four selectors:
   - the stale draft (`b + a`): pass, exit 0;
   - final pass: exit 0;
   - final fail (`t.Fatal`): exit 1, receipt still written;
   - final skip: exit 0.
3. **Producer controls.** With admission on, each control is refused with no bundle:

   | Control | Code |
   | --- | --- |
   | failed receipt | `runner-receipt-failed` |
   | skipped receipt | `runner-receipt-skipped` |
   | draft-source receipt | `runner-receipt-stale` |
   | pass receipt with the fail plan | `runner-receipt-tampered` |

   Without admission, the failed pair is ACCEPTed. This shows the refusals come from admission.
4. **Positive production.** `cem prepare` and one `cem cite` per hunk (4 hunks) run against the base
   spec line, then the producer runs with admission. The result is ACCEPT, and the bundle artifacts
   equal the runner's bytes.
5. **Bind, seal and gate.** After the bind and seal, the gate is submitted on the sealed tree and
   runs through `store.GateRun`. The result is `PASSED`:
   - outcome `GRANT`;
   - native `ACCEPT` with sidecar `EXACT`;
   - portable `ACCEPT` with an equal `verdictSha256`;
   - every governed path satisfied.
6. **Post-production tamper.** A worktree edit of `artifacts/runner-receipt.json` is refused three
   ways:
   - `GateRun` refuses with `DIRTY_WORKTREE`.
   - The in-process gate gives `CEM_VERDICT_UNVERIFIABLE`. Native is `REJECT` at stage `artifacts`
     with `artifact-digest-mismatch`, and portable is `REJECT` at stage `artifacts`, with equal
     verdict digests.
   - `verify.Stable` rejects.

   Committing the edit and resubmitting fails the Tasks gate with `CEM_VERDICT_PRODUCER_MISMATCH` /
   `sealed-tree-mismatch`.
