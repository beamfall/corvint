# Freshness on Playwright 1.64.0 from the shared tuple, live-qualified

Date: 2026-10-20
Human intent: GitHub #1270, V1-2009. Owner decision (2026-10-20): keep decision 0448's
one-exact-release rule; receipts and freshness share one declared exact tuple set; no range.
Contract: `docs/specs/playwright-external-provider-v0.md` `PWP-V0-050`, `PWP-V0-051`,
`PWP-V0-052` (with the amended `PWP-V0-039`/`PWP-V0-040` wording) and the tuple note in
`docs/specs/playwright-per-test-freshness-v0.md`.
Base: `94d212c8c04c6c702ff238f7fade2ab7d3b2f06e`.

## Decision

- The shared table (`runtime_tuple.go`) gains one row: freshness/0 on 1.64.0, Node v22.23.2,
  bundled. That exact tuple was already admitted for the external profiles, so one Node tuple with
  Playwright 1.64.0 now satisfies both the external receipt and the freshness receipt.
- The row is added only because a live freshness run passed on it on this host. Freshness on
  1.64.0 with Node v24.11.1 or v22.23.3 has no live run and no row; no range is admitted.
- Two defects blocked the live run and are fixed in the same change:
  - The freshness command identity read its executable whole under the 64 MiB
    application-attestation bound; the official darwin-arm64 Node binary is about 113 MB, so the
    run failed `command unavailable`. The executable is now stream-digested under its own 256 MiB
    bound (`PWP-V0-051`); the regular-file, no-symlink and same-file checks are kept.
  - The reporter kept its own copy of the freshness tuple (1.63.0 with v22.23.3), so it returned no
    project identity for the new row (`report-identity-unknown`). The provider now passes the
    table's bundled freshness rows as the reporter option `freshnessTuples` (`PWP-V0-052`).
    Non-freshness controlled configs are byte-identical.
- `TestPTFV0ActualLive` takes `CORVINT_PTF_RUNNER_VERSION` (default 1.63.0) and an optional
  absolute `CORVINT_PTF_NODE`, whose directory is placed first on the bound PATH.
