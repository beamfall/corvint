- **new: `contextindex` `roleTerms` calls `countTerms` once per role line.** Each call allocates
  a fresh 8,192-entry interner: about 110 µs and 700 KB per call, against a counter reused across

- **V1-4202** delivered (`53e4f7cd0`; LGL-V0-805, LGL-V0-806).
  - **What it fixes.** The walk paid for each inline post record three times: one encode for the
    decode's size bound, one encode plus hash in `validateEntries`, then one encode plus hash in
    `postBytes` and a full re-parse in `validateRecord`.
  - **The change.** The decode now keeps its one encoding on `PostEntry.Raw`. The receipt checks
    and the walk's checks reuse it, so the bound, digest and content-address checks still run.
    The walk uses the decoded record instead of re-parsing.
  - **Proof.** Every `decodeReceiptValue` caller passes a `wire.Parse` result or a shallow copy
    of one. An elided receipt is restored to bytes and parsed again before decoding. A member of
    a canonical parse, re-encoded alone, is shallower, has fewer nodes, keeps the same array
    bound and holds already-checked strings. So `wire.Parse` cannot refuse it and returns an
    equal value. The walk takes the reuse only when the bytes are that same slice.
  - **Tests.** Four tests in `inline_post_reuse_test.go` cover the lemma, every bound,
    `validateRecord` refusal equivalence, and audit parity including tampering.
  - **WalkCost A/B** (BENCHMARK-HOST.md procedure, 40k, two rounds × 5, load 1.8 → 3.2):

**Where the seal time goes (AC1).** The CPU profile accounts for 37 s of a 193 s wall; the rest
is off-CPU (syncs and I/O waits on a shared disk).
- CPU, cumulative: `sealSegment` 17.6 s, made up of `collectSegment` 8.6 s and `dropSealed` 7.6 s.
  The opening `compactAudit` and the V1-4217 closing `retainMigratedCheckpoint` audit take 7.8 s
  together, and `syncDirs` takes 4.8 s of CPU in syscalls. The sealed range is read, parsed and
  hashed once by the opening audit and again by `collectSegment`.
- Off-CPU: every one of the 77 segments seals with its own durable protocol. That protocol is a
  marker, two synced files, three directory syncs and a head replace. `dropSealed` then removes
  the segment's 512 receipts and 512 request afterimages and fsyncs each directory it touched,
  one after another.
- The request afterimages sit in 256 shard directories, so one segment touches about 220 of them.
  That is about 17,000 serial directory fsyncs per 40k seal, which matches the off-CPU time.

**Why the sealed audit is slower (AC3).** The complete audit's CPU *falls* on a sealed store (8.9
against 12.8 s user) while its wall rises. `auditAttempt` wraps the native source in a
`segmentView`, and `prefetchFrom` only prefetches through a `*nativeRead` source, so a sealed
store walks every receipt sequentially.
