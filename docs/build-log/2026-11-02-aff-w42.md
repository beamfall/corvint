## NEW-C1: the stale-binary fork and the decision

The complaint was that `affected` degrades in every lane because lane Go paths differ from the
installed binary.

Measured first: staleness never changes a plan. AFP-V0-846 `self-binary-stale` is advisory. Every
lane's `UNKNOWN` comes from the plan itself. On the three lanes below it is 94 entries:
77 `LANGUAGE_FRONTIER` and 17 `UNOWNED_DIRTY_PATH`. A fresh binary reports the same scope.

Options weighed, against 51 local lane branches:

| Rule | Branches flagged stale |
|---|---|
| Current rule: any Go source path differs from the binary's build commit | 39 |
| A: stale only when the changed paths fall in the engine packages (package level) | 34 |
| Selection-only: stale only when the changed paths reach the selection code | 31 |

Decision: keep the rule, and fix the reporting.

- None of dgr-u29, tsf-w33 or glc-w34 becomes fresh under any narrower rule. A narrower rule buys
  little.
- Every narrower rule claims that a changed path cannot alter the result. A package-level
  engine-root list is hand-kept and unsound when the engine grows a new import, so it would invent
  certainty (invariant 2).
- Rejected B, self-rebuild: a read command would build into the module cache and run code it just
  built, which breaks invariant 4 and the one-binary local path.
- Rejected C, counting a base-built binary as fresh: the lane's own source would be invisible to it.
- Deferred A', a function-level index of the code the planner actually executes. It is sound, but it
  needs its own spec.

What was delivered instead:

- The notice appears in every output form: JSON `degradationDetails`, a text
  `degraded-detail CODE NOTICE` line, and the `--summary` form (ACX-V0-750).
- The notice appears once per invocation (ACX-V0-751).
- The notice says the plan, selection and exit status are this binary's own and current source may
  compute them differently. It gives both recoveries: `go install ./cmd/corvint`, and
  `go run ./cmd/corvint`.

## V1-4008: the binary-consumer fork and the decision

The root cause is an AFP-V0-762 `UNSELECTED_BINARY_CONSUMER` entry, such as
`tools/web-flows/test/e2e.mjs` for `cmd/corvint-web-flows`.

- It is outside the AFP-V0-028 allowlist, so `sessiontest.Build` turned it into `FULL`.
- `FULL` never runs it; `script/web-flows-gate` does. Widening therefore ran every Go package and
  still left the consumer unrun.
- A change touching only `e2e.mjs` was already `NARROWED` (220 units). `FALLBACK` came from Go
  changes reaching the command.

The fork:

- (a) Widen `gateselect.AllowedUnknown` and AFP-V0-028 for both profiles. This changes the accepted
  closed allowlist shared with the CI driver (AFP-V0-982, decision 0509), so it needs a reviewed
  amendment.
- (b) Local profile only, exactly like the STR-V0-064 precedent.

Chose (b) as STR-V0-750:

- On the local profile, a well-formed consumer entry keeps the scope the rest of the plan earns.
- The consumer is named once under `checks` as still required and not run.
- A malformed detail stays `FULL`. Well-formed means `fs.ValidPath`, not `.`, with no backslash or
  control character, judged the same on every host so the manifest stays host-independent.
- The `ci` profile is unchanged.

Proposal for the owner: a reviewed AFP-V0-028 amendment to admit the entry in CI. It is sound for
the same reason, because no CI job and no `FULL` runs these consumers.

Finding: a first draft also filtered the entry out of the plan that `corvint test` hands to
`gateselect.SelectStructuralIndexed`. A mutation proved that dead: the test passed without it. That
path calls `selectPackagesFrom(..., withUnresolved=false)`, so `unknownNarrowing` never runs for
`corvint test`. Only `sessiontest.Build` turns an unadmitted unknown into `FULL`. The filter was
removed before commit.

## Independent review

One Codex round on `105498708` found one P2 issue: the ACX-V0-752 recovery advice dropped rename
sources. With Git's default rename detection, `git diff --name-only BASE HEAD` lists only a
rename's destination. A `--worktree` path list built from it therefore drops the readers of the
old path, which `--base` still plans.

- Fixed: the refusal now names `git diff --no-renames --name-only BASE HEAD`, and ACX-V0-752 says
  why.
- Added `TestWorktreeWithBaseRecoveryKeepsRenameSources_ACXV0752`. It commits a rename, runs the
  recovery command the refusal names with `diff.renames=true` pinned, and requires both paths. It
  also requires the source in the `--base` plan and in the `--worktree` plan built from the list.
- The test fails on the old message: it lists only `NOTES.md`.
- The earlier test used `base == HEAD`, so it never exercised a committed range.
