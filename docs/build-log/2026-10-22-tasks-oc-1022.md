Lane `claude/tasks-oc-1022`, base `14dc0e985bab1c296a7e79d04f40f6e2eabffc83`.

## V1-2353: affected, init and overview swallowed Git's dubious-ownership refusal

- Problem: under a Git that refuses the repository for dubious ownership, `corvint affected`
  reported `unsupported-affected-revision` (no resolvable HEAD), `init` printed an `INVALID`
  inventory with an `invalid-repository` gap, and `overview` reported
  `unsupported-repository-guidance: invalid-repository`, instead of `GPK-V0-071`'s
  `repository-ownership-refused`.
- Root cause: `GPK-V0-071` classifies in `emitError`, which only sees Git's stderr when the error
  carries it. `affectedRevision` discarded the `rev-parse` stderr; the genesis repository reader
  collapses every Git failure to the bare code `invalid-repository`.
- Fix (`GPK-V0-089`): `affectedRevision` classifies its `exec.ExitError` stderr
  (`gitExitOwnershipRefusal`, `cmd/corvint/repository_ownership.go`); `init`/`adopt` on an `INVALID` inventory and the guidance verbs on
  any failure probe once with a hermetic `git rev-parse --git-dir` (`repositoryOwnershipRefusal`).
  The probe runs on the failure path only; the genesis receipt contract is unchanged.
- Evidence: `TestGPKV0071DubiousOwnershipIsOneCodedRefusal` subtests `affected`, `init`, `overview`
  FAIL with the three source files reverted and PASS with them (`-count=5`); the cmd/corvint
  `Init|Adopt|Activation|Guidance|Overview|Features|Review|Affected|Genesis|Ownership` subset passes.
- Rollback: remove the two helper calls; the helpers are unused otherwise.

## V1-2361: pool entry reasons could push pools.json past 1 MiB

- Problem: a `pool recover` reason of up to 4,096 bytes is copied into the QUARANTINED entry
  reason, so about 200 such entries fill the 1 MiB pools.json bound and every later pool write is
  refused `LIMIT_EXCEEDED`.
- Root cause: the only bound on entry reasons was the 4,096-byte prose bound shared with other
  verbs; nothing tied entry count x reason length to `MaxPoolStateBytes`.
- Fix (`PSR-V0-202`): round 0 capped recover reasons at 512 bytes in the lease codec; repair
  round 1 below moved the check to planning and derived the cap as 224 bytes.
- Evidence (round 0, superseded by repair round 1): a fixture without `configRef`, identities or
  escaping wrote 730,154 bytes; the review showed it did not establish the bound.
- Rollback: drop the planning check in `planPoolRecover`; no recorded reason is rewritten.

## V1-2361 repair round 1 (independent review)

- Finding 1 (replay): the 512-byte cap sat in the lease codec, which `transaction.Digest` runs
  before the replay lookup, so a recover recorded earlier with a 513..4,096-byte reason could no
  longer replay. Fix: the codec keeps 4,096 bytes; `planPoolRecover`, reached only after replay,
  refuses a longer fresh reason `LIMIT_EXCEEDED` with nothing posted.
  `TestPSRV0202_RecordedLongRecoverReasonReplays` drives `Model` with a recorded 4,096-byte recover
  and FAILS on the round-0 code (`Digest` refuses it).
- Finding 2 (bound not established): the round-0 fixture omitted `configRef`, identities and
  escaping. `TestPSRV0202_WorstCasePoolsStayBoundedAtReasonCap` now builds 256 entries with
  maximum `configRef`, source and identifiers (one CLEANING retarget), 256 REPORTED identities and
  512 receipts. It measures 907,069 bytes with empty reasons and derives a cap of 242 bytes from
  `B0 + 256*(68 + 2*cap) <= 1 MiB`, where 2x is the worst JSON escaping prose admits. The cap is
  224. At the cap, with every reason all `"`, the state is 1,038,649 bytes and recovery writes
  1,038,627. With 512 the derivation check fails and the state cannot even be encoded.
- Residual: identifiers made of escaping characters, sweep owners on every entry, or large
  `slots`/`waiters` lists exceed 1 MiB with empty reasons (a probe with escaping holders and
  receipt request IDs measured 1,091,418 bytes). No reason cap can fix that; such writes stay
  refused `LIMIT_EXCEEDED`.
