# 2026-10-07: writer fast route cost (V1-0915, V1-0918)

## Intent

Native tickets V1-0915 and V1-0918 are children of V1-0645 (the `CAL-V0-115..119` writer
checkpoint) from the [issue 641](https://github.com/beamfall/corvint/issues/641) batch. They record
two remaining costs of the fast route:

- **V1-0915.** A fast write read the intent tree about four times: the writer audit's two
  captures, its walk, and the pre-effect recheck. The acceptance asks for a heartbeat median of 5
  at 13k receipts in the tens of milliseconds, with the load band recorded. It also asks for the
  intent tree to be read once per write, with the fork and duplicate-request counterexamples still
  refused.
- **V1-0918.** Refused and replayed writes keep the complete route's cost (`CAL-V0-116`).

Correctness and fencing outrank speed. No refusal of forks, duplicate requests, stale trees or
tampered receipts may weaken.

## V1-0915 decisions (`CAL-V0-189`, proposed)

- **One content read per observation.** The writer audit's first capture keeps the intent bytes it
  read and digested. The walk projects those bytes, and the model takes them.
- **Second capture reuses bytes only for an unchanged file.** The second capture reuses the kept
  bytes only for a path that is still `os.SameFile` with the same mode, size and modification time.
  Any other path is read again.
- **The pre-effect content recheck stays.** `bindObservation` still recomputes the intent tree
  digest from content before effects. `CAL-V0-116` rejects stat stamps as evidence of currency, so a
  same-stat in-place edit must still be caught. `TestCALV0189_FastWriteRechecksIntentContent` plants
  exactly that edit for `mutate` and for a claim, and both refuse `INTENT_DIVERGED` with the complete
  route's decision.
- **The tree is now read twice per write, not once.** That is one observation read and one
  pre-effect content check. Reading literally once would need the stat stamp as evidence, which the
  accepted contract forbids. This is an open question for the owner.
- **No bytes change.** The journal, intent, request, receipt and checkpoint bytes are unchanged.

## V1-0915 measurement

`TestCALV0118_WriterHoldProfile` ran at `CORVINT_TASKS_HISTORY_SIZES=13000` with 880 tickets, 5
repetitions per verb, `GOMAXPROCS=3`, on darwin/arm64 with 12 CPUs. The binaries were prebuilt from
the base (`0b5096ca`) and from this change, and the runs were interleaved ABAB. The host carried
other lanes throughout, at 1-minute load 41 to 64. Medians, in ms:

| run | load before → after (1m) | heartbeat wall | heartbeat CPU | heartbeat observe stage | mutate CPU |
|---|---|---|---|---|---|
| base 1 | 54.9 → 47.2 | 1355 | 689 | 464 | 793 |
| V1-0915 1 | 42.9 → 41.3 | 910 | 617 | 186 | 669 |
| base 2 | 52.4 → 62.0 | 1086 | 680 | 409 | 768 |
| V1-0915 2 | 63.9 → 52.8 | 2611 | 704 | 510 | 720 |

- **Profile.** A scratch CPU profile of 20 heartbeats (not committed) showed `projected` falling
  from 0.86 s to 0.08 s.
- **Effect size.** The CPU difference is within the load noise, roughly 0 to 10%.
- **Dominant cost.** The dominant per-write cost is now the model stage (input validation, ticket
  decode, canonical encode and capacity checks over every ticket), followed by commit.
- **Acceptance.** The tens-of-milliseconds heartbeat target is **NOT_MET** at this load. Wall
  medians at load 40 to 60 cannot qualify it either way. The remaining cost is the ticket-proportional
  cost `CAL-V0-118` already records. Reaching tens of milliseconds needs validated-ticket reuse or a
  cheaper model, which is out of this ticket's scope.

## V1-0918 decisions (`CAL-V0-190`, proposed)

- **Replays are bound by hash, not trusted from the checkpoint.** The writer checkpoint moves to
  profile `taskman-writer-checkpoint/1`. Each request record now carries the SHA-256 of the
  latest afterimage beside the path digest, and is 64 bytes instead of 32. A request posted
  before the checkpoint replays on the fast route only under three conditions:
  - its file hashes to that digest;
  - the receipt that posted it is reached from the checkpoint receipt through at most 256 `prev`
    links, each read and hashed;
  - that receipt posts exactly this afterimage, under this request ID, with the same outcome and
    codes.

  Anything else declines, and the complete route decides as it does with no checkpoint. A
  request in the walked tail replays from the walk's own validated bytes.
- **Writes without a transaction are reported after the checks.** A model result that plans no
  transaction is reported without a write once the branch check and the pre-effect head and
  intent recheck pass. A lease STALE_POLICY candidate still declines, because the complete route
  may convert it through the handoff history.
- **The prior guarantee change stays.** A served replay or refusal detects no more than a fast
  commit does. Fork, torn-tail and stray-own-request cases still decline.
- **Rollback is a version mismatch.** A `/0` file is refused UNSUPPORTED_VERSION and only costs
  one complete-route write, which retains `/1`. A reverted runtime does the reverse.

## V1-0918 measurement

A scratch harness (not committed) ran repeated fast-route writes against cached synthetic stores. It
used `GOMAXPROCS=3` on darwin/arm64 with 12 CPUs, while other lanes kept the 1-minute load at 44 to 60.
The queue's §1 bound refuses a ticket beyond 10000. The "10k" row therefore holds 9900 tickets, so
that the seed write fits under the bound. Wall times are in ms; a range is min to max.

| store | load (1m) | lease replay (3) | mutate replay (5) | receipt-less lease refusal (5) | heartbeat median (5) | complete-route replay (3) |
|---|---|---|---|---|---|---|
| 13000 receipts, 880 tickets | 44 → 55 | 142–206 | 197–234, median 204 | 403–687, median 598 | 1056 | 17457–23701 |
| 10500 receipts, 1000 tickets | 59 → 60 | 239–368 | 211–536 | 827–1447 | 2955 | not run |
| 10500 receipts, 9900 tickets | 45 → 51 | 2012–2738 | 1981–3305 | 4297–9398 | 12192 | not run |

- **Replay stage cost.** The replay decision itself costs under 1 ms (`fast.replay` and
  `fast.lease.replay`).
- **Replay cost is the observation.** Nearly all of a replay's cost is the observation, which reads
  and digests the intent tree. The observation median grows from 134 ms at 880 tickets to 220 ms at
  1000 and 2212 ms at 9900.
- **Refusals add model work.** A receipt-less refusal also pays the model stage (367, 705 and
  3719 ms).
- **Bound against the complete audit: MET at 13k receipts.** Fast replays take 142 to 234 ms and
  refusals 403 to 687 ms, against 17.5 to 23.7 s for a complete-route replay of the same request.
  That is about 2 to 4% of the complete audit.
- **FENCED refusal is not a served refusal.** A stale-generation refusal records a receipt. It
  therefore commits on the fast route like any write, at about 2.3 s at 13k receipts, and is outside
  this measurement.
- **No growth with ticket count: NOT_MET.** Every fast-route write still projects the whole intent
  tree in the observation and checks every ticket in the model. Its cost grows roughly linearly from
  1k to 9.9k tickets. Removing that cost needs per-ticket observation and validated-ticket reuse,
  which `CAL-V0-118` records and this change does not attempt.

## Independent review

One Codex review covered `0b5096ca..66561567`. Both findings were confirmed and fixed:

- **Close failures during a replay are terminal.** `WriterReplay` read retained requests and
  receipts through `Native.Read`, so a failed native close became an ordinary decline. The complete
  route could then succeed past it, unlike the writer audit, where a close failure is terminal.
  `WriterReplay` now uses one native read lifetime and returns its close failure as `cleanup`. The
  route reports that failure as terminal, UNSUPPORTED_FILESYSTEM.
  `TestCALV0190_WriterReplayKeyAndCloseFailure` injects the failure at a request file, a receipt
  file and a root.
- **Request record key wording.** The `/1` wording said the key was the SHA-256 of the request
  path. It is the SHA-256 of the request ID, which names the path. The bytes were already right,
  and the same test pins the key for a real request ID.
