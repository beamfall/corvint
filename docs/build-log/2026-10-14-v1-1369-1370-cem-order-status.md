## V1-1370: spec status and the CEM-V1-107..112 acceptance basis

### Intent

After V1-1276 the spec's header, its Agent digest and the candidate traceability row (line 47) still
said "planned" or "unimplemented". On main, the stable `cem/1.0` wire is in fact implemented and
produced (decision 0525, `CEM-V1-140..152`, V1-1276). V1-1333 also left `CEM-V1-107..112` marked
proposed, even though the owner's standing auto-accept applied to them.

### Decisions

- **Status sentences only.** The status sentences now match the packet's
  `IMPLEMENTED_CONTRACT_PROPOSED_NOT_PROMOTED`: the wire is implemented and produced on main, the
  technical contract is proposed and not promoted, and qualification is bounded. The changed
  sentences are the `Delivery status:` header, the digest `Status:` and `Blocked on:` lines, and
  the remaining-acceptance cell of the `CEM-V1-001, 011..013` row. The `Intent status:` header
  stays "owner scope accepted; technical contract proposed". The
  candidate row still says the candidate is experimental and carries only the 0.2 hunk vocabulary
  (`CEM-V1-013`). No requirement text changed, and no sentence claims that the technical contract
  is accepted or that the profile is promoted.
- **Acceptance basis.** Each of `CEM-V1-107..112` now carries the inline marker "(accepted under the
  owner's standing auto-accept (2026-10-11); V1-1333)". The V1-1333 section's status now names
  that acceptance and says V1-1370 recorded it. The digest now lists `CEM-V1-107..112` as accepted.
  After the spec was staged, `make spec-requirements` regenerated the generated files: the
  `acceptedBy` column of `REQUIREMENTS.tsv` now reads `standing` / `2026-10-11; V1-1333`, and the
  `INDEX.json` and `README.md` delivery projections were updated. `internal/specindex` requires the
  digest `Status:` line to contain both headers, so it repeats them.

### Failure modes

- A status sentence could overclaim (accepted, promoted or stable-released). The Codex review checks
  for that, and the sentences mirror the packet's own status token.
- The generated files could drift from the spec. The `spec-requirements-check` and
  `requirement-definitions-check` gates catch this.

### Rollback

Revert the V1-1370 commit. The status sentences and the markers then return to their previous
text. Nothing reads these sentences as authority.

## V1-1369: normative nested result member order (`CEM-V1-113`)

### Measurement at base

Each consumer ran all eight `citation-vectors` cases twice at `b8a2e0336`, through a temporary
scratch test that is not committed. The native verifier used `Stable` and the portable consumer
used `runStableCanonical`. Each run's output was `json.Marshal` of the result plus LF, the same bytes
both CLIs write through `json.NewEncoder`.

- **Deterministic.** Each consumer's two runs were byte-identical (`diff -r`).
- **Native order.** `drift` entries are a struct, written `evidenceId, path, baseBlobOid, status,
  targetBlobOid, targetSpan`. `targetSpan` is a Go map, so it is written `end, start`. `hunks`
  entries are generic maps, so every nested object is sorted by name. `references` is a map, so it
  is written `artifacts, criterionBindings, criterionLinks, runnerReceipts`. Its entries are structs
  in declared order, with `omitempty` on the optional criterion members. `axes` is a map, so it is
  sorted.
- **Portable order before.** The `drift` struct order was the same, but `targetSpan` was written
  `start, end`. Hunks followed struct order: `id, path, oldRange, newRange, disposition, reason,
  basis`, then the optional witnesses, with ranges written `start, count`. `references` was written
  `criterionBindings, runnerReceipts, criterionLinks, artifacts`. Entry structs, `artifactChecks`,
  `axes`, `runtime` and the citation block matched the native order.
- **Values.** For all eight cases, the two consumers' lines differ only in nested member order.
  `runtime` and `repositoryEnvelope` match on this host (go1.27.2, `NOT_REQUIRED`,
  `canonical-repository-bounded/1`).
- **Digest.** `verdictSha256` was already independent of nested order. Both consumers decode the
  line, remove `runtime`, `repositoryEnvelope` and `verdictSha256`, and hash the canonical JSON with
  sorted names (`ALGORITHMS.md`, CEM-V1-109). The pinned digests in `EXPECTED.json` matched both
  consumers before this change.

### Decision

The orchestrator rule selects the normative branch. The native order is deterministic, and aligning
needs edits only in `interop/cem01-go`. The native verifier's output bytes do not change: the
pinned lines equal the native base-run outputs byte for byte (`diff -r` against the measurement).

- **`CEM-V1-113`** (accepted under the owner's standing auto-accept (2026-10-11); V1-1369) makes
  that order the contract.
- **`CEM-V1-109`** was still proposed in #879 when this lane started, so it was amended in place.
  Its clause "the order is not fixed; compare by digest, citation bytes or parsed value" now points
  to `CEM-V1-113`, and the spec says so. V1-1370 records the acceptance basis for 107..112 in the
  same PR.
- **Non-goal.** The V1-1333 non-goal "no fixed member order for nested result objects" is marked
  removed.
- **Portable consumer** (`interop/cem01-go/verdict.go`). The change touches only the result's
  encoding:
  - `drift03.MarshalJSON` writes `targetSpan` as `end, start`;
  - `resultHunks` re-encodes the hunks through generic JSON values, using `UseNumber`, so every
    nested object is sorted and integer digits are kept;
  - `resultReferences` writes `artifacts, criterionBindings, criterionLinks, runnerReceipts`.

  The map types keep their own encoding. The method is on a separate type because a
  `MarshalJSON` on `stableReferences` would be promoted onto `stableMap`, which embeds it.
  `nullableSpan` is unchanged because `driftItem` also uses it.
- **Packet.** `ALGORITHMS.md` CEM-V1-109 states the full nested order as new Apache-2.0 prose:
  - drift;
  - hunks at any depth;
  - references and each entry type, with the criterion omission rule and both `authentication`
    forms;
  - `artifactChecks`, `axes` and `runtime`.
- **Sealed vector.** Nine whole result lines are pinned:
  - `citation-vectors/results/<case>.json` (eight files);
  - `neutral-criterion/results/accept.json`, which carries non-empty references and artifact
    checks.

  The native verifier generated them through a temporary write switch, which was removed before
  commit. `TestCEMV1111CitationVectors{Native,Portable}` and both `TestCEMV1083NeutralCriterionPublicCase`
  compare their encoder output with these files byte for byte. The only exception is
  `runtime.goVersion`, which is substituted. All nine files are in the stable `manifest.json`, and
  the existing directory read scopes already cover them.
- **Manifest.** `tools/cem-stable-regen` only adds members to the sealed S0E result. It does not
  list new files, so it was not used to write. The manifest `files` entries were recomputed as
  sorted `path`/`sha256`/`bytes` records with a scratch script. The diff is additive, apart from the
  edited READMEs and `ALGORITHMS.md`. `go run ./tools/cem-stable-regen --check` passes.
- **README status lines.** `neutral-criterion/README.md` and `receipt-authentication/README.md`
  still said "PROPOSED / EXPERIMENTAL", contrary to `CEM-V1-107`. Both now use the same truthful
  status line as `citation-vectors/README.md`.

### Mutation check

### Independent review

Codex ran one read-only round, which is in the lane scratch log. It made three findings:

- **(a) Overclaim: passed.** Every "accepted" is scoped to requirement-level acceptance under the
  standing auto-accept. The technical contract stays proposed, and the profile is not promoted.
- **(b) Authentication form: confirmed and fixed.** The nested-order text left out the
  `{"method":"none"}` form, which both consumers write as the single-member object. `ALGORITHMS.md`
  now states all three CEM-V1-084 forms.
- **(b) Result-line encoding: confirmed and fixed.** "JSON escapes" did not settle which
  spelling a string uses (for example `/` or `\/`), or how integers and control characters are
  written. `ALGORITHMS.md` now defines the line's scalar encoding by the verdict digest's canonical
  JSON rules, plus the five HTML-safe escapes both consumers write. Go's `encoding/json` was checked
  on go1.27.2: it writes `\b`, `\f`, `\n`, `\r` and `\t`, other controls as lowercase `\u00XX`,
  `<`, `>`, `&`, U+2028 and U+2029 as `\u` escapes, and `/`, U+007F and non-ASCII as raw. No result
  number is a non-integer: hunk ranges come from typed integers in both consumers.
