Date: 2026-10-14. Base: `ee27168739ec1b65dd5a653d720cf811338c37ae`.
Requirements: `CAL-V0-225` (V1-1386) and `CAL-V0-226`..`CAL-V0-229` (V1-0710) in
`docs/specs/corvint-tasks-agent-leases-v0.md`, accepted under the owner's standing auto-accept
(2026-10-11). No decision file. 1.0 scope: PRS-V1-018.

## Issue 900: relative `--config`

`dispatchFlags` and the program verbs passed `--config` unchanged to `intent.ReadFile`, which opens
through `safeopen.File`. `safeopen.Root` takes only an absolute, clean directory, so every relative
spelling failed, and `readBoundedInfo` reported the open failure as `UNSUPPORTED_FILESYSTEM`. An
absolute path containing `..` already worked, because `filepath.Dir` cleans it before `Root`.

Fix at the caller, as the issue asks: `commandPath` joins a relative `--config` to `env.Cwd` and
cleans it, so `..` is resolved lexically for every form, before any filesystem access, and the safe
open then refuses a symlink in any remaining component as before. This is the rule
`service install` already used. The program verbs (`program.go`) use the same reader and get the
same fix; no other flag reads through it. The safe open still refuses non-clean input. Its error now
says "relative" for a relative directory, and a bounded read of a relative path reports `MALFORMED`
naming the path syntax. That code is scoped to the path-taking entry points (`ReadFile`,
`ReadFileWithInfo`), because `ReadFileFromRoot` passes a diagnostic label, not a path.
`TestCALV0225_DispatchConfigPathForms` failed on the base before the fix.

## Issue 899: sanctioned reader recovery

A dispatcher that stops on the CAL-V0-053 HOLD/UNKNOWN exception keeps `reader-lifecycle.json`, and
every later start refuses `QUIESCENCE_UNPROVED`. Before this change the only way forward was to
delete the marker by hand.

- (a) Operator command. `dispatch recover-reader` takes the program lock without waiting, and a
  running dispatcher makes it refuse `RESOURCE_COLLISION`. It then writes an exclusive, fsynced
  `taskman-dispatch-reader-recovery/0` record in `reader-recoveries/` that binds the reason, the
  evidence and the marker's sha256 and modification time. Only after that record is durable does
  it remove the exact marker it read.
  - Replay of the same request ID finishes the work, and reuse of an ID for a different attestation
    or marker is `REQUEST_ID_CONFLICT`.
  - "Journaled" here means this record plus, on the reboot path, a dispatcher event. It is not a
    native Tasks journal entry: the dispatcher's state is private to the program directory, and the
    recovery must work without the intent branch.
- Live evidence. After the spawn, a separate `taskman-dispatch-reader-leader/0` record
  (`reader-leader.json`) names the reader leader's pid and start identity. The marker itself is
  never rewritten.
  - A leader that still runs with that identity, or whose identity or record cannot be read,
    keeps the refusal, whatever state the marker is in.
  - A leader that has gone lifts nothing by itself, because its descendants may outlive it.
- Removal. Every marker removal renames the marker aside to `reader-lifecycle.json.clearing`,
  checks identity and bytes again there, and puts back a marker that changed. While that name
  exists the program stays quarantined, and the next recovery attests it first.
- (b) Automatic proof. A `/1` marker records sha256 digests of the machine identity (bound to the
  hostname) and of the boot: `kern.uuid` and `kern.bootsessionuuid` on Darwin, `/etc/machine-id`
  and `/proc/sys/kernel/random/boot_id` on Linux.
  - The next start, under the program lock, accepts a same-machine, different-boot marker as proof.
    It records a `HOST_REBOOT` record, removes the marker and emits `reader-recovered`.
  - `dispatch status` only reports that the proof is available.
  - A legacy `/0` marker, missing boot evidence, another machine or the same boot is never a proof.
    In those cases the diagnostic says so and names the operator command.
- (c) The `QUIESCENCE_UNPROVED` diagnostic, `readerDiagnostic` and the verbose help of `dispatch`,
  `dispatch status` and `dispatch recover-reader` all name the command and state the pid and boot
  evidence.
- (d) Re-sampling host pressure after a killed sample is not done. It is recorded as residual.

## Limits

- The reboot proof trusts machine-id plus hostname. A cloned machine identity under the same
  hostname could present a foreign boot as a reboot.
- The operator attestation is a statement, not an observation.
- The operator path emits no event.
- Re-sampling host pressure (issue 899 item (d)) is residual.
- A process that opened the marker before the take-aside rename and writes it after the second
  check is not detected. A crash between the rename and the removal leaves the `.clearing` file,
  which keeps the quarantine.
- A failed leader-record write leaves no live-evidence check for that run.
- A bounded read of a missing relative path still reports a missing file, not `MALFORMED` (Review
  finding 5).
- Live dispatcher qualification and Linux execution of the boot-identity reader are NOT_RUN.
- The full `internal/tasks/cli` package under `-race` was not rerun after the review fixes. Its
  earlier run failed `TestCALV0053_DispatchReaderCLIClearFailure` (fixed, below) and
  `TestATRV0004_InterruptStopsTheRun` (`SURVIVORS`), which passed three times in isolation under
  `-race` and touches no code in this change.

## Review

One read-only Codex round over `ee27168..HEAD`, focused on any path that lifts the quarantine
without proof. Five findings:

1. Blocker, fixed. `recover-reader` attested any marker that failed to decode, including a newer
   `/2`. A newer marker or leader record is now `UNSUPPORTED_VERSION` and is never attested or
   removed.
2. Blocker, fixed. A marker that failed strict decoding (for example a trailing newline) skipped
   the pid check. The pid now lives in the leader record, which is checked whatever the marker's
   state; an unreadable leader record refuses.
3. Blocker, fixed. Removal checked the marker and then unlinked the path, so a marker replaced in
   between was removed. Removal now takes the marker aside by rename and checks it there. The
   check-then-unlink pattern itself predates this change (CAL-V0-053).
4. Major, fixed. The post-spawn pid rewrite of the marker could overwrite evidence the reader had
   left in it. The full CLI `-race` run reproduced this: `TestCALV0053_DispatchReaderCLIClearFailure`
   returned OK with the reader's change lost. The marker is no longer rewritten.
5. Minor, recorded. A missing relative path is reported as missing before the relative-path check
   runs. Every `--config` is now resolved before the read, and moving the check ahead of the stat
   would change what existing callers of `intent.ReadFile` see for absent relative paths, so it is
   left as a limit.
