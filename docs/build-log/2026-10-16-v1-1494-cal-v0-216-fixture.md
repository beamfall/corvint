# V1-1494: CAL-V0-216 lock-wait fixture under CAL-V0-263

Date: 2026-10-16
Ticket: V1-1494 (GitHub issue beamfall/corvint#967, PR beamfall/corvint#985)
Requirements: CAL-V0-216 (accepted, decision 0518) is unchanged; CAL-V0-263 (proposed) is the
behavior change that made the fixture stale.

## Finding

PR CI (go-product-shard 5, run 38932651131) failed `TestCALV0216_LockWaitAdmissionVerbs`: with
the preparation gate held, `claim --next --lock-wait 1` returned `REFUSED ATTEMPT_LIVE`
(`retryable:false`) in about 0.1 s instead of the retryable `LOCK_TIMEOUT`. Reproduced 3/3 on the
branch head `d0bea5a72` and passed 3/3 at its base `294542f02`.

## Root cause: fixture, not a regression

CAL-V0-263 moves preparation before the gate: a preparation whose model plans no transaction is
decided there and reported under the writer lock without entering the gate. In this fixture only
`renew` plans a transaction; `claim --next` (ATTEMPT_LIVE), `submit` (UNSUPPORTED tree),
`pool acquire`, `pool confirm-safe` and `pool release` are write-free refusals. Holding only the
gate therefore no longer contends with five of the six verbs. A probe with the gate held showed
those five returning their refusals in 30-120 ms; with the gate and `taskman.lock` both held, all
six returned the retryable `LOCK_TIMEOUT` after about 1 s.

CAL-V0-216 binds the caller's bound to "preparation admission and writer-lock acquisitions". The
refusal path still acquires the writer lock with `CallerWait` (`commitLease`), so a genuinely held
lock still yields the retryable `LOCK_TIMEOUT` within the caller's bound. No production code changes.

## Fix

The test now holds both the preparation gate and the writer lock for the timed-out phase, asserts
that the planned `renew` timed out on preparation admission ("preparation acquisition exceeded"),
and releases the writer lock before the existing admitted-after-release check, which still holds
only the gate.

## Evidence

- Fixed test: `go test -count=5 -run TestCALV0216 ./internal/tasks/cli/` passed (load average about
  50 on the shared 12-core host).
- Mutations, each reverted: `commitLease` writer lock without `CallerWait` fails the test
  (`LOCK_TIMEOUT after 30.06s with --lock-wait 1s`); `underPreparation` without `CallerWait` fails
  it (`LOCK_TIMEOUT after 30.04s`).

## Review

One Codex round (read-only): no actionable findings; it confirmed both acquisitions keep
`CallerWait` and that the `renew` assertion stops the held writer lock from masking a bypassed
gate. Retained limitation, not introduced here: `lockTimedOut` accepts any timeout from the bound up
to the 30-second default, so neither version proves exact deadline adherence or the "spent across
phases without restarting" clause.
