# Gate-ledger retention, amortized prune and lock-file lifetime (lane glc-w34, V1-4241)

Base origin/main 35475f860d97bfde9bbaa6cccf1f2ba8f78ea44b. New requirements GL-V0-910 to
GL-V0-914 are in `docs/specs/gate-ledger-v0.md`; GL-V0-915 is unused. The spec commit comes
before the implementing commit. Scope: `tools/gate-ledger/` and the spec only.

## Problem (measured on wsl-lanes, `~/.cache/corvint/gate-ledger`, 2026-11-01)

- The directory held 12,493 entries: 4,096 `.json` records and 8,397 `.lock` files. No version
  ever removed a lock file.
- 4,096 records (the old `maxRecords`) spanned only 2026-11-01T13:47Z to 2026-11-02T00:28Z, about
  11 h at about 370 records an hour.
- A record averages 289 bytes (median 291, max 301).
- `prune` globbed and `lstat`ed every record on each write.

## Dispositions

V1-4241 is delivered in code. The ticket record itself could not be read on this host (see
Friction), so the orchestrator's brief served as the ticket text.

- GL-V0-910: `maxRecords` is now 32768, about 88 h at 370 records an hour (72 h was asked). The
  bound is about 9.5 MB of content, or about 128 MB at 4 KiB blocks.
- GL-V0-911: a write scans the directory only when `prune.stamp` is missing or at least 5 minutes
  old. The scan touches the stamp first. Between scans the ledger may exceed the bound by about 31
  records.
- GL-V0-912: the holder removes `KEY.lock` before releasing it. After `flock`, an acquirer checks
  that the path still names the inode it locked, and otherwise reopens the path. So GL-V0-008's
  single execution holds, and no lock file outlives its run.
- GL-V0-913: each scan removes every `*.lock` file it can lock without waiting. That reclaims the
  8,397 leaked files on the first scan after upgrade.
- GL-V0-914: `key`, `digestKey`, `lookup` and the record encoding are untouched, so every HIT or
  RUN decision on a retained record is unchanged.

Overlap screen: there are no commits for V1-4241 on any ref, and `GL-V0-91` appears nowhere in
history. tsf-w33's cac62f0d9 (`claude/lane-tsf-w33-1101`, unmerged) changes `execute` and the
invocation code in `tools/gate-ledger/main.go`, plus `main_test.go`. This lane touches only
`maxRecords`, `prune`, `lock` and the new helpers, and adds tests in the new file
`retention_test.go`, so the textual overlap is nil.

## Benchmark (`BenchmarkRecordFullLedger`, 200 writes into a pre-filled ledger)

`script/heavy.sh go test -count=1 -run '^$' -bench 'BenchmarkRecordFullLedger' -benchtime=200x ./tools/gate-ledger`

| Ledger size | Before (4096 cap, scan every write) | After (32768 cap, scan once per 5 min) |
|---|---|---|
| 4096 records | 31.7 ms/op | 0.18 ms/op |
| 32768 records | 35.4 ms/op (pruned down to 4096) | 1.66 ms/op |

The after figures include the first write's full scan (no stamp yet), spread over 200 writes. In
steady state a write costs one `stat` plus the record write, and a full scan runs once per 5
minutes. At the old per-write scan, a 32768-record ledger would pay a full scan on every write.

## Friction (full list)

1. `corvint-tasks ticket show V1-4241` refuses on wsl-lanes, both in the lane worktree and in the
   primary checkout. The ticket is newer than the committed `.taskman` snapshot, and no journal
   exists at `/home/russell/projects/corvint/.git/taskman`; the journal lives on the
   orchestrator's host. Lanes on this host cannot read new tickets.
2. `make dogfood-change` again refused (`FAIL not-complete`) because the uncommitted benchmark
   file, written to take the before numbers, was in the worktree. The "run it at change start"
   rule and "benchmark before, then change" pull against each other.
3. The real ledger directory was left untouched: the upgrade's first-scan reclaim of 8,397 lock
   files is shown only by tests, not on the live directory (`NOT_RUN`).
4. `corvint dogfood propose-citations` left 9 of 11 hunks `unknown`, including every
   `tools/gate-ledger` hunk. Citing them by hand to the obvious contract lines (GL-V0-006,
   GL-V0-008) was refused `cite-span-not-stable`, because this change amends those very lines.
   The fix was to cite the unchanged failure-mode table rows (BASE 214:215 and 221). When a change
   amends its own governing requirement, the proposer could offer that fallback itself.
