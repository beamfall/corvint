## Finding: slicing was already production, and its inputs were stale

The go-product-shard FULL path already runs every AFP-V0-041 slice under `test-confine` with
`CORVINT_CONFINE_ROOT`. The committed slice file split only `internal/tasks/store`, using an old
run, and the cost table was older than the packages it priced. As a result one shard took the
whole of `cmd/corvint` plus a large store slice. So the work here is to refresh the data, not to
change code or the workflow.

## Change

- `package-costs.json` was refreshed by `tools/ci-shard-costs refresh` from that run's eight shard logs.
  The input was filtered to the `go test -json` lines; the line counts before and after the filter
  were equal, so nothing was dropped.
- `test-slices.json` was regenerated by `tools/ci-test-slices generate --target 350s` from the same
  logs:
  - `cmd/corvint` has 2 slices: 898 named tests at 270.6 s, plus a catch-all at 285.7 s.
  - `internal/tasks/store` has 5 slices, of 288 to 316 s each.
- `tools/ci-test-slices replay` placed 348 units exactly once: 341 whole packages and 7 slices.
  Its predicted maximum shard is 996.6 s, against the observed 1457.4 s. That is a local
  prediction, not a hosted speedup.

The two STR-V0-007/008 tests in `internal/sessiontest` used to assert a fixed two-slice store split
at two or more shards. They now read the committed slice count, since a package with more slices
than shards runs whole (AFP-V0-041 (1)).
