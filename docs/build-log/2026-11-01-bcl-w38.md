# Batch-close fixes after PR #48 (lane bcl-w38)

Lane bcl-w38, branch `claude/lane-bcl-w38-1102`, base `b5620b4d9`. Tickets V1-4266, V1-4267 and
V1-4268. The tickets were not readable in the lane checkout: `ticket show` refused because the
checkout has no journal and `origin/main` does not hold them. The work follows the orchestrator's
dispatch text, and V1-4268's own acceptance criteria stay NOT_OBSERVED.

## Decisions

- V1-4266, TCD-V0-1101..1102. The gated close now plans each row's claim scope before any write,
  so a failure no longer shows up first at the claim. A diff of at most 256 paths keeps the
  TCD-V0-185 `--scope-from-diff` claim request unchanged, so earlier attempts still replay. Over 256
  paths, a declared ticket claims its DECLARED scope. That scope must cover the diff, otherwise
  the row is `UNRUNNABLE` `OUT_OF_SCOPE` naming `--seal` and `--manual`. Any other ticket claims
  the diff collapsed to directory keys as a REQUESTED scope. The collapse runs by depth: each round
  lifts only the deepest entries to their parent key. Collapsing only the deepest level keeps
  shallow, unrelated paths exact for as long as possible, so the claim reserves the least that
  fits. A store-side change to `--scope-from-diff` was rejected: it would change the claim
  contract for every caller, and the DERIVED digest would no longer equal the diff.
- V1-4267, TCD-V0-1103. The refusal came from `prose("")`, which turns an empty `state` into
  "message withheld". An absent, empty or non-prose state is now `MALFORMED`. The refusal names the
  field and the `batchPRFields` list, as the `mergeCommit` refusal of TCD-V0-180 already did.
- V1-4268, TLF-V0-1101..1102. Progress delivers only when it names this batch: a pr equal to the
  batch PR or a lane PR proven in the merge ancestry, or a head the merge reaches and its first
  parent does not. A progress entry naming an excluded PR therefore delivers nothing, the same as
  that PR's body. This is a candidate-selection read in the TLF-V0-883 sense. The gated close
  still runs every gate, and no completion check reads progress. The bulk writer reuses the
  CAL-V0-106 chunked writer instead of adding a new multi-target loop. Each entry therefore keeps
  its own CAS, receipt and `<ID>/<index>` request id. `current` uses the TCD-V0-967
  landed-revision rule, so a retry replays.

## Evidence

`TestTCDV01101_GatedBatchCloseBoundsA712PathDiff` builds a real 712-path batch merge. Its
undeclared ticket closes `VERIFIED` with ten collapsed keys, and those keys are the attempt's
REQUESTED scope. `TestTCDV01101_CollapseScope`, `TestTCDV01103_MissingStateNamesTheField`,
`TestTLFV01101_BatchReadsRecordedProgress` and `TestTLFV01102_BulkProgressWritesManyTargets`
cover the rest. The whole `internal/tasks/cli` package passed once (500 s). A live batch close of
PR #48 is NOT_RUN: lanes do not write the store.

## Independent review

The review found that a progress mark could override a TCD-V0-730 veto. In the case it found, a
batch body says `V1-1: BLOCKED` and a stale `IN_REVIEW` mark names the lane PR. The draft promoted
every mentioned ticket. Now progress speaks only for tickets the batch text never names. The review
also found that each `current` entry paid one store load, and that an empty diff still reached the
claim with advice batch-close cannot take. Both are fixed. Two findings remain open, and both are
conservative. The declared-scope precheck ignores restored widen paths (TRM-V0-006), so it can
refuse a claim that would succeed. Separately, the step request ids, which predate this lane, carry
no scope source.

## Codex review, round 2

Codex found six issues, and all six held up against the code. Each now has a negative test that
failed before the fix.

- **The progress read trusted the first piece of evidence that matched.** A matching `pr`
  delivered the ticket even when the mark's head was the batch's first parent. A `pr` naming an
  excluded PR fell through to the head rule.
- **A failed `merge-base` counted as delivery proof.** The query returned false, and negating that
  false read it as "not in the first parent".

TLF-V0-1101 now requires every piece of evidence a mark carries to hold. Ancestry uses an
error-preserving query, and an unobservable head abstains with a warning.

- **Bulk `current` discarded its read error.** In an intent-only checkout the read panicked. When
  another writer's receipt was pending, it hid recorded entries, so a retry conflicted.

Reading the request index directly was not enough, because that index also refuses REDO_PENDING.
The batch now settles the pending receipt once under the writer lock, as `ticket split` does,
then matches digests as the single-target form does (V1-4290). Without a journal, no lookup runs.
The single-target `current` and `hold` paths still discard that read error, so they meet the same
pending-receipt case.
