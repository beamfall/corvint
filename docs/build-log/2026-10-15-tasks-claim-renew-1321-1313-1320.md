# Tasks renew liveness, superseded generations and claim scope (V1-1313, V1-1320, V1-1321)

Date: 2026-10-15. Base: `595359a1b348ecdb2cfdfbece2ad23bb3ceb9eaa` (origin/main).
Spec: `docs/specs/corvint-tasks-agent-leases-v0.md`, CAL-V0-230..231.

## Decisions (orchestrator, 2026-10-15)

1. V1-1321: claim MUST reserve the union of the ticket's touchPaths and every requested `--scope`
   path, on first claim and on re-activation, or refuse and name the paths it did not accept. The
   claim output MUST list the effective reserved scope.
2. V1-1313: a successful renew by the current holder at the current generation updates
   `lastHeartbeatAt`.
3. V1-1320: a renew (and a heartbeat, if it has the same gap) with a non-current generation MUST be
   refused with the existing code, and the live lease MUST stay unchanged.

Every decision was checked against the accepted requirements before it was implemented. When a
decision conflicted, it was stopped and reported.

## V1-1313: implemented as CAL-V0-231

Root cause: `planRenew` extended the lease but did not write `lastHeartbeatAt`. Only a claim or an
`attempt heartbeat` set it. A holder that kept its lease alive with `renew` alone therefore read
`STALE_HOLDER` once the TTL passed.

Change: `planRenew` now records `lastHeartbeatAt` at its `recordedAt`, in the same write that
extends the lease. This uses the existing optional attempt field, so the journal, request and
receipt shapes are unchanged and there is no migration. The verbose `renew` help states this.

No accepted requirement forbids the change. CAL-V0-048 constrains the heartbeat, which must never
extend the lease; it says nothing about what a renew records. The spec's own runtime model already
says "a lease it renews stands in for process liveness".

Two existing tests had silently depended on renew not recording the signal:
`TestCALV0120_PolicyTTLDrivesHolderReads` and `TestCALV0121_StaleHolderCoordinatorHandoff` (both in
`internal/tasks/cli`). They now place their renew 330 s before the read instead of 180 s, so the
signal is still older than the 300 s TTL. What they assert is unchanged.

## V1-1320: no conflict, already conformant; regression pinned as CAL-V0-230

Reproduction on both the complete route and the lowered writer-checkpoint route:

1. Claim (generation 1), then renew.
2. Release.
3. Re-claim. This keeps the same attempt ID and takes generation 2.
4. Renew with generation 1 under a fresh request ID.

Step 4 is refused `REVISION_CONFLICT` `FENCED` ("generation 1 is not the attempt's current
generation 2"), and the refusal is recorded. Both `expiresAt` and `lastHeartbeatAt` are unchanged.
`attempt heartbeat` behaves the same way.

Reusing the request ID of the earlier generation-1 renew instead returns `replayed: true` with
generation 1 and writes nothing. This is the likely source of the reported "OK".

Refusing that replay would break the request-ID replay contract. For heartbeats, CAL-V0-048 says
replay returns the original result "including after expiry or readmission". The replay is
therefore documented in CAL-V0-230 and in the `renew` help, not changed.

## V1-1321: stopped on CAL-V0-021

CAL-V0-021 fixes a precedence: DECLARED, "else" REQUESTED, else DERIVED, else WHOLE_REPOSITORY. A
union of declared and requested paths contradicts it. `claimScope` drops `--scope` whenever the
ticket declares paths under QUALIFIED coverage. This happens on a first claim too, not only on
re-activation.

One compatible form would be an amendment to CAL-V0-021. It would admit the union as DECLARED plus
the requested paths, which is the CAL-V0-025 widen shape at admission. Refusals would name the
unaccepted paths, and the claim result would list the effective scope. Nothing was implemented.

amendment. Attempts that a renew already wrote keep a valid `lastHeartbeatAt`.
