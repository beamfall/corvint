## The four 2026-10-31 audits

None of the audit reports carries an explicit verdict line; the verdicts below are this lane's
one-line summaries of each report's conclusion.

- Format (`cem-audit-format.md`): CONCERNS. The Go consumer cannot verify every committed map
  (F1, the 4096 tree-entry cap), one sidecar disagrees with its map at 8668f77b (F2), base retention
  is unenforced (F3), the closed 1.0 decoder has no extension point (F4, V1-3759), and integrity
  does not bind semantics (F5, V1-3771). Order: fix F1-F3, add the 1.1 extension point, and move to
  an index-based 2.0 only once map cost matters.
- Trust (`cem-audit-trust.md`): CONCERNS. Claim semantics, the producer identity and the ledgers
  are not bound by any signature. Adopting in-toto/DSSE envelopes fits; Sigstore and SCITT need a
  network service and conflict with invariant 7.
- Agent production cost (`cem-audit-agent.md`): CONCERNS. No runner-signed receipts exist, 19% of
  hunks are `unknown`, and reruns dominate the cost of producing a map.
- Usage (`cem-audit-usage.md`): CONCERNS. Closeout cost sits in reruns, not in the format; nothing
  in a map is runner-verified; "supported" means "cited", not "shown adequate".

## Decisions

- The body is index-based: `paths` in first-use order, evidence rows `[path, start, end]` (derived)
  or `[path, start, end, blobOid, spanSha256]` (pinned), and hunk rows `[reason, [ev, rel]...]`
  bound to the patch hunk ordinal. Hunk IDs, ranges, display paths, evidence IDs, blob ids, span
  hashes and dispositions are recomputed by the consumer, which is what makes four format-audit
  tamper vectors unrepresentable (CEM2-V0-019).
- Paths are interned in first-use order (evidence order), not sorted, so the encoding is a
  deterministic function of the 1.0 map and needs no extra sort key.
- The encoder abstains with `cem2-unsupported` instead of approximating whenever the 1.0 map holds
  something the body cannot carry: a spec other than `cem/1.0`, another `excludedPath`, criteria,
  receipts, links or artifacts, an explicit `role: "change"` (projection would drop it), a repeated
  or non-derived evidence id, a coverage or discriminates witness, an unknown reason or relation,
  a disposition that is not its reason's, or a dangling basis (CEM2-V0-020).
- A body over any cem/1.0 bound (bytes, hunks, evidence, path bytes) is refused with
  `cem2-bound-exceeded` before any Git read (CEM2-V0-010). The codes are prototype-local, not
  registry entries.
- Hunk order is significant: reordering hunk rows permutes the claims across patch hunks, so the
  projected 1.0 map is different and shows as a byte mismatch, not as an equivalent encoding.
- `GitSource` opens one budgeted `gitauth` repository per map and reads each distinct blob once;
  evidence is resolved at the base tree with the same mode and span rules as the native verifier.
- `internal/cem2proto` is declared in `.corvint/unbounded-readers.json`, not in
  `.corvint/test-read-scopes.json`. Its corpus test resolves every committed map's base and target
  in the repository Git object store, and the unwired test runs `git grep` over every tracked Go
  file; `.git` is unreadable under the confine wrapper, so the reads cannot be declared narrowly
  and the package is selected on every change. `make selection-baseline-check` stays at its floor
  (narrow 12/19, misses 0).

## V1-3760 measurements

Re-measured on the 180 committed maps under `.corvint/changes/` at base e9a5d6c8 (the charter's
111 is the count at the audit's base), by the committed tests in `internal/cem2proto/corpus_test.go`:

```sh
HEAVY_WHOLE_REASON='new experimental package internal/cem2proto; no prior selection exists' \
  CEM2PROTO_CORPUS=all ~/lanes/heavy.sh go test -count=1 -v ./internal/cem2proto/
```

- Round-trip (CEM2-V0-005): 180/180 projected byte-identical to canonical 1.0, 0 abstained,
  0 unavailable; 17.9 s in total, a mean of 99 ms per map including Git (the audit's Python
  prototype reported 0.15 s on 111 maps).
- Corpus facts: every role absent, 1 map with provenance, 10,501 hunks, 5,266 evidence records,
  2,259 `unknown` hunks (21.5%). Median 1.0 map 27,880 B (upper median).
- Sizes in bytes (CEM2-V0-022; share of 1.0 raw in parentheses):

| Form | Raw | gzip per file | gzip of the whole corpus |
|---|---|---|---|
| cem/1.0 | 5,567,310 | 1,290,574 (23.2%) | 1,234,628 (22.2%) |
| 2.0 body, derived | 340,815 (6.1%) | 148,286 (2.7%) | 92,308 (1.7%) |
| 2.0 body, pinned | 920,075 (16.5%) | 408,453 (7.3%) | 339,956 (6.1%) |

- Header: mean 278.0 B, the unit a signature covers. The audit reported about 460 B to sign; the
  two header layouts were not reconciled, so the difference is unexplained.
- Against the audit (111 maps): derived 6.1% vs 5.7% (16.3x vs 17.7x smaller), pinned 16.5% vs
  15.4%. The audit's 25.4% delta-encoding figure was not re-measured; the prototype has no delta
  form.

## Tamper-vector analysis

- Made unrepresentable in derived mode (the consumer recomputes the value, so a forged value has
  nowhere to go): `fabricated-evidence-id`, `span-hash-mismatch`, `hunk-ranges-moved`,
  `hunk-id-forged`. Tests: `TestCEM2V0019DerivedVectorsAreUnrepresentable` (a moved range, forged
  hunk id and forged span hash project back to the original; a forged evidence id does not encode).
  In pinned mode a stale or forged blob id or span hash is refused with `cem2-pinned-mismatch`.
- Changed meaning: `hunk-reorder` now permutes claims across hunks instead of being refused by an
  ID check (`TestCEM2V0006HunkReorderPermutesClaims`).
- New vectors introduced by the index format, each refused and tested in `refusal_test.go`:
  hunk-count mismatch, index out of range, code out of range, unknown `critical[]` entry
  (`cem2-unsupported-critical`), and `bodySha256` mismatch. The lane also tests patch-sha mismatch,
  pinned mismatch, malformed body, unresolved evidence, non-empty `parents[]` and the bound refusal.
- Still admissible: `span-hash-recomputed` and `evidence-ids-swapped` yield a different but valid
  1.0 map (`TestCEM2V0019AdmissibleClaimEdits`). The format binds what was cited, not whether it
  supports the claim; that stays V1-3771 and is not closed by 2.0.
