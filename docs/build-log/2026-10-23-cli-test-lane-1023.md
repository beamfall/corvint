## V1-2305: cli tests orphan dispatch workers (ATR-V0-310)

Cause: the dead-man reaper of V1-2189 hooks `dispatch.launch` from inside the dispatch package's own
test binary (an unexported seam), so a test binary of another package that starts the dispatcher
has nothing. Two `host.sh` workers of an `internal/tasks/cli` test survived 9 to 12 hours.

Decision: do not widen the product seam. The cli test binary finds the groups the dispatcher starts
by their shape: a worker is a session leader whose parent is the binary. Three layers
(`worker_reap_internal_test.go`, `main_internal_test.go`):

- `ReapWorkersOnCleanup(t)` (per test, run last, also after `t.Fatal`) kills every group led by a
  child of the binary that was not running when it was called and fails the test naming them. It is
  called by the tests that start dispatcher workers: `TestCALV0052_DispatchCLIClaimHandoffAndStatus`,
  `TestATRV0101_WorkerWithoutDispatcherVerbReceivesNoticesThroughHook`,
  `TestCALV0053_DispatchReaderCLICrashRetainsQuarantine` and both `TestPSRDispatchNativeAdapter` cases.
- `TestMain` kills any such group left after the last test and fails the package. The full package
  run reported none.
- A dead-man reaper (the binary re-executed in its own session, standard input a pipe only the binary
  holds) samples the binary's group-leading children every 200 ms (from `/proc` on Linux, `ps` on
  Darwin) and, at end of file, SIGKILLs each recorded group and member whose start identity still
  matches. This covers SIGKILL and the package timeout, when no cleanup runs. A binary that tests
  re-execute as a helper inherits `CORVINT_CLI_TEST_ROOT` and stays out of the reaping.

Limit: a group started and ended within one 200 ms sample of the binary's death is not attributed
by the reaper; the per-test and end-of-run checks do not sample.

Evidence: `TestATRV0310_LeakedWorkerGroupsAreReaped` re-executes the test binary as a helper that
starts a real dispatcher worker (`dispatch --once`, a host that sleeps) and then (1) leaks it after
registering `ReapWorkersOnCleanup`: the helper must fail naming the group and the group must be gone;
(2) leaks it unregistered: the package must fail and the group must be gone; (3) is SIGKILLed after
the reaper logged the group: the group must be gone within 30 s. With the three layers disabled
(`TestMain` not arming, `ReapWorkersOnCleanup` a no-op) all three subtests fail: the first two with
"did not fail" messages, the third at its two-minute bound because the reaper never logs the group.
With them enabled it passes, and 8 repeats of this and the three new tests below passed at load 6.

## V1-2173: detached equals foreground (ATR-V0-312)

The V1-1557 decision (`2026-10-21-detach-claim-semantics-and-prune.md`) made `--detach` a transport
with no semantics of its own. `TestATRV0312_DetachedClaimOutcomeEqualsForeground` builds two stores the
same way, gives holder `agent` a live attempt under request id `r1`, and sends three claims in the
foreground to one store and as `--detach --wait 30` to the other: another ticket under `r2` (a second
attempt, generation 2), the held ticket under `r3` (`ATTEMPT_LIVE`) and the held ticket under `r1`
(idempotent replay). The exit code and envelope must be equal after removing the random attempt id,
wall-clock instants and the digests of records that carry them, and the three outcomes must differ.
Mutant (reverted): the detached child rewriting `ATTEMPT_LIVE` fails it.

## V1-1559: Linux detach evidence and the LOST attach race (ATR-V0-311)

Linux (this host): the 25 detach tests (`ATRV0021..0029`, `ATRV0050`, `0053`, `0066`, `0095`, `V11721`,
`PSRV0111..0114`, `PSRV0185`) plus the new ones pass, 28.7 s; `-run` pattern and output in the PR.
Race: `leaseDetachAwait` read the child's liveness first and the launch lock second. The launcher
writes `child.json` and then releases the lock, so a launch that completed between the two reads
left "no child on record" and "lock free", and the attach reported `LOST` for a child that was
running. It now reads the lock, then liveness, then (only when both say "no launch, no child") the lock again and, if still free, liveness once more, and reports LOST only if every read agrees. The independent review found the first version of this fix, which re-read only the lock, still left a launch that began after the first read; the extra liveness read closes it. A package seam
(`leaseDetachProbeGap`, nil outside tests) runs between the first lock read and the liveness read.
`TestATRV0311_AttachNeverReportsALaunchCompletingBetweenItsReadsLost` completes a launch inside that gap
and requires PENDING; with the old read order it fails with `SUPERVISOR_LOST` (checked).
`TestATRV0311_AttachDuringChildStartupIsNeverLost` attaches continuously through a real launch with the
injected 1.5 s child startup delay; it also passes on the old order (the window is too narrow to hit
reliably), so it is end-to-end evidence, not the regression test.
