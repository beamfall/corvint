## V1-2881: no aggregate admission wall (`IDX-SNAP-V0-910`, `IDX-SNAP-V0-911`)

Decisions:

- The aggregate refusal is removed, not raised: `validateBlobAdmission` and the query rename
  (`queryAdmissionError`) are deleted, and `fetchBlobs` reads in chunks of at most 32 MiB of framed
  `cat-file --batch` output (`maxBatchBytes`, was the 128 MiB whole-set buffer). Each chunk's
  buffer is its exact expected size and its blobs alias it, so the total is held once and no single
  read scales with the repository. A chunk is a separate `git cat-file --batch` process; for 575 MB
  that is about 18 processes, negligible beside parsing.
- Incremental consumption (direction 2) is not attempted: the compiled `Index` keeps every
  source's `Data` (snippets, spans and the snapshot need it), so peak memory is bounded by admitted
  bytes plus the derived index whatever the read pattern. Recorded as the measured residual below.
- `maxIndexedSources` (200,000) and the 64 MiB tree listing stay. Both bound bookkeeping before any
  blob is read, the listing at 200,000 entries is about 14 MB, and no observed repository is near
  either; lifting them needs a streamed `ls-tree` and is not needed for any criterion.
- The receipt gains `source_bytes` and `build_ms` (`IDX-SNAP-V0-911`); that is the read-only
  report: report fields only, no snapshot byte.
- Tests whose trigger was the aggregate refusal: `TestIndexBuildingCommandsRecordUnsupportedRefusal`
  now asserts the 135 MB fake tree is not refused (`..._IDXSNAPV0910`); the prove checkpoint
  subtest "coded Build error" is removed because no coded unsupported Build refusal remains on that
  path (the codeless path stays covered by `TestPlainProveCodelessBuildErrorStderrIsUnchanged`);
  `TestValidateQueryBlobAdmissionUsesFullEagerBound` and the language-free message test are removed
  with the message.

## V1-3310: the refresh writer converges under load (`IDX-SNAP-V0-912`)

Decision (the fork the ticket names): a CPU-time work budget under a longer hard wall, not
adaptive backoff. The writer cancels its build after 55 CPU-seconds (getrusage self plus reaped
children, checked every second) and records `expired`; its hard wall is 10 minutes (work context
ends at 550 s). Backoff alone would stop doomed writers but never deliver context while the load
lasts; with a long wall the single-flight lock already stops later hooks from starting writers
(`already running`), so both acceptance branches hold. The V1-0607 numbers fix the size: 8 CPU-s
idle, about 3.6% of a CPU for a nice +10 writer under 36 nice-0 loops on 12 CPUs, so about 220 s.

Second finding while qualifying: with the wall bound lifted the writer still failed, after 266 s,
with `Git repository index exceeded its deadline` (12.7 CPU-s used). The shared 30 s
`DCW-V0-075` deadline wraps the build's Git phase and is a wall bound too. The worker now marks
its context in-process (`contextindex.WithWriterBounds`), and only that context drops the 30 s
deadline; `DCW-V0-075` notes the exemption. Every other build keeps 30 s.

Live qualification (`~/lanes/indexcli-w5-scratch/refresh_qual.py`, real
`corvint adapter claude-code user-prompt` hook under `timeout 2` on a `--no-local` clone of the
base, 36 nice-0 `sh` loops; driver, loops, hooks and writer pinned to CPUs 0-11):

Before (same driver, wall bound removed but the 30 s deadline still applied): the writer ran

## V1-2585: Git start errors name their class (`DRC-V0-910`)

Decision: a closed class, not the errno text. `contextindex.GitStartErrorClass` maps the retained
start error to `ETXTBSY`, `ENOENT` (including `exec.ErrNotFound`), `EACCES`, `EPERM`, `ENOEXEC`
or `other`; the uncoded `emitError` envelope adds `"git_start_error"` between `error` and `ok`
only for that cause. The `error` bytes stay `Git error: cannot start Git`, and no path or errno
string is emitted, so the member needs no secret screen. The fallback the ticket observed was a
test's own failure text; any caller that records a fallback reads the same function.
`TestGitStartErrorClass_DRCV0910` starts a real missing executable (ENOENT) and a real executable
held open for writing (ETXTBSY, the V1-2585 race), and an exit failure that names nothing.
