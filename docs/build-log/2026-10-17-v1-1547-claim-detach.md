# V1-1547: detached claim and pool acquire

Date: 2026-10-17. Base: `8fa297eae3e31f2cde6811552dd762ed031dad40` (origin/main).
Ticket: V1-1547, from GitHub issue 1005. Spec: `docs/specs/corvint-tasks-agent-leases-v0.md`,
CAL-V0-320..326, accepted under the owner's standing auto-accept of lane requirements
(2026-10-11). No accepted requirement is amended: the store's request-id replay (CAL-V0-069) and
`--lock-wait` (CAL-V0-111, CAL-V0-216) are used as they are.

## Problem

An agent host kills a tool call at its own timeout. A claim that waits for the preparation gate
can outlive that call. The agent then cannot tell whether the claim committed, and a retry under
a new request id can claim a second time.

## Decisions

- Handle. The caller's `--request-id` is the handle. `--attach` takes it and nothing else except
  `--holder` and `--wait`.
- Process. The launcher re-executes the same binary with an internal `--detached-child` flag in a
  new session (`setsid`, the same `detachAttr` as detached attempt runs), with no stdin or stdout
  and stderr appended to `child.log`. The child runs the unchanged `leaseCommand`, so its result
  is the plain command's result.
- Records. One directory per request id, `<common dir>/taskman-requests/<sha256(id)>/`, beside the
  journal and outside the store, as for detached attempt runs (`taskman-runs`). Nothing is added to
  the store, receipts or policy.
- Exactly once. The store already replays a committed request id, so the detach layer only has to
  avoid running two children at once and to keep refusals, which the store does not record. A
  launch lock serialises launchers. The child holds a `running` lock for its life and exits at once
  if it cannot take it or a result already exists. A lost child is restarted only by a repeated
  `--detach`; attach never starts anything.
- Conflict. `request.json` records command, holder and an argv digest. Another command, holder or
  argv under the same id is refused `REQUEST_ID_CONFLICT`, like the store's own rule.
- Ceiling. 600 seconds as a context deadline on the lease command (above the 300-second
  `--lock-wait` maximum, so a lock wait ends first with its own `LOCK_TIMEOUT`), and a hard exit 60
  seconds later. The kept result at the deadline is the command's own cancellation result.
- Retention. Finished records older than 7 days are pruned, best effort and bounded by the same
  65-entry listing as `taskman-runs`, when a later detach starts.
- Unchanged path. Routing changes only when `--detach`, `--attach` or `--wait` is present, found
  by a scan that skips every lease flag's value.

## Interpretation of acceptance (5)

The issue asks that a holder with a live attempt gets that attempt back. Under the same request id
this holds: the kept result, or the store replay after a lost child, returns the same attempt and
generation. A claim under a different request id by a holder that already has a live attempt is
not changed here. That would alter claim semantics for every caller and is recorded as a residual.

## Evidence

Focused tests in `internal/tasks/cli/lease_detach_test.go` (Darwin) cover a caller killed by
`SIGKILL` of its process group mid-claim, repeated attaches and detaches with `head.json`
unchanged, the plain replay of the same attempt, a lost child restarted to the replayed attempt,
request-id conflicts, verbatim refusals for `claim` and `pool acquire`, the wait bound, the
ceiling, the unchanged path and pruning. The existing claim, pool, lock-wait, detached-run and help
tests pass. Linux runs NOT_RUN on this host; `GOOS=linux go vet` and `GOOS=windows go build` pass.

## Rollback

Revert the change. Leftover `taskman-requests` directories are inert.
