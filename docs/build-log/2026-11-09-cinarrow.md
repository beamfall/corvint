## V1-5196: FULL reasons in the log and a tallyable decision

What was wrong: `narrow.sh` wrote the FULL reason only to `GITHUB_STEP_SUMMARY`, a `full()`
fallback dropped the record, and no run artifact held a reason code, so FULL frequency by cause
could not be computed over run history.

Fix (CIN-V0-8421, CIN-V0-8422): `narrow.jq` builds its reasons as coded causes and records
`reasonCodes` parallel to `reasons`; `narrow.sh` prints every decision line to stdout as well as the
summary, a FULL one as `AFP-V0-098 shard N: FULL (REASON; ...); reason codes: CODE, ...`, and writes
`decision.json` (`corvint-pr-narrowing-decision/0`) beside the record for every decision, including
the four fallbacks (`decision-failed`, `record-unreadable`, `sidecar-unwritable`, `sidecar-mismatch`).
`ci.yml` uploads `decision.json` in the `ci-narrowing-N` and `ci-shard-plan` artifacts.
`full-reasons.sh N [EVENT]` tallies modes and codes over the last N runs with gh and jq. The
merge-queue path reaches the same `narrow.sh`, so `mq-narrow.sh` refusals log as `driver-reason`.

Tests: `TestCINV08421FullReasonIsLoggedAndRecorded_CINV08421` (decided FULL, several codes in order,
a dropped record, a failed decision, NARROWED, the merge-queue path) and
`TestCINV08422FullReasonsTally_CINV08422` (five fixture runs, the event filter, argument and
listing refusals) in `tools/ci-forward-row`.

## V1-5202: per-input classification of the guarded `.github/` inputs

What was wrong: any changed trusted narrowing input forced FULL, even one whose only consumers are
tests the selection already names.

Fix (CIN-V0-8423, CIN-V0-8424): `github-guard.sh` classifies each changed input as global (the
decision scripts, the verdict scripts and `names.sh`, `cishards`, `testconfine`, `actions`, every
guarded `ci.yml` section) or mapped to the test packages that read it (the row production and
reporting scripts to `tools/ci-forward-row`, `tiers.*` also to `tools/tiers-replay`, the two
workflows to `tools/capabilities-check`, `tools/ci-forward-row` and `tools/ci-reuse-plan`), and
prints `mapped` with `INPUT CONSUMER...` lines when only mapped inputs changed. `narrow.sh` then
narrows only when the selection within the universe holds every consumer, records the mapping as
`githubMapped`, and is otherwise FULL with `github-consumer-unselected` naming the omission; an
unmapped, renamed or non-ASCII input stays global. `tools/selection-baseline` applies the same rule.

Measured against the ticket's six baseline cases with the new guard: pr-11, pr-12, pr-13, pr-40 and
pr-42 change `ci.yml (go-product-shard)`, the test job; pr-12 and pr-42 also change `narrow.sh`;
pr-13 and pr-17 change `accept.sh` or `bar.jq`. Each is a global input the ticket itself names, so
all six stay FULL (`github-guard.sh` prints `1` for every one). Narrowing them would weaken the
guard; the acceptance criterion "the 6 baseline cases narrow" is therefore not met and is reported
as such in the handback. The mechanism narrows a change confined to any mapped input.

Tests: `TestCINV08423GuardClassifiesEveryInput_CINV08423` (every file of `.github/forward-rows`
and both workflows; consumers hold every declared reader of `.corvint/test-read-scopes.json`; an
unmapped file, a rename and a mixed change stay FULL), the mapped cases of
`TestAFPV02720GuardNamesOnlyTheNarrowingInputs_AFPV02720`,
`TestCINV08424NarrowShRequiresMappedConsumers_CINV08424` (real guard and git) and
`TestCINV08424MappedInputsNeedTheirConsumers_CINV08424` (`tools/selection-baseline`).
`tools/ci-forward-row` now declares `.corvint/test-read-scopes.json` and
`.corvint/unbounded-readers.json`, which the classification test reads.

## V1-5011: manifest producer stamp and the heavy.sh refusal

What was wrong: a `corvint-test-manifest/0` named no producer, so `script/heavy.sh --plan M` ran a
selection a stale installed corvint had computed.

Fix (STR-V0-8301, TSP-V0-8131): `sessiontest.Manifest` carries `producer` (`commit`, `commitState`)
from the binary's Go build stamp, the same information AFP-V0-846 judges; an unstamped binary
records none. `heavy.sh` checks `source.head` against HEAD and the producer against HEAD (fresh when
equal, or an ancestor with no non-test Go source, `go.mod` or `go.sum` difference) before `--plan`
prints or an admission admits anything, refusing `manifest-head`, `manifest-producer-missing`,
`manifest-producer-unverified` or `manifest-producer-stale` with a `fix:` line naming the rebuild
and the regenerate command.

Tests: `TestSTRV08301ManifestCarriesItsProducer_STRV08301` (internal/sessiontest),
`TestSTRV08301DryRunManifestNamesItsProducer_STRV08301` (cmd/corvint, a stubbed build stamp), and
the TSP-V0-8131 cases of `script/lane-scripts_test.sh` group `policy` (fresh, test-only ancestor,
stale, unknown, missing, another HEAD, for `--plan` and admission). The group's and
`tools/test-commands-check`'s hand-written manifests now carry a producer.

## V1-5028: unresolved go targets in test-read-scopes-check

What was wrong: `goBuildTargets` recorded nothing for a positional argument that is no literal, so
`go build -o ./out pkg` in a helper passed with `go.mod` as the only entry; `goListTargets` ignored
literal ranges and took a variable target for the package itself.

Fix (TSP-V0-8132): both return the unresolved arguments' source text; `checkFile` reports them as a
finding unless the package declares a whole top-level tree with its reason or
`.corvint/test-read-scope-literals.json` records `go-target:EXPR` for the package (an unused record
is stale). `go list` expands literal ranges and honours `-f`'s value; `go run` takes one target and
`go test` stops at `-args`. On this repository the rule found four sites: three temporary-path
builds (`cmd/corvint-analyzer-html-css`, `internal/sessiontest`, `tools/beamfall-shadow`), now
recorded, and `internal/analyzernativebridge`, whose candidate build passed a struct field; it now
spells the three executables through a literal range, whose closures its declaration already covers.

Tests: `TestTSPV08132UnresolvedGoTargetsAreFindings_TSPV08132` (nine cases); `make
test-read-scopes-check` passes on the repository.

## V1-5092: ci.yml steps under bash with pipefail

What was wrong: `ci.yml` set no `defaults.run.shell`, so steps ran under `bash -e` without
pipefail while the extract-and-run tests used pipefail.

Fix (CIN-V0-8425, CIN-V0-8426): `ci.yml` declares `defaults: run: shell: bash`. The pipeline audit
(87 pipelines) found two that read a file that may be absent (the advisory shard-balance `sed |
head` and the cost-drift `find | wc`), now guarded by a file test; the tests step already reads
`PIPESTATUS` under `set +e`, and `git archive | tar` pipelines now fail their step when `git
archive` fails, which is the intended behaviour. `internal/workflowshell.Argv` derives the step
shell from a workflow's text; the `ci.yml` extractors of `tools/ci-forward-row` (four sites) and
`tools/ci-reuse-plan` (five sites) use it, and
`TestCINV08425CIDeclaresPipefailShell_CINV08425` pins the declaration, the pipefail behaviour and
the absence of hard-coded shells. The hosted run of the changed workflow is `NOT_OBSERVED` here
(no push from this lane).
