## V1-2443: racy-window guard on coarse and network filesystems

No coarse or network filesystem could be mounted here: the lane runs in a container on btrfs, with
no `/dev/fuse`, no loop control and no user namespaces (`unshare -rm` is refused). The measurement
is therefore a model. A seam (`stampNow`, `stampTimes`) replaces the clock and the lstat time
reader with a filesystem whose times come from a server clock running behind the reader by a lag,
truncated to a granule.

Analysis: a capture is accepted only when every recorded time is older than now - 2 s. A same-size
in-place edit after the capture keeps the stamp only if it records the same granule. With the
reader's own clock, that edit is always at least 2 s past the recorded granule start, so a granule
of up to 2 s is safe. With a lag `s` and a granule `g`, it is unsafe exactly when `g + s > 2 s`.

`TestDCRV1845SkewedCoarseEditNeverServedStale` sweeps granules of 1 s and 2 s, lags of 0, 0.5, 1
and 3 s, and edit offsets every 100 ms.

- At BASE (seam only): 120 accepted captures, 70 served stale: 2 s granule with 0.5, 1 and 3 s
  lag (20 each), and 1 s granule with 3 s lag (10). With zero lag, nothing was served stale, so
  local FAT and HFS+ volumes were safe already.
- After the fix: 0 accepted captures, 0 served stale. A directory whose every recorded entry has
  whole-second ctime and mtime now makes the stamp unavailable, and so does an artifact file with
  both times whole seconds. Such checkouts take the Git path.
- `TestDCRV1845CoarseTimestampsLeaveNoStamp`: a fine-grained checkout and artifact file are still
  stamped. All-coarse times, or one coarse directory, leave no stamp.
- Limit: NFS client attribute caching (`actimeo`) can hide another client's edit from lstat. That
  is outside the stamp, as it is outside Git's own reads. Recorded, not fixed.

## V1-2240: untracked cache and fsmonitor for the isolated status (rejected)

hook-w13 rejected this on raw `git status` (see `2026-11-01-hook-w13.md`). This lane measured the
isolated read itself. Each run builds a private metadata directory: copies of config, HEAD and the
index (mtime kept), with `objects` and `refs` symlinked. It then runs the exact `gitstatus` prefix
(`--no-optional-locks`, `--git-dir=PRIVATE`, `core.hooksPath=/dev/null`, `core.fsmonitor=false`) and
the done-list arguments (`status --porcelain=v1 -z --no-renames --untracked-files=all
--ignore-submodules=dirty`).

The fixture is a synthetic repository with 3,000 tracked files, 700 modified and 767 untracked:
1,467 dirty paths. It ran on git 2.43.0, 12 CPUs, load 2.4 to 2.6. The five cases were
interleaved, n=31 each, two rounds; times in ms.

| UNTR extension | core.untrackedCache | p50 r1 / r2 | p95 r1 / r2 |
|---|---|---|---|
| absent | false | 8.0 / 7.1 | 9.4 / 8.0 |
| absent | true | 8.1 / 6.8 | 9.0 / 7.9 |
| present | false | 7.5 / 6.7 | 8.3 / 8.0 |
| present | true | 7.9 / 6.9 | 9.4 / 7.7 |
| present | unset (keep) | 7.9 / 6.9 | 9.3 / 7.9 |

The output was byte-identical in every case (sha256 prefix `d4008a5571d6`).

- Decision: REJECT. There is no measurable win. The private index copy is discarded after every
  read and `--no-optional-locks` forbids writing it, so a cache can never persist without a new
  write outside the admitted ledgers (invariant 4). Built-in fsmonitor has no Linux daemon, and
  any daemon breaks invariant 7.
- Implication: at 1,467 dirty paths the isolated status costs about 7-8 ms, so the ticket's
  200-370 ms hook cost at load 40 to 80 lies elsewhere in the hook (new hot spot below). Load 40
  to 80 was not reproduced: lanes may not start background load generators.

## V1-1148: tasks-scale gen (blocked, owner decision)

Before, at BASE: `gen --tickets 500` took 181.8 s (above). One `ticket create` at 500 tickets took
253.6 ms. Its CPU went to `transaction.loadTickets` decoding every ticket, `intent.LoadExpecting`
and `intent.WriteClosedIndex`. This confirms the cause recorded in `2026-10-31-tools-wsl.md` and
`2026-10-31-tools-r-w7.md`: each product write is O(tickets), so gen is O(tickets²).

- Fork, recorded: a linear gen needs either the cross-call intent cache that V1-0910 proposes
  (declined by decision 0549 F1; V1-0910 holds `owner-decision`), or a harness that writes ticket
  and receipt files directly. The direct-write harness would stop exercising the product writers
  that `gen` exists to measure. The scope note also keeps this lane out of `internal/tasks/store`,
  journal and wire, which tkp-u33 owns.
- The importer's bulk path was considered and rejected: it creates shadow IMPORT tickets, which
  are a different store shape.
- Nothing was built. Criterion 2 (cause recorded) was already on base; criterion 1 stays blocked.
