## 2026-09-27 V1-0427 V1-0428: two test races that failed the hosted rc.1 full gate

The owner-dispatched release-gate run 36338249213 on the `1.0.0-rc.1` candidate c9019c4b failed
`full-gate` on both hosted runners. Every other job passed. Neither failure is in the Core binary.

V1-0428, ubuntu-24.04, twice in two attempts.
`TestSelfuseSeparateGroupsCleanedBeforeFallback/flood` reported `separate group survived`. The
fake leader starts a `sleep` child in its own process group. It waits 60 ms, then floods stdout until
the output limit closes the pipe, and dies by SIGPIPE before its deferred kill runs. The orphaned
child is no longer reachable from the leader. So the benchmark cleanup
(`benchmarks/selfuse-batch/descendants_posix.go`) owns it only if a `/bin/ps` probe saw it first:
- the `start` snapshot, or
- a monitor tick every 250 ms.

Instrumented runs of the benchmark cleanup's `stop` show a zombie leader in every run on both
systems:
- On darwin, `/bin/ps` reads the process table late enough that the `start` snapshot always held the
  child. The test passed even with the tick raised to 10 s.
- In a linux `golang:1.27.1` container, the `start` snapshot was taken before the child existed, and
  the leader died before the first tick. The test failed in two of three runs.

The per-package gate ledger runs one package at a time on an idle runner, and that makes the linux
failure deterministic. In the CI shards, parallel packages slowed the fake enough for a tick to land.

The cleanup was not wrong. When no probe saw the child, it records the observation as
`NOT_OBSERVED: leader-exit-race` in the receipt. The test was wrong: it assumed the child was
observed. The fake now waits two monitor ticks before flooding, and the test timeout grows by four
ticks so that the timeout path cannot win. The comment on `descendantMonitorTick` claimed that the
stop snapshot made the tick matter only for a child that starts and exits between polls. It now
states that stop reaches descendants only through a live leader.

V1-0427, macos-15. `TestPinnedMetadataReaderDetectsParentReplacement/symlink` copied the fixture's
`.git` while Git's detached auto-maintenance, started by the fixture commit, removed
`objects/maintenance.lock`. This is the same class as V1-0351. The package's `testRun` prefix now
passes `-c maintenance.auto=false -c gc.auto=0`. The settings are not written to the fixture's
config, because the simple metadata reader accepts only a closed set of keys: writing them there
sent `TestPrivateStatusSimpleMetadataAndFallbacks` down the fallback path.

Evidence:
- linux container: the flood test passed ten of ten runs (`-count=10`), and both packages passed in
  full.
- darwin: the flood test passed five of five runs, the gitstatus tests ten of ten, and both
  packages passed in full.

Rollback: revert the change. The hosted linux full gate then fails again on the flood subtest, and
the macOS one can again race auto-maintenance.
