## Native Windows access

None of the native Windows runs these tickets ask for could be made from this lane. The WSL distro
has Windows interop off (`powershell.exe` exits `Invalid argument`). `192.168.4.128:22` is the
distro's own mirrored address and refuses connections. The Windows sshd answers on
`127.0.0.1:22`, but the distro holds no key for `russe` (`Permission denied (publickey,...)`). Every
native Windows result below is therefore `NOT_RUN`. Linux/WSL2 unit runs and `make windows-vet`
are the only evidence.

## V1-2487: platform-refused Git reads (PRS-V1-840)

- Decision: `procgroup` exports `ErrPlatformUnsupported`. Only the `process-platform-unsupported`
  `processError` matches it with `errors.Is`, and its text stays exactly
  `process-platform-unsupported`, so the `testplatform.PlatformRefusals` entry is unchanged. The sentinel lives in its own file, `internal/procgroup/platform.go`, so the many `process.go`
  line citations in other specs stay valid.
- Decision: appmap and appflows refuse with the gokernel code `process-platform-unsupported` and a
  message ending `: process-platform-unsupported`. That suffix is the form `SkipWindowsRefusal`
  matches. testsource keeps `tests-source-unavailable`, because `corvint tests --help` lists its
  refusal codes and a new code would change the help and catalog. Its message ends the same way
  and its `Error` now unwraps to the sentinel.
- Decision: each package's `git` reader checks the sentinel once, and an `orPlatform` guard (or an
  `errors.Is` check in appflows and testsource) keeps every resolver caller that rewraps the error
  from renaming it as `not a commit`, `not a Git worktree/checkout` or `has no HEAD commit`. Callers
  that only pass the error through, or that turn it into `FreshUnknown` or a rebuild, are left
  alone: they report uncertainty, not a wrong cause.
- Test seam: a package `runGit = procgroup.Run` variable, following `behaviorfalsify`'s
  `runProcessGroup`. `TestGitPlatformRefusalIsNotReportedAsARevisionDefect` in each package forces
  the refusal through it.

## V1-2488: Windows path logic

- ALREADY-DELIVERED on base under AFP-V0-415: items (1) projectpath, (2) gitstatus `.exe` fixtures,
  (3) specindex key, (4) flowdocs volume root, (7) liveverify/gotest fixtures and (9)
  behaviorfalsify (BBF-V0-215). The tests are listed in the AFP-V0-415 trace row. Item (8) was
  fixed in the V1-2441 PR.
- Delivered: item (6), lspstdio (AFP-V0-850). `parseContextParams` compared the URI path with
  native `filepath.Clean`. On Windows that rewrites every slash, so every editor context request
  failed as `invalid or truncated LSP frame`. A drive URI `/C:/x` also never related to a `C:\`
  root. The check now uses slash syntax, and `uriNativePath` drops the drive's leading slash on
  Windows only. POSIX behavior is unchanged.
- Item (5), analyzernativebridge `ERROR_BAD_LENGTH`: the failing code is the test-only Windows job
  object helper (`process_windows_test.go`), so the item belongs to the test-helper class
  (V1-2490). Its struct sizes match the Win64 ABI (64/144 bytes; `TestWindowsJobObjectABI`), so the
  root cause needs a native run. Not fixed.
- Acceptance criteria 2 and 3 are BLOCKED. AFP-V0-416 cites a per-package class table in the
  archived entry `2026-10-23-windows-production-path-logic`. That entry is not in this repository,
  and `raw.githubusercontent.com` returns 404 for it at the archive pin, so this lane could not
  verify that the table covers items (10) and (11). The Windows-host before/after rerun needs the
  host access described above.
