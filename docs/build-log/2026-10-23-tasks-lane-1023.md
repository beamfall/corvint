## V1-2352: null request pre-state on the read checkpoint (PSR-V0-203, CAL-V0-321, DELIVERED)

- Reproduction: `TestPSRV0203_CheckpointTailRefusesNullPreStateDuplicate` posts `r1`, derives a
  read checkpoint, removes the request file and re-posts `r1` (null pre-state). The complete
  audit refuses `JOURNAL_FORKED`; on the base the checkpoint read returned no error.
- Decision: the earlier lane (`2026-10-22-tasks-oc-1022.md`) named a request set or a
  no-false-negative filter. An exact set is 32 bytes per request, 67 MB at 2.1 M requests, past
  the 16 MiB bound. The read checkpoint now carries a Bloom filter (`requests: {bits, data}`,
  16 to 32 bits per request, 11 positions by double hashing of the path digest, about 0.05%
  false positives). A tail request whose path the filter may hold declines the route, and the
  complete audit classifies it. The key is optional in the codec because seal anchors and writer
  checkpoint headers embed it and must keep their bytes. The read route refuses a checkpoint
  without it, so a checkpoint from an earlier binary costs one complete audit until the next
  writer retains a new one.
- Writer-resumed derivation (CAL-V0-119) adds the writer checkpoint's delta and base request
  records. `TestCALV0321_CheckpointRequestFilter` checks that its bytes equal the
  complete-audit derivation.

## V1-2425: Linux pool runner identity from /proc (PSR-V0-204, DELIVERED)

- `poolRunnerIdentityContext` uses `supervisor.ProcessIdentity` on Linux as on Darwin.
  `BenchmarkPSRV0204_RunnerIdentity` (`-count=3`): before (bounded `ps` listing) 3,606,092,
  4,142,580 and 3,945,220 ns/op with `-benchtime 200x`; after 11,897, 8,976 and 9,465 ns/op with
  `-benchtime 2000x`. Host: linux/amd64, 4 vCPU Intel Xeon @ 2.10GHz, Go 1.27.2.
- Recovery compares a `linux:` record with btime tolerance of one second and an exact start tick.
  The V1-1091 residual names cross-process btime jitter, and pool recovery is cross-process: the
  writer records the identity, `pool recover` re-reads it. Without the tolerance a live runner
  could read as gone. The tolerance is scoped to pool runner records. The other V1-1091 call
  sites stay open.
- `PSRTestUnknownRunner` injected its failure only into the `ps` listing. Once identities came
  from the kernel, `TestPSRRequestConflictAndOrphan/live-unknown-gone` failed at line 618 on
  Linux. That is the same failure `2026-10-22-tasks-oc-1022.md` observed on macOS base, which
  has used the kernel read since PSR-V0-201. The seam now injects into the kernel read too, and
  the test passes on Linux. macOS: `NOT_RUN` (no macOS host).

## V1-2447: pools.json worst case past 1 MiB (BLOCKED, owner decision)

V1-2447 is not in the tracked `.taskman` store on base `77a49dfa`. `corvint-tasks ticket show`
reports it `NOT_OBSERVED`. It was worked from the orchestrator's statement.

Measured on base with a throwaway snapshot test (not committed). The state is codec-valid: 256
CLEANING entries, each with a pending retarget, a sweep owner, a 128-byte `runnerStarted`, a
maximum `configRef` and a source. It also has 256 REPORTED identities, 512 operation receipts,
512 slot entries and 512 waiters. All labels, request IDs and holders are at their maximum
lengths, and reasons are empty.

| Section | plain identifiers (B) | identifiers all `"` (B) |
| --- | --- | --- |
| entries | 602,009 | 712,857 |
| identities | 178,345 | 209,577 |
| operation receipts | 352,425 | 478,889 |
| slots | 256,164 | 349,860 |
| waiters (approx.) | 306,342 | 368,806 |
| whole state | 1,694,669 | 2,119,373 |

The PSR-V0-202 reasons add up to 256 x (68 + 2 x 224) more. The member-indexed sections alone
(entries, identities, receipts) reach about 1.40 MB with escaping. So no set of fresh-admission
bounds on free text alone brings the worst case to 1,048,576 bytes. That would need one of:

1. Raise `MaxPoolStateBytes` (for example 4 MiB) with a derived worst case. Older binaries then
   refuse a larger pools.json `LIMIT_EXCEEDED`, a compatibility boundary.
2. Keep 1 MiB and amend accepted bounds. That means fewer slots and waiters (PSR-V0-031,
   PSR-V0-131), one receipt per member (PSR-V0-196), and refusing escaping characters in
   pool-bound labels and request IDs. Each is a behavior change to an accepted requirement.

Both are owner calls. Nothing was changed for V1-2447. A write past the bound stays refused
`LIMIT_EXCEEDED` before any write (`PoolState.Encode` decodes its own bytes), as PSR-V0-202's
limit records.
