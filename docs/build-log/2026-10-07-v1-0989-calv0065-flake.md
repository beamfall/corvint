# 2026-10-07: CAL-V0-065 native fixture flake under load (V1-0989)

## Intent

Ticket V1-0989 records that `TestCALV0065_NativeFixture` (`internal/tasks/cli`) fails
intermittently on a loaded host. It is one of the load-sensitive failures gathered under the
test-reliability umbrella V1-0849. The change finds the cause, proves it deterministically and
fixes it. It adds proposed `CAL-V0-187` to `docs/specs/corvint-tasks-agent-leases-v0.md`, pending
owner acceptance.

## Reproduction

The host is a 12-core Darwin machine, at load average 46 to 62 from parallel lanes. The base is
`0b5096ca`.

- `go test -count=50 -run TestCALV0065_NativeFixture ./internal/tasks/cli` gave 21 failures and
  14 passes in the 35 iterations that finished before the default 10-minute timeout.
- Every failure was the same refusal: the claim, which excludes `review` and `a`, was refused
  `RESOURCE_COLLISION` "no eligible free member; occupied and quarantined members unavailable".
- A failure-only diagnostic in the test prints `pools.json`. In all 21 failures member `b` was
  `QUARANTINED`, with reason `EXIT_ZERO; operator safe-reuse confirmation required`.
- So the health command (`/usr/bin/touch`) exited zero, but its observation did not pass.
- The original lane failure log carries the same message.

Ruled out:

- **The 3-second health timeout.** A timeout records class `TIMEOUT`, not `EXIT_ZERO`.
- **Wait-delay and pipe-drain uncertainty.** Each records class `UNKNOWN`.
- **Lease clocks.** The refusal comes from member eligibility, not lease time.
- **Leaked claims or a resource shared with another test.** Every test uses its own `TempRepo`
  state directory, and the occupant was this test's own quarantined member.

## Root cause

An observation passes only when the class is `EXIT_ZERO` and the cleanup is clean. After the
command exits, `executePoolGuarded` proves its owned process group is empty with `poolGroupLive`.
That function lists the whole process table with `/bin/ps -axo pgid=,stat=` under a fixed 1-second
bound (`poolProbe`). A listing that errors or overruns returns "unproved", so `clean=false`.

Measured on the same host and load, the listing took 0.72 to 1.65 s, with 8 of 15 samples over
1 s; an earlier set reached 2.43 s. The single-process `ps -p PID -o lstart=` stayed at or below
0.33 s.

The refusal is the specified fail-closed behaviour: CAL-V0-033 refuses admission on unproved
cleanup, and PSR-V0-010 makes a blocked probe UNKNOWN. The defect is that the proof could not be
obtained for a group that was already empty, because the only proof was a whole-table listing.

## Deterministic proof

`TestCALV0187_GroupListingOverrun` (`internal/tasks/store`) injects a `poolProbe` whose
`-axo` listing always returns `context.DeadlineExceeded`, the same result as the measured overrun.
It counts listings.

- **Retired group.** `/usr/bin/true` must observe `EXIT_ZERO`, clean, with no listing. The test
  checks both `executePool` and `executePoolCaptured`.
- **Control.** A command that leaves a detached `sleep` in its group must still be unclean and must
  have attempted a listing.

Results:

- On base code (applied with `go test -overlay` so the tree stayed fixed), the test failed 10 of
  10 runs with `retired group unproved: EXIT_ZERO clean=false listings=1`. That is exactly the
  fixture's quarantined observation.
- With the fix it passed 30 of 30 runs.

No sleep or timing assumption is involved.

## Fix (product)

`poolGroupLiveContext` first asks the kernel with `kill(-group, 0)`.

- `ESRCH` proves the group has no member, not even a zombie, and no listing runs.
- Any other answer falls back to the unchanged bounded listing. This includes Darwin's `EPERM`
  for a zombie-only group, recorded in the V1-0771 drain amendment beside CAL-V0-086, and success.
- A failed or overrun listing still refuses admission.
- The check is guarded to groups above 1, so it never broadcasts.

The same precedent is `groupExists` in `supervisor/ownership_unix.go`. No wire profile, codec,
request preimage, receipt or replay rule changes. Rollback removes the seven-line check.

The test-side change only adds the `pools.json` dump to the fixture's claim failure message.

## Remaining load-sensitive bounds (not fixed here)

These stay under V1-0849:

- **Runner identity.** `poolRunnerIdentity` (`ps -p PID -o lstart=`, 1 s bound) can still fail a
  health preparation on a heavily loaded host. A ps-free runner identity is a follow-up for the
  orchestrator to file under V1-0849. It was not filed from this isolated lane.
- **Fixture timeout.** The fixture's 3-second health timeout is unchanged.
- **Live-group listings.** Some store tests deliberately keep a live group, or a pid-1 probe, on
  the listing path, and they fail under the same load with or without this change. With the fix
  reverted (count 10, load about 54), each of these failed 6 of 10 runs:
  `TestPSRBoundedProbes/actual-blocked-probe-process`, `TestPoolProcessDescendants` and
  `TestPSRFirstCleanupProbeFailureRetiresChild`.
- **Probe errors.** `executePoolGuarded` still does not kill the group when the listing errors.
  That is a separate hardening question.
