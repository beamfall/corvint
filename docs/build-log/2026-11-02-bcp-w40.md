# 2026-11-02 bcp-w40: gated batch-close writes on the writer checkpoint (V1-4315)

Lane bcp-w40 (store-performance), host wsl-lanes, model fable-5.1 high. BASE
`8e84e2e5ba7b321ec184edacce512dab0ab416e4` (origin/main). Ticket V1-4315 (P1, v1-0, optimizations):
`corvint-tasks ticket batch-close` paid one full-store administrative write for every gated step of
every row. Requirements `TCX-V0-970` to `TCX-V0-976` in

## Where the time went at BASE

Sampled on this host (perf, user space only; kernel sampling is not permitted here) on a 4,000-ticket,
19,200-receipt store, three gated rows: every gated step (claim, submit, gate run, complete) took the
complete lease route, so each step ran the complete-history audit over 19,200 receipts, built the
complete inventory (`checkCapacity`, `MeasureManifestEncoding`, `SortFiles`), and decoded every ticket
record (`transaction.loadTickets` → `ticket.Decode` → `FileDigest` re-encode: 44% of CPU after the
first change). Measured by hand at BASE: about 12.6 s per row at load 4, 22.7 s per row at load 14.

## Design decision

Route, not model: the gate verbs join the writer-checkpoint route and reuse what that route already
has, instead of a new incremental capacity measure. In order of effect:

1. `TCX-V0-970`: `SUBMIT`, `GATE_RUN` and `COMPLETE` are served by the CAL-V0-116 writer route (as
   `POOL_CONFIRM_SAFE` was by CAL-V0-205), so a step audits the tail after the writer checkpoint
   instead of the whole history. Same bytes and report as the complete route (parity tests).
2. `TCX-V0-971`: the lease writer route hands the model the derived closed-ticket index exactly as the
   mutation writer does (TCX-V0-846), so an unchanged ticket is held as its summary and not decoded;
   `TCX-V0-972`: `ticket batch-close` refreshes that index once before its first gated row, so a cold
   store pays the full decode once per command instead of once per step.
3. `TCX-V0-973`: the gate run's pre-read resumes the read-side audit from the read checkpoint (else the
   writer checkpoint) instead of the complete audit; the write still rechecks everything under the lock.
4. `TCX-V0-974`: the intent-tree capture (read, stat, hash) and the audit's directory listing run on up
   to eight workers with serial semantics, and the lease route captures the tree once under the lock
   and hands it to its audit as the mutation writer takes the CLI preload (LGL-V0-845); the pre-effect
   recheck still reads and hashes every file again.
5. `TCX-V0-975`: the claim's know-how delivery read loads as the CLI preload loads (index-held records
   undecoded, everything else decoded and checked, so KHN-V0-014 still reports an unreadable inventory)
   and materializes only the claimed ticket and the records whose bytes carry `"knowHow":`.
6. `TCX-V0-976`: `archive.EntryCost` is memoized by path and size (pure), bounded, refusals never cached.

Not done, on purpose: no collapse of a row's steps into fewer receipts (receipts and journal stay
byte-identical with the complete route); no stat-key trust on the write path (TCX-V0-981 stays a
read-path rule); no change to any model, refusal or wire result. Fail-closed is unchanged: a tampered
or stale ticket projection is refused by the writer audit's projection comparison or the model's
projection check with or without an index, on both routes, and nothing is written
(`TestTCXV0970_TamperedProjectionRefusesGateWrite`; `TestCALV0070_MutateRefusesMappedWriteAfterMergedAudit`
and the batch-close refusal and rerun tests still pass).

## Slow spots at the initial delivery (superseded in the AC2 continuation)

- Every lease write captures (reads and hashes) the whole intent tree twice (audit preload, pre-effect
  recheck) and lists it once more; the gate run's pre-read adds a capture and a listing. About 100 to
  150 ms per write at 4k tickets on this host, the whole of the AC2 gap.
- `NewSummarizedInventory` / `summarizedCost` rebuild the inventory map and sort every entry per write
  (the entry-cost memo removes only the measure); `indexedTicket` hashes every canonical ticket per
  write (parallel, about 24 ms CPU at 4k) although the audit already holds the digests.
- `cli.withStore` planning (`batchHits`, `closeoutIndex` regexps) costs 0.5 to 1.3 s per batch-close
  command at 4k to 8k tickets, once per command.
- The first `WriteClosedIndex` of a cold store decodes every ticket (about 0.35 s at 4k, 0.7 s at 8k).
- The CLI refreshes the closed index only after a mutating command ends, so any other long multi-write
  command (dispatch, programs) runs its early writes without it, as batch-close did before TCX-V0-972.
- `git worktree add` and remove per gated row: 80 to 150 ms.
- The baseline's own cost is dominated by the complete audit over the receipt history per step
  (about 15 s per row at 19,200 receipts), which every verb still on the complete route pays.

## AC2 continuation: command-scoped content reuse (TCX-V0-977..979)

The earlier AC2 verdict and "not fixed" list above describe the first lane delivery, not this
continuation. The owner explicitly authorized reducing redundant captures while preserving the
pre-effect content check. The new requirements are in the same closed-ticket-index spec.

The batch command owns one in-memory capture and one summarized inventory. Each capture still
lists the bounded closed intent layout and stats every entry through confined descriptors. On
Linux, content reuse requires identical device/inode, mode, size, nanosecond mtime AND ctime;
ctime must predate the retained capture's **start** by more than two seconds and have nonzero
nanoseconds. Checking age only at reuse would be wrong: an originally racy stamp must not become
trusted merely by waiting. Changed/recent entries are read and hashed; other platforms always
read and hash. The cached capture is never the persisted closed index's mtime-only key. The
pre-effect binding independently repeats this validation and compares the current head/tree to
the audit, under the same held writer lock. Only that lock-held capture's listing and file metadata
serve its audit/inventory; external preloads and unlocked gate pre-reads keep independent audit
listings. Audit-computed digests accompany the same immutable canonical bytes into the model.
The summarized inventory compares every current entry, validates/recharges changes, and rebuilds
when the audited checkpoint prefix, store, directory set or summary changes. Failure discards it.
No persistent format, receipt count, lifecycle step or authority is changed. Rollback is to remove
the command's WithBatchWrites opt-in; full capture/rebuild paths remain available.

Adversarial refusal case list (docs/LANE-ORCHESTRATION.md §9):

| Category | Evidence / boundary |
| --- | --- |
| Malformed input | `TestTCXV0977_CaptureLayoutChanges` rejects unexpected names; `TestTCXV0979_IncrementalInventoryMatchesRebuild` compares duplicate, malformed-digest, unknown-path, missing-parent, overlapping-elided and oversized entries with fresh construction. |
| Aliasing | `TestTCXV0977_ConcurrentTamperBetweenWritesRefused` covers inode replacement; root-confined capture retains its existing symlink/layout refusals. |
| Spread / variadic arguments | Not applicable: no command parser or argument expansion changes; fixed typed capture/inventory inputs. |
| Quoting / escaping | Not applicable: no shell interpolation, path parser or wire encoding changes. |
| Historical versus current reads | Cache stores one command's native worktree bytes, never Git history; checkpoint identity changes rebuild. All observations revalidate the current layout and stamps. |
| Absent / unreadable / unindexed | Deletion and recovery after a refused capture in `TestTCXV0977_CaptureLayoutChanges`; no index falls back to decoding; unsupported stamps/platforms fall back to full bytes. |
| Concurrency overlap | `TestTCXV0977_ConcurrentTamperBetweenWritesRefused` uses a peer writer preserving size/mtime; `TestTCXV0977_PreEffectTamperRefused` edits at the model/pre-effect boundary. Both require no publication. `TestTCXV0977_CaptureReusesOnlyStableContent` proves actual stable-content reuse, rejection of an originally recent capture after waiting, and fresh hashing after restored-mtime tampering. |
