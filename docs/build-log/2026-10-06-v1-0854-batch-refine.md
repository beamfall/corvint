# 2026-10-06: V1-0854 chunked batch ticket refine

## Intent

Ticket V1-0854 ([issue 625](https://github.com/beamfall/corvint/issues/625)): refining about 110
tickets took 110 `ticket refine` processes, each taking the writer lock, running the guards, §5.2
redo and a store audit, while claims and heartbeats queued behind them. The issue asks for a batch
refine that validates everything first, applies in bounded chunks that release the lock, keeps
per-entry CAS and receipts, and replays idempotently. The governing contract is the new
requirement `CAL-V0-106` in `docs/specs/corvint-tasks-agent-leases-v0.md` (V1-0854 batch refine
amendment).

## Change

- **Store:** `Mutate` is split after the lock, session, guards and redo into `mutateLocked`, so
  single-mutation behaviour is unchanged. The new `store.MutateBatch` decodes every envelope and
  checks the actor before any lock. It then applies the envelopes in chunks. A chunk is bounded by
  `BatchChunkEntries` = 8 entries or `BatchChunkHold` = 2 s of lock hold, and its first entry
  always runs. Each chunk takes the lock, runs the guards and redo once, and calls `mutateLocked`
  per entry. Between chunks the lock is released and the batch waits `BatchYield` = 5 lock polls.
  A refusal continues the batch; an error stops it. A test-only `WithBatchYieldHook` exposes the
  point between chunks.
- **CLI:** `ticket refine --batch --request-id ID (--payload-stdin | --payload JSON)`. The input
  is a canonical array of `{target, expectedRevision, payload}`, at most 1000 entries and 8 MiB.
  Each entry is validated before any lock: closed shape, canonical REFINE payload, a target that
  exists, no duplicate target, and an envelope that decodes. Entry `i` uses request ID `ID/i` and
  the batch's one `issuedAt`. The result carries per-entry outcomes, receipts and revisions, plus
  counts. `ticket refine --help` and `docs/TASKS-EXTERNAL-AGENTS.md` document the form.

## Decisions

- **Replay:** follows the existing TM-V0-006 request-ID and digest replay per entry. The request
  digest covers `issuedAt`, so all entries share one `issuedAt`, and a retry must pass the value
  the first result reports. The prompt's "CAL-V0-065" reference does not match: CAL-V0-065 is pool
  exclusions.
- **Time:** each entry samples the time again from the command clock (`recordedAt`). A fixed
  `now` would make an entry after a concurrent claim look clock-backward.
- **Lock fairness:** the lock is a polling flock with no fairness. The yield after release lets
  polling waiters win; it is not a guarantee.
- **Not atomic:** a stale entry refuses alone and the batch continues, as the issue asks.
- **Requirement ID:** `CAL-V0-106`, not the next free ID 104, because concurrent lanes for
  issues 622 and 623 already use 104 and 105 in the same spec. Renumber at integration if needed.

## Not run

Full package suites, `go test ./...` and `make gate` (a release-candidate gate is running on this
host). Also not run: a live 110-ticket timing measurement, so the throughput gain is an inference,
not a measurement (each entry still audits the store); the dogfood CEM; and independent review.

## Rollback

Revert the commit. This removes `--batch`, `store.MutateBatch` and the `mutateLocked` split.
Batch entries are ordinary REFINE receipts, so no store or journal state depends on the batch
form.
