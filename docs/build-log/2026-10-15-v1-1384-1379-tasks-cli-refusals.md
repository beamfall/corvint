# V1-1384 and V1-1379: corvint-tasks CLI refusals that name their cause

Date: 2026-10-15
Tickets: V1-1384 (suspected defect), V1-1379
Requirements: CAL-V0-250 (`docs/specs/corvint-tasks-agent-leases-v0.md`), CTS-V0-010
(`docs/specs/corvint-tasks-store-init-v0.md`), both new and accepted under the owner's standing
auto-accept of lane requirements (2026-10-11). No accepted requirement was amended.

## V1-1384: same request ID, byte-identical payload, refused REQUEST_ID_CONFLICT

Reproduced on a fixture store (`TestCALV0250_DefaultedIssuedAtRetryNamesTheDifference` against the
unchanged CLI): `ticket create --request-id R --payload-stdin` without `--issued-at`, then the
identical command in a later wall-clock second, returns `REFUSED` `REQUEST_ID_CONFLICT` with only
"different original request" and no ticket ID.

Cause (confirmed from source, not actor or cwd): the CLI defaults `issuedAt` to the current second
and writes it into the mutation envelope, whose SHA-256 is the TM-V0-006 request digest. A retry in a
later second therefore carries different envelope bytes. This is the documented contract (the
operator-notes spec says a retry passes `--issued-at`; batch replay CAL-V0-106 likewise), so the
conflict itself is correct and stays.

Decision: keep the refusal and make it name the differing input (the ticket's second acceptance
option) rather than auto-replaying. Replaying would mean the CLI synthesizes the original `issuedAt`
into a write the caller did not specify, contradicting the accepted "do not synthesize a new
issuedAt into replay bytes" rule; it would need an owner decision. The journal keeps only the
original digest, not the envelope, so the diagnosis is digest-verified: the CLI rebuilds this
invocation's envelope with the recorded ticket's `createdAt` / `updatedAt` (and up to two seconds
earlier, since the writer clock may tick past the CLI's second) and names `issuedAt` as the only
difference, with the original value, ticket and replaying retry, only when a rebuilt digest equals
the recorded one. Any other mismatch gets the generic list of digest inputs; a changed payload is
never attributed to `issuedAt`. The diagnosis is a read after the refused write and adds no wire
code, result field or format. `docs/TASKS-EXTERNAL-AGENTS.md` now advises a fixed `--issued-at`.

Residual: the first successful result does not report its `issuedAt`, so a caller that loses it and
whose ticket was later updated (createdAt and updatedAt both moved past the defaulted second)
gets only the generic text. Reporting `issuedAt` in the mutation result item would be a result-shape
change and is left for a separate ticket.

## V1-1379: plain clone reports a newer ticket as nonexistent

Cause (confirmed): `.git/taskman` (the journal) is never committed, so a plain clone has none, and
`ticket show` takes the CTS-V0-002 journal-absent path that answers from the checkout's `.taskman`
projection. A ticket created after the last committed snapshot was refused "does not exist in this
queue".

Choice: an accurate refusal, not a read of the primary store. A plain clone has no recorded link to
the primary checkout; reading it would need a new out-of-repository authority input (an environment
variable or flag naming another store), which CTS-V0-002 lists as a non-goal (journal-optional reads
beyond the four verbs) and which could silently read the wrong store. The refusal is smaller and
fails closed: same `REFUSED` outcome, no code, no item, `snapshot: null`, the existing journal-absent
warning, plus one warning naming the ticket, the intent tree SHA-256, the absent journal path, that
the ticket is `NOT_OBSERVED` in this checkout rather than proven absent, and to read it from the
checkout whose `.git` holds the journal. A journal-backed miss keeps its wording. `docs/DOGFOOD.md`
states how a lane clone reads its own ticket.
