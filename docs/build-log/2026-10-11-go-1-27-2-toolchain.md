## Structural tuple re-qualification at go1.27.2 (V1-1240, CEM-V1-050)

Codex review P1 found the gap: the native `internal/cem/verify/stable.go` and the portable
`interop/cem01-go` (`cem.go` twice, `stable_repository.go`) accepted only `go1.27.1`. So every
pinned go1.27.2 build refused structural mechanical proof with `unsupported-structural-runtime`
(exit 2). The tuple guards `go/format.Source`, `go/parser.ParseFile(ParseComments)`,
`go/scanner` and `go/ast`/`go/token`, through `scanGoTokens`, `parseGoFile` and the rename, move,
import-reorder and formatter-only predicates. It was re-qualified on darwin/arm64 against the
official go1.27.1 toolchain archive and Homebrew go1.27.2. Each go1.27.1 run used
`GOTOOLCHAIN=local` in a scratch worktree whose `go` directive alone was lowered.

- Standard library source. The `go list -deps go/format go/parser go/scanner go/ast go/token`
  closure has 70 packages. 66 are byte-identical. The other four differ only in
  `internal/godebugs/table.go`, `runtime` (`iface.go`, `netpoll_epoll.go`, Windows and iOS files),
  `internal/poll/fd_windows.go` and `os` (Windows and `root_*` files). The full go/ast, go/format,
  go/parser, go/printer, go/scanner, go/token, go/build/constraint and cmd/gofmt trees are
  byte-identical.
- Behaviour corpus. A scratch harness (never committed) ran over all 3745 tracked `.go` files of
  `8410da997c4a`, frozen with `git archive`. For each file it recorded:
  - the digests of `format.Source` and its error;
  - the `scanGoTokens` stream;
  - an `ast.Fprint` dump;
  - the `go/printer` output;
  - the `parseGoFile` error;
  - the same for the formatted output, plus all four predicates in both directions.

  It also recorded the 12x12 `testdata/structural` fixture matrix under all four predicates. The
  output was 3212820 bytes. It was byte-identical between go1.27.1 and go1.27.2 (sha256
  `0a4a997d…cbeb125`), and a repeat go1.27.1 run was also identical.

  Two artifacts surfaced in a first run, and both were fixed in the harness:
  - `ast.Fprint` iterates `Scope.Objects` maps in random order (`go/ast/print.go`), so the dump
    now filters `Scope`;
  - one corpus file was edited between the two runs, so the corpus is now a frozen extract.

  No format, token, printer, parse or predicate output ever differed for identical input.
- S0E results. With the frozen-tuple gate neutralised in scratch copies of the tests, every result
  was dumped under both toolchains. After the only substitution, `runtime.goVersion`, the outputs
  were byte-identical:
  - native: 56 public cases plus the linked control, 57 results, normalised sha256
    `20dc6ad0…bd41263`;
  - interop: full results, linked control, 4 ledgers and 29 envelope cells, 88 results with 84
    goVersion substitutions, normalised sha256 `6362aa11…2def17c`.

Admission: `structuralTuples = {go1.27.1, go1.27.2}` in both implementations. Every other release
still refuses. The new sealed packet `protocol/cem-1.0/structural-tuples/go1.27.2/` contains:
- `TUPLE.json`, which records:
  - the S0E manifest (`21655c5d…`) and the `FULL-RESULT-CASES.json` and envelope-cell file digests;
  - the single substitution `expectedResult.runtime.goVersion` `go1.27.1`→`go1.27.2`;
  - the evidence above;
  - `EXPERIMENTAL_TUPLE_PENDING_FULL_CORPUS`;
- `manifest.json`, which seals `TUPLE.json`.

The S0E packet and the go1.27.1 evidence are unchanged. In both test suites the tests now bind the
running toolchain through that packet:
- native `s0eBindRuntime`;
- interop `s0eRequireBoundTuple` with `s0eExpect`.

A tuple with no sealed binding is still NOT_RUN. `TestCEMV1050StructuralTupleAdmission` (native and
interop) checks three things: the admitted set, that each admitted tuple other than go1.27.1 binds
the S0E packet to an admitted predecessor, and that `go1.27.3` binds nothing.

## Shard cost and slice provenance (V1-1241)

`.github/cishards` `SourceGoVersions` admits `go1.27.1` and `go1.27.2` for `Costs` and
`SliceFileUsable` (`AFP-V0-022`, `AFP-V0-041` (3) amended). On go1.27.2 the writers had refused at
`tools/ci-shard-costs/main.go` and `tools/ci-test-slices/main.go`. They now record the toolchain
they run under, and the retained go1.27.1 tables stay valid. `TestAFPSourceGoVersionsAdmitted`
checks the admitted set. `TestAFPV0022RefreshRecordsTheSourceToolchain` and
`TestAFPV0041GenerateRecordsTheSourceToolchain` show that refresh and generate succeed and record
`go1.27.1` and `go1.27.2`, and that they refuse `go1.27.99` without writing. The tables are not
regenerated: their inputs are hosted CI `go test -json` shard logs, none is committed or available
locally, and fetching one would need network or a workflow dispatch.
