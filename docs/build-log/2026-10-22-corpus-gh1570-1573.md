## Decisions

- #1570 part 2 is delivered as `DCP-V1-332`, an optional caller revision on every read (MCP
  `caller_revision`, CLI `--caller-revision`, HTTP request `caller_revision`). The trust envelope
  relates it to the corpus source revision as `equal`, `descendant`, `ancestor`, `diverged` or
  `unknown`, with a fixed reason. Readers that hold a checkout (the CLI and the corpus MCP bridge,
  both through `QueryLive`) decide ancestry with a new `gitauth.Repository.IsAncestor` (`git
  merge-base --is-ancestor`, which treats exit 1 as false). A shallow marker or an absent object is
  `repository-object-unavailable`, so the answer is `unknown`: truncated history cannot prove
  divergence. The static reader and the HTTP companion have no repository. They answer `equal` for
  the identical string and `unknown` otherwise, and never guess. When the field is absent, the
  envelope bytes are unchanged.
- Supplied text is marked per visible result in `text_origins` (`DCP-V1-322`). Native records are
  never listed, so existing native receipts keep their bytes.
- The coverage-ledger, flow-completeness and unresolved-concept families are closed claim details
  (`DCP-V1-324..326`). `docs_gaps` serves them as claims with their details, after the supplied
  gaps, rather than as gap records, because "known but not placed" is not a gap. They never derive
  readiness, and they no longer count toward `subjects_with_claims`.
- Search ranking (`DCP-V1-331`) is binary-term-frequency BM25 with field weights 3 (ID or name)
  and 1 (claim text). Terms are summed in sorted order, so the float score is deterministic; ID
  order breaks only exact ties. Claim hits (`DCP-V1-328`) share the same score scale, with the
  inverse document frequency taken over claims. The search `kind` filter applies to subject
  kinds, and a claim is kept when its subject's kind is kept.
- An alternate id resolves only when no record has that ID and exactly one subject declares it
  (`DCP-V1-330`). Ambiguity is refused at import within one provider, and across providers it
  resolves to nothing, so the reader's existing typed miss stands.

## Independent review findings (Codex, PR #1580)

All four hypotheses held when checked against the code. Each was fixed with a regression test,
and each test was checked by removing its fix and watching the test fail.

1. An alias could shadow a join record. Before this fix, `validateRecords` ran before the
   test-knowledge, flow-relation and claim-audit joins, before stability evidence, and before
   legacy cases were added. An alias equal to one of those IDs was therefore admitted, and the
   alias resolution then replaced the record. The fix adds `validateAlternateIDsAfterJoins`,
   which refuses such an alias at build. Resolution now also applies an alias only when `get`
   finds no record. `TestDCPV1329AliasCannotShadowJoinRecords` failed without the fix, both at
   build and at read time.
2. A flow-completeness flag without `value`, or with `"value": null`, decoded to `false` and was
   admitted. `CompletenessFlag.Value` is now `*bool`, and nil is refused.
   `TestDCPV1324To326CoverageDetailShapes` gains cases for an omitted and a null value.
3. With `include: ["claims"]`, the subject and claim families computed separate exact bonuses. On
   skewed document frequencies, a partial claim hit could therefore outrank an exact subject name.
   Both families now share one bonus: each term's largest possible contribution, taken over both
   families. `TestDCPV1331ExactBonusAcrossFamilies` failed without the fix.
4. MCP `docs_search` passed an unknown `include` value to the reader, so the call returned a
   `corpus-refused` tool failure instead of `invalid-arguments`. The bridge now refuses any
   `include` other than `["claims"]` itself. `TestDCPV1328And331SearchArguments` gains the cases.

## Residuals

- The HTTP companion and static index reader always report `unknown` for a caller revision other
  than the source revision. A shallow clone reports `unknown` even when Git could answer some
  cases. `equal` is decided by string equality, without Git.
- The BM25 weights are fixed constants. They are not tuned against the recorded "which flow
  covers X" questions in #1579, and no retrieval evaluation was rerun.
