# CI narrowing: the `.github/` guard names its inputs, and a narrowed run sizes its shard matrix

Date: 2026-11-06 (lane selgh). Tickets: V1-4930 (P1, the `.github/` guard), V1-4934 (P1, the shard
matrix). Requirements: AFP-V0-2720 to AFP-V0-2725 in `docs/specs/affected-plan-selection-v0.md`.
Base: `55a87ca885ae429345832b68b34f2a7c686cf792` (the head of PR #123, stacked on `origin/main`).
Owner goal: every local and CI run executes only the tests the change can affect, and never fewer.
The selection audit (`2026-11-06-selection-audit`) found no under-selection and two large sources
of over-selection in CI; this entry fixes both.

## V1-4930: only a trusted narrowing input under `.github/` forces FULL

Before, `narrow.sh` ran `git diff --quiet ... -- .github/` and any `.github/` change recorded FULL
(AFP-V0-098, AFP-V0-933). PR #120 (run 42294716102) changed `.github/workflows/greptile-gate.yml`;
PR #111 (run 42233489680) changed `.github/ci-cadence/*`, `go-macos.yml`, `release-gates.yml` and
the cadence jobs of `ci.yml`. Both narrowed in the driver and the shadow (97 over 43 and 89 over 48
packages, `omitted: []`) and both ran the whole suite: about 18,000 package-seconds each.

The guard exists because a pull request can edit its own narrowing. The decision keeps FULL for
exactly the paths the trusted narrowing reads or executes, and lets every other `.github/` path
narrow. `github-guard.sh` (AFP-V0-2720), beside `narrow.sh` in the trusted checkout, lists them:
`.github/forward-rows`, `.github/cishards`, `.github/testconfine`, `.github/actions`, the two
verdict workflows (`ci-forward-bar.yml`, `ci-control-plane.yml`), and the narrowing jobs of
`ci.yml` plus its top-level text (AFP-V0-2721: `docs-plan`, `narrowing-verdict`, `shard-plan`,
`go-product-shard`, `ci-tested-tree-record`, `ci-narrowed-tree-record`, `go-product`, compared
block by block from `git show` of both revisions). The list is the trusted copy's; the tested tree's
copy is never read. The diff is `--name-only -z --no-renames` over those pathspecs, so a non-ASCII
path is named raw (the AFP-V0-933 quoting bug cannot recur) and a rename shows both sides. Anything
the compare cannot attribute is FULL: a YAML anchor, a `jobs:` key that is not a block mapping, a
job key moved out of shape, a deleted `ci.yml`, an unreadable base. The record names the changed
inputs (`githubInputs`) and the reason reads "the change touches .github/ narrowing inputs
(AFP-V0-2720): ...".

Rejected: guarding whole `ci.yml`. It would have kept PR #111 FULL (its `ci.yml` hunks were the
`cadence-plan` job and two doc-gate conditions) and every PR that adds a job. Rejected: a path list
in a data file beside the script; the list is three lines of the script and the script is itself an
input, so a separate file bought nothing.

## V1-4934: the shard matrix is sized from the selected cost

A narrowed pull request started all 16 `go-product-shard` jobs. On run 42212454082 (PR #106,
NARROWED, 101 selected packages) 10 of the 16 shards ran one package; a one-package shard
(shard 7) took 241 s of which 134 s were its tests, so about 107 s was fixed setup (checkout 8 s,
setup-go 10 s, the pinned tool build 46 s, the shadow and gate 15 s, uploads). The audit put the
waste at about 2,000 to 2,800 runner-seconds per narrowed run.

Design. A `shard-plan` job (AFP-V0-2724) runs after `narrowing-verdict` and `docs-plan`, only for
a same-repository pull request with narrowing on and a MET verdict, builds the same pinned tools a
shard builds and runs the trusted `shard-plan.sh` from the `CORVINT_PR_TOOL_SOURCE` checkout. That
script runs `narrow.sh` once as shard 0 of 16 with every input a shard's gate gets, and on a
NARROWED record sizes the recorded selection with `ci-shards --size-budget-ms 400000 --min-shards 2
--parallel 4` (AFP-V0-2723: the fewest shards whose balanced placement keeps every shard's
predicted wall time within 400 s, or within the longest unsplit unit, never fewer than 2). It writes
`count` and `matrix`; `go-product-shard` takes `fromJSON(needs.shard-plan.outputs.matrix || '[0..15]')`.
Everything downstream already used `strategy.job-total`, so partitions, placements, records and
coverage markers name the sized count; `go-product`'s AFP-V0-591 guard and `ci-narrowed-tree-record`
read the same `count`. The guarantees are unchanged: each shard still runs its own gate and, on
FULL, its complete-universe partition over the sized matrix (slower, never smaller); the superset
rule is the shards'; a `merge_group` entry and a `main` push keep 16. The narrowing pins moved to
the workflow `env` so both jobs read the same values.

Consumers that assumed 16 (AFP-V0-2725): `row.jq` now admits the selection run's own count when a
record with that count says NARROWED, so a sized run's queue row stays a real row (its pull-request
row is NARROWED as before) and the AFP-V0-030 kill switch sees no INCOMPLETE from sizing;
`tools/ci-reuse-plan` admits a narrowed record of any count whose every shard job of that count
passed, so the AFP-V0-734 reuse of a sized run still works; the docs-plan REUSE check accepts the
record's count for a NARROWED scope. `ci-shard-cost-drift` abstains on a sized run as it does on
every selected run; `ci-tested-tree-record` needs all sixteen `full<index>` outputs, so a sized run
never records a full tree.

Rejected: keeping 16 jobs and exiting empty shards early. The fixed cost is the tool build and the
gate, which run before a shard knows it is empty. Rejected: sharing the trusted tool binaries from
the plan job through an artifact; the shards keep building their own, so the plan job decides only
the job count.

### Wall-clock budget and before/after (PR #106, run 42212454082)

Budget: a sized shard is planned within 400 s of predicted test wall time at `-p 4` (the AFP-V0-060
slice bound) plus its fixed setup; the plan job adds about 80 s of its own setup, beside docs-plan
(69 s on this run), before the shards start.

| Measure | Before (16 shards) | After (sized) |
|---|---|---|
| Selected packages (driver) | 101 (99 in today's universe) | 101 |
| Table cost of the selection | 5,189 s | 5,189 s |
| Shards started | 16 | 3 |
| Shards running one package | 10 | 0 |
| Predicted max shard wall (cost table, `-p 4`) | 448 s | 448 s (bounded by the unsplit `internal/companionrelease`, 448 s) |
| Measured shard job durations | 241 s to 576 s (16 jobs, 6,189 s in all) | not observed; modelled 3 jobs of about 448 s tests + 110 s setup |
| Fixed setup spent | 16 x about 107 s = about 1,700 s | 3 x about 107 s + the plan job (about 80 s) = about 400 s |
| Critical path to the first shard | 69 s (docs-plan) | about 80 s (shard-plan, beside docs-plan) |

Two shards would leave `cmd/corvint` whole (1,147 s; its slices need three shards), so the sizing
chooses three; four or more do not shorten the predicted wall, which the 448 s whole package sets.
The sized plan's predicted wall equals the 16-shard plan's, so the run finishes in about the same
time with 13 fewer jobs. The measurement is `cishards.PredictedWallMs` over the committed cost
tables; a hosted sized run is `NOT_OBSERVED` until the owner's ci-control-plane review and a
`CORVINT_PR_TOOL_SOURCE` that carries `shard-plan.sh`.
