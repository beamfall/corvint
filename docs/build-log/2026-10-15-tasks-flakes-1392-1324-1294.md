# 2026-10-15 internal/tasks load flakes (V1-1392, V1-1324, V1-1294)

Base `32c57367d00bc2ee67401a90b8f101e07067dc78`. Darwin, 12 CPUs, shared with other agent lanes.
"Load" is the host load average at the start and end of a measurement. Burners are `/usr/bin/yes`
loops started and stopped around each measurement. BASE and fixed binaries ran concurrently under the
same burners, so each pair saw the same load. No product deadline, budget or allowance was widened.
The product-side additions are unexported and only change a bound when a test sets them. A test sets
them through a context key, or through a per-`Dispatcher` field that is zero in production.

## V1-1392: dispatch

**TestPSRDispatchAsyncSupervision**
- Root cause: two single-tick assumptions.
  - The second admitting tick ran inline, so a blocked sweep and a slow tick were indistinguishable.
  - Wall enforcement assumed one tick's kill window (`KillDeadline` + 2s, real time) finishes the
    stop. Above load 60, `ps` alone can take more than 3s.
- Fix:
  - The admitting tick now runs on its own goroutine with a 2-minute test hang bound. A sweep that
    blocks admission still fails.
  - Enforcement ticks until `Running() == 0`, bounded at 50s after the workers spawned. `killTree`
    keeps its deadline on the worker, so a later tick continuing the stop is product behaviour. The
    bound ends before the workers' own `sleep 60` could, so only a kill stops them in time. A first
    version used a 2-minute bound, and the review found a no-signal mutant then passed by natural
    exit.
- Counts, 24 burners:
  - BASE 22/40 FAIL (load 55-93 and 65-78). With the final version, BASE 13/20 FAIL against
    fixed 0/20 (load 27-74).
  - First fixed version: 0/20 (load 65-78).
- Mutations:
  - `tickPoolSweep` waiting on `job.done` fails ("blocked sweep prevented other admission").
  - Skipping `supervise()` while a sweep is active fails ("active sweep hid worker wall enforcement").
  - `killTree` sending no signals fails the final version after 59s ("active sweep hid worker wall
    enforcement").

**TestCALV0053_CancelledTickKeepsState**
- Root cause: the subject is what a cancelled tick keeps, but the tick also ran the reader's fixed
  1s retirement allowance. Above load 100 the leader exited after 1s, so the tick returned
  QUIESCENCE_UNPROVED (owner HOLD).
- Fix: an unexported `Dispatcher.readerAllowance`, set by this test to a 1-minute hang bound.
  - Zero keeps the product's fixed second (`readerRetirementAllowance`).
  - `TestCALV0053_ReaderFixedRetirementBound` and the quiescence tests still own the 1s allowance.
- Counts, 24 burners: BASE 4/40 FAIL, fixed 0/40.
- Mutation: removing `observe`'s post-read `ctx.Err()` check fails 3/3 ("cancelled tick emitted 1
  events").

**TestCALV0191_StopAfterReapIsRecoveredAfterRestart**
- Root cause: one tick after restart was assumed to finish the stop. Above load 100, one `ps` read
  took more than 3s.
- Fix:
  - Tick until no worker is running, with a 2-minute test bound.
  - Also assert the stop was not re-reaped: exactly one request and one reap.
- Counts, 24 burners: BASE 4/40 FAIL, fixed 0/40.
- Mutation: `killTree` sending no signals fails ("the worker survived the restart").

**TestCALV0053_ReaderExpiredBeforeRetirement** (added from CI go-product-shard 5 on PR #893)
- Root cause: a 50ms command deadline expired before the reader started.
  - `stateCommand` then returned the parent's "context deadline exceeded".
  - The cleanup dereferenced a nil `cmd.Process`: `exec` had refused the start, but the test had
    already recorded the command.
- Fix:
  - The cleanup checks `cmd.Process != nil`.
  - The test observes whether the reader started. Only when the deadline won that race does it
    retry with a longer test margin (50ms, 500ms, 5s, 30s). The retirement still happens after the
    deadline's allowance.
- Counts, 60 processes of `-count=5` each:
  - 24 burners, load 54-92: BASE 1 FAIL in 148 runs, fixed 0/150.
  - 32 burners, load 76-91: BASE 8 FAIL in 122 runs, fixed 0/150, with 11 deadline-won retries
    logged.
  - Each BASE failure is the CI signature (`context deadline exceeded`, then a nil-pointer panic at
    `reader_test.go:110`). The panic ends that process, so its remaining runs are missing from the
    BASE totals.
- Mutation: computing the retirement deadline from `commandDeadline + 1h` fails 3/3. Primitives run
  after expiry ("group signal failed").

## V1-1324: store

**TestPSRSweepMismatchRetries, TestPSRAmbiguousResponseReconciliation**
- Root cause: on a quiet host, each sweep observation fits its fixed bound. These are the source
  Git observation (2s) and the runner-identity probe (1s, with a 250ms pipe delay).
  - At load 60-70, `git` took 1-2s and `ps` 3.3s.
  - The observation then ended TIMEOUT, or with runner identity unavailable.
  - The subject (retry or reconciliation) was never reached.
- Fix: a context key `sweepObservationBoundKey`, private to package tests.
  - It lifts only those observation bounds.
  - It is set through `PSRTestLiftObservationBounds` in the internal test file.
  - The group-cleanup proof (the `context.Background` cleanup allowance and the command pipe delay)
    never reads it.
  - Both tests now use it, plus a 120s safe-reuse timeout.
- Counts, 24 burners:
  - Load 55-97: BASE Mismatch 8/8 FAIL, Ambiguous 8/8 FAIL (24 subtests).
  - Load 60-72 (earlier run): BASE 20/20 FAIL for both.
  - Fixed: Mismatch 6/6 PASS; Ambiguous 5/6 PASS (17/18 subtests).
- Mutations:
  - Verification always passing fails Mismatch ("entry freed").
  - `reconcileSweep` returning pending fails Ambiguous ("bounded reconciliation: pending=true").
- Remaining quiet-host assumption, recorded in the test file: a Git observation must still prove
  group cleanup inside the fixed pipe delay and cleanup allowance. At load 113-206 that failed
  2 of 18 runs as an unproved `UNKNOWN`, which `sweepSourceClass` reports as SOURCE_CHANGED. The one
  fixed Ambiguous failure above is the same case.

**TestCALV0089_ProgramWallExpiryEndsContinuation**
- Root cause: the shared program wall runs from `OpenWorkflow`. At load 160-180, setup took more
  than the one-minute wall, so SPAWNING was refused LIMIT_EXCEEDED. BASE failed 3 of 4 at load
  159-184: 2 LIMIT_EXCEEDED, 1 SURVIVORS.
- Fix:
  - The program wall is 3 minutes, a test-only setup tolerance.
  - The implement stall sleeps 600s, so only a wall stops it. The 600s stage wall stays above the
    program wall.
  - A setup slower than 3 minutes still fails, as LIMIT_EXCEEDED.
  - The test runs in parallel, so the longer wait overlaps other tests.
- Counts, load 84-145: BASE 6/6, fixed 6/6. The failure did not reproduce at that load.
- Mutations:
  - Dropping only `programBound` passes, because the continuation guard in `workflow.go` independently
    refuses to continue after the wall.
  - Dropping that guard as well fails 1/1, at `:674` with SURVIVORS (210s).
- The SURVIVORS mode (fixed supervisor drain bounds) is not fixed. It is a residual.

**Class decision with V1-1294**
- One seam (`sweepObservationBoundKey`) covers the V1-1324 sweep tests.
- CALV0089 is a different class (program wall against setup time), fixed by test configuration.
- V1-1294 is a third branch, the signal-0 listing fast path, already fixed by #909. The sweep seam
  does not cover it.

- Root cause: recorded in `2026-10-14-batch3-process-timing-flakes.md` and fixed by #909, with no

  answers EPERM for a just-reaped group.
- `-count=20 -run 'TestCALV0188_GroupListingOverrun$'` under 24 burners (load 84-145): 20/20 PASS.
- Package duration:
