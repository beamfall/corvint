# CEM 0.1 interoperability algorithms

This file removes implementation choices from the `cem/0.1` acceptance decision. Terms such as
byte, SHA-256, UTF-8, and Git object ID are literal. Implementations must not normalize text,
paths, JSON strings, line endings, Unicode, or whitespace. The schema is a shape aid; these
algorithms and `manifest.json` are also normative.

> **Pre-release security erratum — 2026-08-23.** This revision replaces every earlier `cem/0.1`
> draft and vector manifest. It closes fail-open handling of line-joining whitespace changes,
> unbound create/delete modes, special or contradictory Git mode metadata, and unbounded LF
> tokenization. A consumer claiming `cem/0.1` conformance MUST implement this revision and reject
> the exact negative vectors identified by `expectedCode` in `manifest.json`; an earlier 0.1 draft
> is not an accepted compatibility profile.

## Closed patch recipe

A manifest case selects patch bytes with exactly one of `patch` or `patchRecipe`. CEM 0.1 defines
one recipe ID only: the exact ASCII string `cem/0.1-lf-overflow-x-lines`. Its complete
materialization is the two bytes `78 0a` repeated exactly 262,145 times, producing 524,290 bytes,
262,145 LF bytes, and SHA-256
`cfecb16854630a4d141b429fdfdcdc73bb48124ac47375b5896c634037c9eee6`. The generated bytes are the
case's exact patch input but are not a checked-in artifact and therefore do not appear in
`artifactSha256`.

The harness MUST reject a non-string recipe ID, an ID longer than 64 UTF-8 bytes, an unknown ID,
both selectors, or neither selector. It MUST check the fixed output length, LF count, and digest
before invoking a consumer. This is a single closed fixture transport profile, not a generator
language; no count, unit, encoding, interpolation, or other recipe parameter exists.

## JSON and version dispatch

Read at most 4 MiB of UTF-8 JSON. Reject malformed UTF-8, duplicate object keys at any depth,
non-integer or non-finite numbers, a non-object root, an unpaired surrogate after JSON decoding,
missing fields, and every unknown field. Integers are mathematical integers in
`0..9007199254740991`; booleans are not integers. Dispatch on the exact string `cem/0.1`.
Any other `spec`, including `cem/0.2`, is rejected by a 0.1 consumer. There are no compatible
minor versions and no extension fields. An enclosing tool-specific envelope may carry extensions.

Paths are non-empty UTF-8 strings of at most 512 encoded bytes. They are relative POSIX paths:
no leading `/`, backslash, NUL/control byte, empty segment, `.` segment, or `..` segment. Do not
case-fold or Unicode-normalize them.

## Canonical identity encoding

Canonical identity JSON is UTF-8 with no BOM or trailing LF. Object member names are sorted by
their Unicode scalar values; all identity member names are ASCII, making this byte ordering
unambiguous. Emit `:` and `,` without spaces. Emit integers as shortest unsigned decimal and null
as `null`. Encode strings as JSON strings: escape `"` and `\`; use `\b`, `\f`, `\n`, `\r`, and
`\t` for those controls and lowercase `\u00xx` for other U+0000..U+001F values; emit all other
Unicode scalar values as their shortest UTF-8 sequence. `/` and non-ASCII characters are not
escaped. Identity paths already exclude controls, backslashes, and unpaired surrogates.

Evidence identity is exactly this logical object:

```json
{"blobOid":OID,"path":PATH,"span":{"end":END,"start":START},"spanSha256":DIGEST}
```

Its ID is `evidence:sha256:` plus lowercase hex SHA-256 of the canonical bytes. A hunk body is the
exact bytes after its `@@` header through its final body/no-final-newline marker. Let
`contentSha256` be its lowercase SHA-256. Hunk identity is exactly:

```json
{"contentSha256":DIGEST,"newPath":NEW_OR_NULL,"newRange":{"count":N,"start":S},"oldPath":OLD_OR_NULL,"oldRange":{"count":N,"start":S}}
```

Its ID is `hunk:sha256:` plus lowercase hex SHA-256 of the canonical bytes. The golden Unicode,
SHA-1, and SHA-256 IDs in `maps/valid/` are mandatory algorithm vectors.

## Patch byte profile and parser

Read at most 8 MiB. Before splitting, reject any input whose LF-tokenizer record count exceeds
262,144: count LF bytes, then add one exactly when the non-empty input does not end in LF. Split
only after LF bytes and retain each LF; retain a preceding CR as payload except where a header
grammar explicitly permits CRLF. This bound applies every time the LF tokenizer is used, including
patch and blob bytes. Reject NUL, binary markers, empty input, zero textual hunks, and any byte
outside the states below. Paths in headers are literal UTF-8; quoted/escaped Git paths are not in
0.1.

For an ordinary modification whose old and new paths are both non-null, accept either `--- OLD`
immediately followed by `+++ NEW`, or this state machine. Creates and deletes MUST use the state
machine so their tree mode is bound:

1. `diff --git a/OLD b/NEW` using the literal paths later declared by the file headers. For create
   or delete, repeat the non-null path in both `diff --git` positions.
2. Before file headers, accept each applicable metadata line at most once: `index` with 4..64
   lowercase hex OIDs and an optional mode; at most one mutually exclusive `new file mode` or
   `deleted file mode`; paired literal `rename from`/`rename to`; and at most one `similarity index`
   or `dissimilarity index` in 0..100 percent, written in canonical decimal with no leading zero
   and allowed in any state-machine group, not only a rename (erratum 2). Every mode carrier MUST
   be exactly `100644` or `100755`. `old mode` and `new mode` are unsupported in 0.1 and MUST be rejected. Reject
   misplaced, repeated, incomplete, or header-disagreeing metadata.
3. `--- a/PATH` / `+++ b/PATH`; `/dev/null` is allowed only on the old create side or new delete
   side. A create MUST carry `new file mode`; a delete MUST carry `deleted file mode`; and an
   optional `index` mode MUST equal that create/delete mode. Modified rename metadata and both
   headers must agree exactly.
4. One or more contiguous hunks; every create hunk has old range `0,0` and every delete hunk has
   new range `0,0` (erratum 2). A file path pair may occur in only one contiguous file group;
   an old path and destination path may each be consumed only once.

A hunk header is `@@ -START[,COUNT] +START[,COUNT] @@` with an optional uninterpreted suffix (any
bytes, erratum 2) and optional CR before LF. Omitted count means 1. Zero count permits start 0; nonzero count requires a
one-based start. Each value and computed end must fit the wire integer bound.

Consume exactly the declared old/new line counts. Body prefixes are space (both), `-` (old), and
`+` (new). At least one changed line is required. Every body record MUST end in LF. The exact
marker record `\ No newline at end of file` plus LF may follow a body line and removes that line's
LF from that side's reconstructed payload; it is the only way to remove an LF (erratum 2). Reject surplus payload, overlapping/out-of-order old ranges,
inconsistent new positions, duplicate derived hunk IDs, and trailing or top-level material.

## Patch/base simulation

Resolve `baseRevision^{commit}` and require byte-for-byte equality with the supplied full lowercase
40- or 64-hex OID. Group hunks by `(oldPath,newPath)` in patch order. Read base blobs through Git
objects, never through the worktree. A create requires the destination absent; a delete requires
the old path, a base tree mode equal to its `deleted file mode` (else `diff-metadata-mismatch`,
erratum 2), and must produce empty bytes; a rename requires the old path and an absent destination.
Copy untouched base lines, compare every context/removed payload byte-for-byte, append context/added
payloads, and verify every old and new cursor. This is a simulation only; do not execute the patch.

## Evidence and disposition checks

For every evidence record, resolve `path` at the exact base tree to a blob whose mode is exactly
`100644` or `100755` (not a symlink or gitlink), require
its full OID to equal `blobOid`, read at most 64 MiB, require a non-empty half-open raw-byte span in
bounds, and verify `spanSha256` and the evidence ID. Support both SHA-1 (40 hex) and SHA-256 (64 hex)
Git repositories; mixed-format identities do not resolve. Total distinct blob bytes read are at
most 128 MiB. Every evidence ID is unique and cited; every basis pair is unique.

Recompute all patch hunk IDs and require one map entry per hunk and no others. `supported` requires
reason `evidence-backed` and 1..32 bases whose relations are one of `specification`, `decision`,
`test-claim`, `implementation`, `call-site`, `dependency`, or `incident`. `unknown` requires an
empty basis and one of `no-evidence`, `insufficient-evidence`, or `conflicting-evidence`.

For `mechanical`, concatenate all removed payload bytes and all added payload bytes separately;
both must be non-empty and unequal. `line-ending-only` is true exactly when replacing every CRLF
pair with LF makes the concatenations equal. `whitespace-only` first requires equal removed and
added LF counts and equal LF-tokenizer record counts. For each corresponding record, delete only
horizontal bytes in `{09,0d,0c,0b,20}` and require byte equality; LF record boundaries are retained
and therefore cannot be joined or split. No other mechanical reason exists.

Limits are 4,096 evidence items, 2,048 hunks, 32 bases per hunk, 64 reason UTF-8 bytes, 262,144
LF-tokenizer records per input, 1,024 Git operations, 10 seconds per Git operation, and a 30-minute
verification budget. The cumulative deadline is a finite hostile-input resource bound and hang
detector, not a performance threshold: operation count bounds fan-out, the per-operation timeout
bounds one stuck child, and the cumulative deadline bounds many near-timeout children without
rejecting valid work merely because the host is loaded. A consumer may use lower declared
operational limits, but must report that as unsupported/operational, not invalid. This operational
limit changes no CEM wire value or frozen conformance vector.

## Same-path drift

Resolve an optional target to an exact commit OID. For each base evidence item, inspect only its
literal same path; never follow a rename. Missing path is `deleted`. Identical blob OID is `stable`
with the original target span, whatever the entry mode. A different entry that is not a blob with
mode exactly `100644` or `100755` (a symlink, directory, or gitlink) has no file content: it is
`deleted` with null target blob OID and span, and is never searched (erratum 1, 2026-09-12; see
`IMPLEMENTATIONS.md`). Otherwise take the exact base span bytes and search the entire target
blob byte-for-byte. Count overlapping matches by resuming one byte after each match. Zero is
`stale`; exactly one is `relocated` with that half-open target span; two or more is `ambiguous` with
no target span. Never normalize or fuzzy-match. `stable` and `relocated` accept; any `stale`,
`ambiguous`, or `deleted` item rejects the target check.

## Repository construction

The corpus contains raw trees, not a Git database. Initialize with the requested object format,
disable system/global configuration, copy `repository/base` without text conversion, add all files,
and commit with the author, timestamp, and message in `manifest.json`. File modes are `100644`.
The resulting OID must equal `repository.revisions[objectFormat]`. A SHA-256-incapable Git runtime
reports the required case as `UNSUPPORTED`; it must not report full conformance PASS. Construct each
non-stable target from the SHA-1 base, apply its exact target patch, and commit with its manifest
timestamp/message and the same author. Require the declared target revision before testing drift.
