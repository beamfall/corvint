# CEM 1.0 experimental candidate

This Apache-2.0 packet specifies `cem/1.0-experimental.1`. It is not the stable
`cem/1.0` profile, a relabelled 0.3 map, or permission to promote a release.
Historical CEM 0.x packets and producer defaults are unchanged. Existing readers
must reject this profile unless they implement its explicit candidate interface.

The candidate joins immutable Git evidence and mapped hunks to references for
native Tasks criteria and retained runner receipts. Verification proves canonical
Git binding and reference integrity only. It does not verify native Tasks
record authority, current applicability, runner source Git identity, authenticated
execution, test adequacy, or criterion discrimination. Every successful result
retains those limitations. A generic test failure never means a mutant was killed.

The normative contract is [ALGORITHMS.md](ALGORITHMS.md); the structural schema is
[candidate.schema.json](candidate.schema.json). Cross-record identities, duplicate
keys, byte limits, Git proofs and filesystem rules require algorithmic checks in
addition to JSON Schema. The manifest pins the new candidate vectors. None of the
historical frozen 0.1/0.2 packet bytes or digests are changed.

The first candidate admits the 0.2 hunk vocabulary. CEM 0.3 structural mechanical
reasons, coverage and discrimination witnesses remain unavailable here; migration
of those capabilities and all existing consumers remains a stable-release blocker.
The native candidate API and standalone portable `verify-candidate` command are
opt-in. Core producers, existing CEM CLI/MCP, OCM, frontier, TCQ, obligations,
completion, bundles and attestation consumers do not acquire candidate support.

Both implementations are Corvint-authored reference portability evidence. They do
not establish independently authored interoperability, external adoption or matched
external outcome evaluation. Vector authority records are manufactured examples,
not observations of native Tasks authority or actual runner execution.
